## 1. 目标、范围与边界

### 1.1 目标

为填报与流程、考勤、工具与自动化、可视化、知识与文档等获授权消费者提供统一的数据接入、加工、发布和查询能力，使：

-   业务数据"接入一次，发布一次，多处消费"，不再出现同一份数据被不同模块各自导出、各自加工、各自出错的情况；
-   每一个对外发布的指标都能回答"这个数字是哪条流水线、用哪个版本的规则、在什么时间点算出来的"；
-   计算能力可以随规模增长而更换执行引擎，不要求上层消费者（可视化、Agent）感知这种更换。

### 1.2 范围内

-   数据接入（实时事件、增量同步、批量导入、外部数据源）；
-   原始层、标准层、业务层的存储与流转规则；
-   流水线定义、版本化、执行与恢复；
-   Dataset / Query 服务层：契约、权限、缓存、计划选择；
-   数据质量规则与血缘记录；
-   业务自定义基表、分类与映射的建设、版本发布、关联和异常核验；
-   与工具与自动化中心共用的 JobRun
    执行协议（本文只定义数据处理侧如何使用，协议本身归属参见 1.3）。

  B --> C["原始批次与数据质量"]

  E --> D["Dataset 与版本"]
  D --> F["物化 Dataset 与查询"]
  F --> G["可视化、表单与 Agent"]
  F --> H["数据服务发布"]

质量校验、版本记录与权限贯穿整个链路。三类图保持独立语义：数据血缘由数据处理领域拥有，描述数据/字段如何产生；关系/依赖图描述跨资源引用与影响关系；运行拓扑描述某次运行及其
Job / Executor /
外部调用状态。后台治理可消费后两类及血缘投影进行统一查看，但不建立第二套血缘或运行事实。关系、血缘与拓扑读取资产定义、依赖事件和运行遥测，向管理员提供影响分析与运行诊断；不把所有模块强制串成单一路径。

业务人员维护的基表从文件、已有数据库或页面编辑进入受控基表资产；发布后作为
DAG 的输入，与原始/标准数据按显式规则关联，再形成
Dataset。基表不是所有外来数据的准入前提。

控制面管理定义、权限、版本、质量及发布；执行面运行 SQL、Polars
和后续注册算子。接入与发布可形成多条链路，不要求所有数据经过图中每个物理节点。

正式调用链遵循
`Human / Agent / Automation / Domain -> Data Capability / Command -> Data Processing Domain -> PipelineRun -> JobRun / JobAttempt -> Executor`。同步
Query 不必人为创建
Job；重计算、批处理等按能力契约进入持久执行。跨域业务事实仍由原领域拥有：数据处理可以消费其受控
Dataset / API /
Event、形成派生数据与分析结果，但不得通过共享数据库或事件旁路改写
BusinessRecord、AttendanceResult、KnowledgeVersion 等对象。

### 3.2 权限模型

沿用总框架第 8.5 节的角色 + 资源 ACL 模式，本方案补充的资源类型：

-   **DataSource**：谁能配置接入凭据、谁能查看接入状态；
-   **Pipeline**：谁能编辑、谁能发布、谁能触发手动执行；
-   **Dataset**：谁能定义、谁能订阅、字段级/行级权限如何标注；
-   **Query**：调用方（人工/Agent/自动化）分别鉴权，参数化查询的参数范围本身也受权限约束（例如某角色只能查自己部门）。
-   **ReferenceTable**：按空间和资源划分查看、编辑、校验、审批（如启用）、发布和回退权限；编辑权不自动获得其他来源或结果
    Dataset 的读取权。Agent 与人工遵循同一能力授权、审计和发布门禁。

角色不自动获得 Dataset
访问权------制作、发布角色与数据访问权限分开授权，与总框架 8.5
节原则一致。

额外约束：关系、血缘、运行拓扑与诊断下钻均按资源 ACL
过滤，错误样本和原始值按权限脱敏；Consumer 登记与访问凭证分离。

"可写计算"是独立于"可读来源""可分享结果""可认证发布"的权限，不以岗位头衔自动放通。用户可复制获授权的权威规则到个人工作区（不能复制无权查看的源码或敏感输入），在相同授权数据、输入版本、参数和时间范围下重算；比较输出总量、行级差异、未匹配项和规则版本，生成可提交给口径负责人的差异报告。个人结论不能覆盖权威数值；报告也不能未经授权暴露他人明细。

共享时同时检查创建者对上游的使用/再分发权限和接收者对来源数据的可访问范围；共享代码、共享计算结果、共享输入资产为三个独立选择。动态查询按接收者权限重新过滤；物化结果若不能证明接收者只能看到获授权的行列与聚合，则拒绝共享或先生成经过批准的脱敏副本。撤销来源或接收者权限后，查询、缓存、下载与后续重算同步失效；已合法导出的副本遵循使用方留存政策，不许承诺技术上能追回。个人算出的结果即使数值与权威相同，也不得冒充权威标识。

## 4. 核心对象模型

  -------------------------------------------------------------------------------------------------------------------------
  对象               定义
  ------------------ ------------------------------------------------------------------------------------------------------
  DataSource         外部或内部数据来源的接入配置，含凭据引用、接入方式（事件/增量/批量）、水位

  RawRecord          原始层记录，保留来源、批次、版本、变更类型、原始文件引用

  StandardRecord     标准层记录，完成校验、去重、类型转换、人员部门映射、时区统一

  BusinessEntity     业务层的关联结果，如"人员-部门-日期-工时-出勤"的汇总行

  Pipeline           版本化的加工流程定义，由多个 Node 组成的 DAG

  Node               流水线中的单个处理步骤，声明使用的 Executor 类型及输入输出 Schema

  Operator           DAG 节点所引用的版本化计算语义与输入输出契约；可由内置实现、插件贡献或工具实现承载

  Executor           实际领取 JobRun / JobAttempt 并执行 Operator 的受限运行实现（如 SQL、Polars、后续认证宿主）；不拥有
                     DAG、质量或发布语义

  Dataset            对外发布的数据契约，含字段 Schema、权限声明、新鲜度声明、来源流水线引用

  PersonalResult /   个人计算输出及定向授权的版本化结果，标明非权威、所属用户、输入授权、来源版本、留存期限与接收范围
  SharedResult       

  Query              Dataset 之上的参数化查询定义

  Metric /           有业务域和责任人的指标及不可变口径版本；绑定公式、统计粒度、时间口径、可用维度与剔除规则版本
  MetricVersion      

  ExclusionRule /    版本化的分子/分母剔除规则，以及有稳定身份、来源和生效期的业务切片定义
  Dimension          

  Snapshot           某个时间点/某次汇报固定下来的数据快照，绑定 snapshotId

  QualityRule        数据质量检查规则及其检查结果

  ReferenceTable /   业务自定义基表的稳定资产身份及不可变发布版本；记录字段契约、业务键、适用范围、负责人、来源和生效口径
  ReferenceVersion   

  MappingRule        某一来源字段/业务概念与基表之间的显式关联规则，含键、规范化、时间判定、基数、异常策略和版本

  LineageEdge        血缘关系记录：某个 Dataset 字段/某次发布由哪些上游 RawRecord 批次、哪个 Pipeline 版本产生

  PipelineRun        一次流水线领域运行记录，拥有 DAG 推进、质量门禁、输出提交与发布结果；可关联一个或多个 JobRun，不与 Job
                     状态机合并
  -------------------------------------------------------------------------------------------------------------------------

对象之间通过引用关联，不构成强制单链：一个 Dataset 可能由多个 Pipeline
共同产出的 BusinessEntity 组成；一个 Pipeline 可以产出多个 Dataset。

补充对象：Connection（连接配置及凭据引用）；Asset（原始文件及媒体引用）；QuarantineRecord（异常行及修复状态）；DatasetVersion（正式发布的输入、规则和输出证据）；DataService/Consumer（服务契约和登记的调用方）；DraftRevision（版本化未发布草稿）；Diagnostic（错误证据与修复链）；Telemetry（时序状态、指标和追踪）。Dataset
稳定身份与其来源连接、正式版本分离；RawRecord、StandardRecord、BusinessEntity
是逻辑层次，可由受控表或视图承载。

## 5. 数据连接、接入与资产

-   Source/Connection 代表
    Excel、CSV、Parquet、数据库、JDBC/ODBC、REST/OData、企业集成平台
    等来源。企业集成平台
    提供何种目录、资产或数据服务能力须按实际协议确认；若有独立元数据能力，作为专用
    Connector 设计。
-   Dataset 是稳定的数据资产身份，与来源连接分离。同一 Dataset
    可在开发、测试、生产绑定不同来源，但必须验证 Schema
    与数据契约；上层通过稳定引用而非来源地址依赖它。
-   接入记录来源、凭据引用、Schema、批次、时间、增量游标、写入策略与操作主体。连接的权限、超时、分页、重试和限流按来源分别配置。
-   接入过程包括发现、预览、画像、质量验证、标准化与发布。画像包含行列数、类型、空值、唯一性、重复、分布、疑似键和
    Schema 漂移；大数据使用受控抽样或服务端聚合。
-   外来临时 Excel 可以按授权快速创建数据资产，再选择是否纳入稳定
    Pipeline；不能要求事先来自内部基表。

导入使用统一 Asset
引用原始文件，接入器记录采集时间、来源版本和水位；批量导入写暂存区，验证后原子提交。图片、视频等附件由
Asset
保存并通过业务键与稽查问题关联；数据行只保存附件引用和授权信息。连接端分别管理凭据、最小权限、分页、超时、重试和限流。

### 6.1 业务基表与映射管理（首期基线）

**定位与归属。**
业务基表是业务人员定义且会修订的分类、映射、参数或系数表，例如"工号/编码→分类""分类＋部门→系数"。它不同于系统导出的事实数据，也不默认等同于全企业唯一的人事主数据。若企业已有权威主数据，应记录其所有者和来源；本模块只管理授权引入或本地维护的业务口径，不冒充其权威源。一个基表可供多个
Pipeline 复用，外来 Excel 仍可不依赖任何基表直接进入流程。

**建立和维护。** 授权用户可在页面定义字段并编辑条目、从 Excel/CSV
批量导入，或把既有数据库表登记为来源。每张基表必须登记稳定
ID、名称、负责人、业务说明、作用空间、键及唯一性口径、字段类型、空值规则、适用范围、是否按生效日期取值、来源、更新频率和下游影响。导入保留原文件与工作表/行号；页面修改保留修改人、原因和审计。草稿可协作、预览与校验，已发布版本不可原位覆写；是否需要业务审批由权限与业务规则决定，不能以审批缺失阻断所有基表建设。

**发布和时间语义。**
发布前检查键重复、同一作用范围内的有效期重叠、类型/值域异常、失效引用与下游兼容性。支持无生效期的当前映射，以及按业务日期匹配的区间映射；生效边界使用明确的半开区间
`[valid_from, valid_to)`，时区和日期粒度由业务定义。执行固定
ReferenceVersion、MappingRule
版本和来源批次；同一发布版本可复算。若追溯历史，应同时记录业务生效期与记录/发布时间，不把"后来录入的旧日期"伪装成当时已知。修改基表须展示受影响
Dataset/日期范围、预估重算代价，明确选择仅影响后续、回补历史或生成并列修订版；已发布历史结果不静默改变。

**连接和关联。** 同一 PostgreSQL 实例中授权可读的表/视图可经 SQL 直接
JOIN；远端 PostgreSQL
可在网络、权限与负载允许时用受控连接/外部表，其他数据库经相应 Connector
接入。跨库实时关联不是默认方案：频繁使用、需稳定历史或高负载的数据优先按批次/增量同步到受控表，再与固定基表版本计算。选择依实际新鲜度、来源限流、查询计划和实测负载；所有方式对上层暴露一致的
Dataset
契约。数据库外键可以约束同库存储关系，但不能替代跨文件、跨库和有效期关联的
Pipeline
规则及质量校验。原始层不得由人工直接改写；基表草稿和正式版本由其自身受控写入路径管理。

**关联规则与异常。** MappingRule 必须显式指定源
Dataset/字段、基表及版本、精确或复合键、字符串规范化方式、业务日期字段、预期
1:1 或 1:N
基数、字段权限及无匹配/多匹配策略。工号等稳定编码优先；姓名仅可作辅助核验，不能默认作为唯一键。需要多分类归属时先声明分摊或展开语义，防止
JOIN
使工时重复计数。预览提供匹配率、空键、重复键、有效期冲突、未匹配/多匹配样本、输出行数与金额/工时守恒检查；关键映射可配置阻断发布，其他异常进入
Quarantine
等待修正。无证据时不自动把未匹配项归入"其他"，模糊匹配只作为人工复核候选。

**工时样板。** 原始工时 `(工号, 日期, 工时)`
与考勤结果先按受控键对齐，再以 `(工号或岗位编码, 日期)`
取当日有效的职业分类，之后按 `(分类编码, 部门/业务范围, 日期)`
取有效系数，计算并发布效率
Dataset。运行证据绑定工时批次、考勤版本、两张基表的发布版本及规则版本。首期须盘点现有手工维护的基表，逐表区分主数据引用、分类、映射和参数；真实键、部门口径与公式由业务人员核对后冻结，不从样板反推所有表的结构。

**业务友好的表形与计算表形分离。** 基表可以继续按
`姓名、工号、1月、2月、3月…`
维护；适配规则声明每个月份列的年份、月份、列代表岗位还是部门、空值语义、重复人员处理与原单元格定位。平台生成按
`(工号, 年月, 岗位/部门, 基表版本)`
查询的规范视图或受控中间结果，而不要求业务人员手工改成长表；需要时可重新透视成宽表展示/导出。若一人同月中途换岗，月列本身无法表达哪天变动，应在同一基表增加"例外有效期记录"或使用更细粒度的业务输入，并声明覆盖优先级；系统不得臆造日级历史。按事件日期取月份列，相当于电子表格中 VLOOKUP＋MATCH 这类查找的可审计表达，但只是通用表形适配中的一个例子。支持列名来自业务值的动态取列、跨工作表/多级表头、宽转长、长转宽、行列转置、公式迁移与字段派生；复杂表头先由授权用户显式映射，不能默默误读。

**节假日与时间运算。** 建议业务维护形态采用
`节假日名称、日期、适用部门/范围、规则引用`，日期保持真正的日期字段；"2025""2026"作为筛选/分组或视图表头即可，不要求按年拆列。一个节假日跨多日时明确登记每个业务日或开始/结束日期及展开规则。当前部门假日业务日定义为当地日期
`D 08:30:00` 至
`D+1 08:30:00`，采用左闭右开区间；这是可配置的部门规则，不写死为全平台自然日。计算时把待算时间段与所有适用的假日区间求交，先合并重叠的待扣区间，再扣除交集时长；同一时间落入多个节假日不能重复扣除。遇到时区、夏令时、跨月、跨年、夜班、零时长、反向区间及与排班/请假规则冲突时，按业务确认的优先级和时间计量口径处理。结果附可解释明细：原始区间、命中规则、每段重叠、去重后的扣除和剩余时长。

**开放的运算模型。**
基表既可用于等值/复合键关联，也可作为规则参数、分类词典、列选择依据、区间集合、计算函数输入、校验依据或结果补全来源。DAG
支持表形转换、动态列选择、按键/有效期/区间匹配、分段、集合运算、窗口、聚合、条件分支与用户定义计算；结果必须声明输入/输出
Schema、粒度、确定性、错误与权限语义。先用内置算子与可授权的 SQL/隔离
Python
解决新场景；用户可在自身授权范围内编写、试运行、版本化并发布可复用的规则/算子实现，经过契约与资源校验后注册使用，不以平台发版作为每条新业务规则的前置条件。安装新运行时、原生二进制或外部网络能力仍由平台治理，不承诺无条件执行任意代码。

## 7. Pipeline、DAG、控制面与执行面

### 7.1 分层

沿用总框架 12.1 节的划分：

-   **控制面**：Dataset / Query
    定义、Schema、权限、血缘、质量、执行计划选择。控制面对上层（可视化、Agent）暴露的契约保持稳定，不随执行引擎变化。
-   **执行面**：实际跑计算的地方。首期为 PostgreSQL SQL 与隔离 Polars
    Worker；后续按需接入更多 Executor（见第 8 章）。

控制面与执行面之间的边界是本方案的核心资产：**只要执行面的输出满足
Dataset
字段契约、权限过滤前的原始结果格式、错误与新鲜度语义,控制面完全不关心底层是
PostgreSQL 算的还是 Polars 算的还是未来某个 OLAP 引擎算的**。

### 7.2 流水线即 DAG

流水线（Pipeline）建模为有向无环图，节点是
Node，边表示数据依赖。这是对总框架 6.5 节"配置节点、SQL 节点和 Python
节点进入同一版本化流水线"的具体化，新增两点：

1.  节点类型不再局限于 SQL / Python 两种，而是通过 **Executor
    注册表**开放，任何新增计算能力（现在是
    SQL、Polars，未来可能是外部服务调用、专用算子）都以同一种方式接入
    DAG，不需要每次新增类型都改动流水线引擎本身；
2.  每个 Node 的输入输出必须声明 Schema、资源预算上限、幂等键，DAG
    引擎据此做依赖排序、失败重试范围界定（只重跑失败节点及其下游，不整链重跑）。

### 7.3 编排与关联

统一 DAG 节点契约规定输入、配置、输出
Schema、版本、权限、资源预算、确定性/副作用、错误与可观测信息。基础算子包括筛选、选列、重命名、转换、填充、去重、关联、映射、校验、聚合、窗口、SQL、受控
Python 与发布；可视化编排与高代码编辑共用同一执行模型。SQL/Python
的运行环境、权限和资源隔离服从总框架，扩展算子按类型注册与授权。

关联支持常用
JOIN、Lookup、映射、多键与时间范围关联；同时支持基表宽/长表形转换、按业务值动态取列、区间交集及扣除等可组合运算，详见
6.1。模糊匹配必须展示匹配置信和人工复核入口。执行前提示字段类型冲突、空键、键重复、预期
1:1/1:N/N:N、未匹配率和可能的行数膨胀。大规模风险预估基于统计信息，标注其估计性质，并对超预算任务阻断或等待授权。

可视化编排和高代码编辑共享版本化
DAG；编辑预览有抽样与资源边界，发布前校验
Schema、依赖和权限。关联的统计预估仅为估计；高基数和可能的行数膨胀触发额度检查。

## 8. Executor 与算子扩展协议

### 8.1 注册与开放范围

Executor 注册表登记：

-   executorId、类型（sql / polars / external_service / 未来类型）；
-   输入输出 Schema 校验方式；
-   资源预算声明（CPU、内存、超时、并发上限）；
-   执行身份与凭据范围（只读/写、可访问的数据对象范围）；
-   幂等与重试语义；
-   版本与兼容性声明。

首期建议范围（保守方案，未确认前按此执行）：

  ------------------------------------------------------------------------------------------------------------------------------------------------------
  Executor 类型                      首期是否实现                       说明
  ---------------------------------- ---------------------------------- --------------------------------------------------------------------------------
  SQL（参数化，PostgreSQL）          是                                 复用总框架 6.5 节既有能力

  Polars（隔离进程）                 是                                 复用总框架 6.5、12.4 节既有约束

  外部服务调用（HTTP，走能力网关）   协议预留，首期不实现具体节点类型   用于将来接入工具中心已注册的脚本能力

  Rust / Java / C++ 原生算子         协议预留，不实现                   仅在总框架 16.1
                                                                        节"负载、团队能力、运维成本证明收益"时按同一协议接入，不因为协议预留就默认会用
  ------------------------------------------------------------------------------------------------------------------------------------------------------

用户自定义业务计算在首期即可通过授权 SQL 和隔离 Python
节点提交并复用，不等同于首期开放任意第三方二进制安装。自定义算子实现可登记契约、精确版本和受控执行身份；新增业务规则不需要改平台核心或等待平台版本发布。节点提供样例预览、测试运行、诊断、输入输出约束及成本上限；发布后供有权限的流水线引用。

个人节点/算子的"保存版本"和"仅本人启用"不要求业务权威发布权；若作者愿意，可另行申请在业务项目共享或成为公共能力。个人规则即使被共享也仍属非权威，除非由相应口径责任人按
3.3 认证发布。

**协议现在就设计、具体实现按需要开通**，这样不会因为首期只用两种
Executor 而在将来扩展时重构 DAG 引擎和调度层。

### 8.2 算子与运行约束

基础算子包括筛选、选列、重命名、转换、填充、去重、关联、映射、校验、聚合、窗口、SQL、受控
Python 与发布；均声明输入/输出
Schema、版本、权限、资源额度、确定性、副作用、错误语义和观测字段。对
Connector、转换算子、渲染器、组件及任务执行器分别注册与授权；本章的
Executor
仅负责计算执行，不赋予其他扩展类型跨边界能力。外部服务和原生算子实际开放仍须第
0 章决策。

### 8.3 插件交付与版本绑定

遵循总框架第 8.6 节。OperatorContract
声明运算语义；OperatorImplementation 提供具体实现；Executor
提供执行环境；PluginPackageVersion
交付其中一种或多种贡献，各自注册与授权。内置
SQL、Polars、解析器及质量规则首期即通过相同契约注册，后期才开放更多具体实现。

PipelineVersion
固定节点契约、算子实现、插件精确版本和产物摘要。PipelineRun
记录实际组合、Executor、输入、配置、授权及检查点版本；授权仍按当前有效策略裁决。自动重试默认沿用原实现，不解析
latest；替换实现产生新执行意图，跨版本续跑须验证检查点兼容和副作用。停止新用阻止新绑定与准入，排空处理在途任务；紧急禁用阻止继续使用受影响实现，保留运行证据并由领域决定取消、待核对或恢复。

插件卸载不删除原始批次、Dataset
或历史运行。大表以授权引用和受限数据通道交换；运行遥测不承载完整业务数据。进程内事件不代替持久业务事件或数据库提交。

### 8.4 个人插件生命周期与可见性

插件贡献须声明其类型（计算算子、连接器、执行器等）、包/实现版本、宿主兼容性、输入输出与请求能力；"个人"是分发范围和授权状态，不是绕过运行约束的插件类型。允许用户将受当前宿主支持的插件实现上传到个人空间，自动完成格式、完整性、依赖、能力请求和静态/运行校验；通过后在隔离测试环境用授权的样本/数据试运行，再由本人启用。上传、测试、启用、停用、删除和版本升级分别记录，不提交平台目录、不进入他人搜索结果、默认不触发人工推广审核。未通过自动安全/兼容校验的包可保留为不可运行草稿并给出诊断，不能在共享服务器上以"仅本人使用"为由放行。

个人插件默认只由本人调用，仅读取本人有权访问的资源；不继承平台服务账号、管理员或权威发布者权限。禁用默认网络、文件系统和凭据访问，按宿主批准的能力逐项开放；限制
CPU、内存、执行时间、并发与输出量，进程/容器隔离及终止清理由宿主提供。SQL/Python
代码作为首期可用的个人插件式实现；上传包含额外第三方依赖、原生代码或新运行时的包，只有在相应隔离宿主具备可靠校验和能力限制后才能运行，不应以一套通用容器承诺所有插件格式都能安全执行。

可见范围分别为"仅本人""定向分享插件实现""项目内提供""平台目录"；提升范围须由作者主动发起并经相应管理/安全/口径责任人要求的评估。作者可永久保持个人使用，不因使用次数、他人需求或代码能力不足而强迫上架；也可只分享计算结果而不分享插件代码。分享插件不转移源数据权限，接收人安装/运行时重新校验其身份、输入
ACL、宿主能力与配额。插件输出的个人结果不自动拥有权威地位；被引用的精确版本、授权能力和运行记录均可追溯。

## 9. 数据更新、增量计算与变更识别

支持 Append、Replace、Upsert、Insert Only、Update
Only、Merge、Snapshot、Partition
Replace。每项策略明确业务键、删除语义、幂等键、冲突规则和回退方式。通过业务键、批次、版本、更新时间或哈希识别
INSERT、UPDATE、DELETE、UNCHANGED；没有可靠删除证据时不得将"本批缺失"直接解释为删除。历史修订向受影响的下游分区或节点传播；无法安全增量计算时执行受控全量重算。

编辑阶段提供 Sample Preview、Dry Run 与 Full
Run；预览估算和实际结果分别标识。JobRun
记录输入版本、Pipeline/算子版本、输出版本、异常、耗时及资源用量；支持队列、并发配额、超时、取消、重试和中断恢复。共享
Linux 服务器上为交互查询和重计算划分预算，防止错误 JOIN 挤占其他业务。

复用中间结果、分区、物化、增量计算、查询下推、列裁剪和有权限边界的缓存；看板查询使用服务端聚合与分页，避免打开页面就实时重算多表。Dataset
正式版本保存输入与计算证据，并支持按发布策略回退；回退后的外部服务缓存和消费者版本也须同步校验。

幂等约束：源变更携带稳定记录
ID、事件/采集时间与源版本或水位；批次按文件哈希与业务键策略去重。历史修订只在依赖和分区可确定时局部重算；否则先提示预算并执行受控全量重算。

## 10. 数据质量、Quarantine 与修复闭环

### 10.1 质量规则

QualityRule 绑定到 Pipeline 的某个 Node 或
Dataset,类型包括：非空校验、范围校验、引用完整性（如部门编码是否在有效主数据中）、重复检测（配合第
10.2 节的哈希去重）。

质量检查结果分三级：**通过 / 告警（数据仍发布，但标记）/
阻断（数据不进入发布）**。阻断规则的清单需要业务方参与定义，不能由数据开发单方面决定"什么算错误数据"。

### 10.2 变更去重与幂等

沿用总框架 6.2 节：源变更携带记录
ID、事件时间、采集时间及源版本/水位；消费者按稳定事件 ID
幂等处理。批量导入按内容哈希去重（已确认的思路；是否判定为同一业务导入还须结合来源、期间、导入模式和映射版本，见能力契约 7.1）,防止同一份
Excel 被重复导入两次而重复计入。

### 10.3 隔离、修复与回流

区分完全重复与业务键冲突；冲突处理可配置保留、聚合、合并或隔离，不静默删除。异常数据进入
Quarantine，记录来源文件/工作表/行/字段、原值、规则、批次、修复人与修复状态；修复后重新验证并记录回流批次。规则可按数据资产版本管理。

阻断数据不可进入正式版本；告警可随版本保留诊断。修复提交生成新的作业与修订证据，保留原始值和旧版本。

## 11. 关系、血缘、影响分析与运行拓扑中心

三种视角共享稳定资产标识及有类型的关系定义，但运行状态是时序遥测，不能只存入静态
Node/Edge：

  -----------------------------------------------------------------------------------------------------------------------
  视角         回答的问题                                     主要数据
  ------------ ---------------------------------------------- -----------------------------------------------------------
  关系         哪些资源引用或消费该资源                       Dataset、Query、页面、组件、服务、Consumer 的声明依赖

  血缘         数据从哪来，经过什么转换，到哪里去             Source、批次、Pipeline/算子、字段映射、Dataset 版本

  运行拓扑     当前或某一时间段链路怎样运行，哪里故障或变慢   部署/运行实例、JobRun、调用、状态、时间序列指标与追踪链接
  -----------------------------------------------------------------------------------------------------------------------

统一关系目录至少区分节点/边类型、方向、版本、所属项目与权限；关系来源标注为静态声明、执行观测或人工登记，分别展示可信程度和更新时间。Dataset
→ API/Data Service → 已登记 Consumer 的依赖不得在 API
处截断。字段级血缘仅对可解析或显式声明的转换给出确定结论；动态
SQL、Python 或外部黑盒转换显示"未知/部分"，不能伪装成完整血缘。

关系和血缘视图支持上下游、N
层、字段级/资产级、只看报表或服务、隐藏中间节点、版本和异常过滤。影响分析在修改字段、Schema、Pipeline
或服务契约之前列出可能受影响的 Dataset、看板组件、Agent Tool、API
与登记的外部消费者；未登记的实际消费者需明确标注为观测不足。

### 11.1 运行拓扑的对象和链路

以可观察的数据流为主：Source/Connector → 同步或上传 JobRun → 原始
Dataset → Pipeline 节点/任务 → 输出 Dataset 版本 →
Query/可视化或数据服务 → Consumer。按需切换到服务部署层查看
Worker、数据库、缓存或 API
网关；业务资产和运行实例不能混成同一种节点。图中每条连接注明流向、协议/任务、最近成功时间或调用窗口。按项目、环境、时间范围、任务与
Dataset 版本过滤，历史回放必须以当时的拓扑快照和遥测为准。

### 11.2 状态、指标与诊断

-   节点状态：正常、运行中、延迟、告警、失败、暂停、未知；状态附采集时间、判断原因和新鲜度。失联或无遥测显示"未知"，不显示"正常"。
-   连接状态：最近成功/失败、吞吐或行数、传输延迟、错误率、重试、积压；按适用场景展示，不能把批处理任务伪装成持续流量。
-   JobRun
    可下钻输入批次、节点耗时、异常样本、队列等待、资源峰值及日志；服务可下钻调用量、P95/P99、超时、限流、消费者和响应版本；Dataset
    可看最新成功版本、更新时间与质量结果。
-   数据处理产生领域状态、事件与指标信号；平台运行告警由公共监控告警设施以 PlatformAlertRule／PlatformAlertInstance 管理，数据质量等业务异常保留数据处理自身语义并以 DomainAlertRef 供后台聚合，Notification 只负责投递；领域对象处于告警状态不等于存在活跃平台告警实例。图上从失败节点沿权威血缘标注受影响的下游，但"可能受影响"和"已实际失败"分开展示。支持从异常
    API 回溯到服务、输出 Dataset、计算 JobRun 与上游来源；从失败
    Connector 正向定位看板和外部调用方。
-   所有运行指标关联稳定资源 ID、环境、版本与 JobRun/请求追踪
    ID；收集与展示遵循权限、脱敏、保留期和采样预算。外部 Consumer
    只能按登记与本平台可观测的请求呈现，不能声称掌握其内部拓扑。

例如：企业集成平台 人员同步失败时，拓扑标出连接失败时间、未更新的人员
Dataset、使用旧版本完成的效率计算，以及受影响但仍可访问的看板/API。这样既避免把整条链一律标成失败，也让管理员知道数据是否过期。

### 11.3 与总框架的分工和实施边界

数据处理平台拥有 Dataset、字段映射、Pipeline
等数据血缘权威模型与推导语义；后台通过受控接口嵌入或跳转权威视图，仅维护跨资源治理依赖投影，不重新推导血缘。数据处理子方案定义业务资产、血缘和数据链路视图；平台公共监控提供日志、指标、追踪及平台运行告警；数据质量等业务异常保留数据处理领域语义，Notification 只负责投递；JobRun
与数据服务提供运行事件。运行拓扑消费这些信息，不另建一套任务状态或审计真相源。本稿确认能力和最低数据契约，具体采集栈、图数据库/关系库选择、刷新频率、告警阈值和图形库待需求与规模确认后确定。

流水线级血缘首期记录发布版本、Pipeline/规则版本及输入批次；字段级只在解析或显式声明可证实时给确定映射。运行遥测与静态依赖分开存储，通过资源
ID、版本、环境与 JobRun/追踪 ID 关联。

## 12. Dataset / Query / Data Service 服务层

### 12.1 契约内容

每个 Dataset
声明：字段名、类型、单位、精度、时区、空值语义、权限维度（哪些字段/行需要按角色或部门过滤）、新鲜度声明（实时/准实时/按发布批次）、来源
Pipeline 引用、版本号。

Query 是 Dataset
之上的参数化定义：允许的过滤参数（按 FieldRef 的可筛选声明见 12.6）、聚合方式、分页/降采样策略、单次返回的最大行数与体积上限。

这份契约是数据可视化控制台"展示端只依赖 Dataset / Query，不感知
PostgreSQL 或未来 OLAP
执行引擎"这句话得以成立的前提------本方案交付的正是这份契约的具体定义方式，而不只是一句原则。

### 12.2 查询执行

查询服务先做行列权限过滤和参数校验，再决定下推到哪个执行引擎（首期恒定是
PostgreSQL，Executor 注册表扩展后可按 Dataset
声明选择计划）。大结果集走分页、聚合或降采样，不整表拉到调用方。

### 12.3 精度与类型

数值字段固定使用 PostgreSQL numeric 类型；超出 JS 安全整数范围的 ID
或需要精确十进制的字段，API 输出采用字符串编码而非直接输出
number，避免前端 `Number()` 强转损失精度------这是总框架 6.6
节原则的具体落地方式。

### 12.4 发布与双向集成

Dataset 可按授权发布为版本化 Data
Service。服务定义暴露字段、参数、过滤、分页、行/字段权限、消费者身份、认证方式、限流、超时、缓存、调用审计、废弃窗口与兼容策略。外部系统主动调用平台与平台从
企业集成平台 等来源读取是两个方向；企业集成平台
也可按实际场景担当来源或消费者。精确协议和网关实现留待外部系统清单及其认证方式确认。

正式发布使用不可变 DatasetVersion
与原子版本指针，发布失败不得替换已有版本。服务缓存和外部调用方登记其可观测的消费版本；版本回退按发布策略校验缓存失效及消费者兼容。

### 12.5 业务语义契约与指标口径

语义契约位于受控 Dataset
与消费端之间，由数据处理模块维护计算和查询语义；可视化、API、报表与
Agent 通过稳定指标/维度 ID 使用，不各自复制口径。它不取代 Pipeline
的复杂转换，也不要求首期采购独立语义产品。`Metric`
记录业务域、责任人、名称/别名、适用范围、公式引用、统计粒度、单位、时间口径、允许的维度、可汇总性、权限、来源与版本；`Dimension`
登记切片键、层级、归属和生效规则；`ExclusionRule`
分别声明分子、分母或共同事实集需要剔除的记录、判断条件、依据、剔除发生在去重/关联/汇总之前还是之后，以及有效范围和版本。来源选择、去重键、部门归属和业务日期仍在
Dataset/Pipeline
契约中明确，避免把不同问题都塞进剔除规则。别名仅帮助检索，不能作为指标唯一身份。

多数指标可共用固定数学公式，同时引用不同的版本化剔除规则。例如"合格率＝合格数÷应检数"，某场景剔除取消的检查，另一场景还要剔除无效样本；分子与分母必须分别写清剔除条件，避免只改一个而无意改变比率。显示"质量域·合格率（抽检口径）"与"生产域·合格率（生产口径）"的稳定
ID、定义和责任人。同一公式不证明同一口径；相同名称也不自动合并。一个剔除规则修订时只影响显式引用它的指标，需显示受影响看板/API/Agent
查询和历史范围。

比率按汇总后的分子与分母重新计算，不默认平均行级或部门百分比；非可加指标、去重人数、快照存量及跨时间汇总要声明各自聚合语义。关联必须校验事实粒度、实体键、有效期、基数与多重路径，避免重复计算；查询不满足声明的维度或粒度时拒绝或提示明确的变换策略。零分母、缺失基表、未知归属与延迟数据的显示和阻断规则由指标定义确定，不能默认为
0。

个人用户可定义私有指标/剔除规则并对照权威版本；定向共享仍标为非权威。业务域负责人或获授权数据开发将公式与剔除规则共同校验、认证后发布权威
`MetricVersion`，绑定
Dataset/Query、来源批次和执行版本。若指标受外部/上级固定公式约束，登记依据和相应变更门禁；在尚未核实具体外部要求前不擅自指定审批流程。指标从人工/Excel
迁入平台时保留原口径和对账结果，不因上线自动改定义。

### 12.6 字段标识、可筛选声明与数据代次（拟定）

本节为数据可视化子方案 8.2（筛选器与字段绑定）、8.3（报表模板与数据绑定）与 16.2（生成式 HTML 报表）提供数据侧接口。对象与字段为拟定，待工程 Schema 确认；草案见 titanloom-contracts 的 field-ref、query-filterable、dataset-generation-changed。

**FieldRef（字段标识）**。FieldRef 是数据处理登记的稳定字段身份，ID 形如 `fld_department`，记录语言资源键、数据类型、单位、时间字段的粒度与业务时区、取值字典或选项 Query、是否为权限维度、所属业务域与责任人、版本与状态（draft / active / deprecated）。FieldRef 只回答"这是哪个业务字段"，不承载口径；口径、层级与生效规则仍由 12.5 的 Metric / Dimension 表达，Dimension 可引用 FieldRef。已被 Query 声明引用的 FieldRef 不可删除，只能标记 deprecated 并给出替代项。

**字段映射**。Dataset 字段经字段映射绑定到 FieldRef，一个字段至多绑定一个 FieldRef。不同 Dataset 中含义相同而列名不同的字段（同义列）由责任人显式绑定到同一 FieldRef；平台不按列名或别名自动归并（与 12.5"同名不自动等同"一致），只可提示候选。绑定要求数据类型兼容；时间字段粒度不同时登记换算关系。字段映射随 DatasetVersion 版本化，修改映射生成新版本，并按第 11 节展示受影响的 Query、看板与报表。字段映射同时是第 11 节字段级血缘的输入。

**可筛选声明（filterable）**。Query 契约按 FieldRef 声明可接受的筛选：FieldRef、对应参数槽位、允许的操作（等于、多值、区间、相对日期、文本搜索、层级）、Query 粒度（grain）、是否必填、多值上限，以及可选的选项来源（选项 Query 或字典）。基于 Dataset 语义层生成的 Query 由平台推导声明；手写 SQL 的 Query 须显式声明参数槽位及其在 SQL 中的绑定位置，平台不改写 SQL。一个 Query 只声明一次，被多少组件复用都不重复配置。执行规则：

-   只接受已声明 FieldRef 的筛选；未声明的筛选返回参数错误，不静默忽略。
-   区间一律左闭右开；相对日期（如本月、近 7 天）由服务端按 Dataset 声明的业务时区解析，调用方不自行拼接区间。
-   筛选值与行列权限同时生效，"全部"指当前主体权限范围内的全部；选项来源同样按权限过滤，高基数选项由服务端分页搜索。
-   筛选粒度与 Query 粒度不同时按登记的换算关系处理；无法换算时拒绝并说明原因。
-   筛选值规范化（多值排序、去重）后进入查询缓存键。

**数据代次（dataGeneration）**。每个 Dataset 维护单调递增的数据代次，消费者可见数据变化时加一：原子发布新 DatasetVersion、版本回退（指针回到旧版本时代次仍递增，不复用旧值）、准实时 Dataset 的增量批次提交、更正批次发布。权限变化不改变代次，由授权失效机制处理；被质量规则阻断而未发布的批次不改变代次。代次变化与版本指针切换在同一事务内写入 outbox 事件 `data.dataset.generation_changed`，载荷含 datasetId、新代次、datasetVersion、变化类型（publish / rollback / incremental / correction）、dataAsOf、来源水位摘要与质量结论，不含数据行。事件按至少一次投递，消费者按代次去重并丢弃旧代次。Query 响应返回所读数据的 dataGeneration，供调用方判断结果是否已过期；snapshot 模式返回快照固定时的代次。

代次事件是数据变化的通知，不是数据本身：可视化收到后仍经 Query 重新获取（可视化 8.3），生成式报表据此决定是否生成新实例（可视化 16.2）。报表生成完成事件属于数据可视化领域，由其发布，不由本模块发布。

## 13. 错误定位、失败隔离与草稿恢复

导入、处理、分析和发布的失败均不得只显示"执行失败"。错误本身、用户正在编辑的配置、已上传的原始文件、已成功发布的数据版本分别保存和管理；任一作业失败不应触发页面整体崩溃、未保存草稿丢失或现有正式数据被半成品覆盖。

### 13.2 失败隔离与可继续操作

-   上传先生成可追踪批次和文件引用；质量与计算在作业中执行。导入失败保留原始上传和诊断结果供重试或修补，临时结果不能冒充已发布
    Dataset。
-   预览与编辑的错误局限于当前组件或任务；页面侧栏、编辑器、保存草稿、查看错误和撤销操作保持可用。异常组件提供重试、打开诊断和返回最近正常状态的入口。
-   导入、变换、增量写入采取可恢复的暂存与提交边界；只有完整通过必要校验才切换正式版本指针。失败保留上一个成功版本和可用的看板/API，并明确提示数据新鲜度；禁止部分成功被误报为成功。
-   修补原始表、映射规则或异常行时产生新的修订/作业记录，保留原始证据；重跑只处理可确定的受影响范围，无法确定时提示全量重跑成本。重复提交按批次与幂等规则处理，防止越修越重复。
-   前端使用组件级错误隔离、请求取消和有界预览；耗时任务后台运行，刷新或关闭页面后可回到任务中心接续查看。诊断弹窗和编辑器不等待整张大表加载完毕才能操作。

### 13.3 草稿保存与恢复

Pipeline、导入映射、质量规则、SQL/Python、数据处理侧的数据绑定/Query
定义和修补内容均采用带版本的服务端草稿：编辑时定期自动保存，手动保存有明确成功/失败反馈，离线或短时断网时先保留浏览器本地恢复副本并在重连后同步。界面必须区分"已保存到服务端""仅在本地待同步""保存失败"；离开页面或刷新之前提示尚未持久化的改动，并提供恢复入口。服务端草稿与正式发布版本分离，自动保存不得隐式发布或覆盖他人的编辑。
可视化 Page / Release
的页面草稿仍归可视化领域，本方案不取得页面定义所有权。

草稿恢复需处理并发编辑冲突，保留最近可恢复修订与时间戳；在提交或发布失败后仍可继续编辑同一草稿。浏览器崩溃、作业失败、页面组件抛错、刷新和断网重连都不能使最后一次**已确认保存**的修改消失；未成功同步的本地改动明确告知其恢复范围，不承诺设备损坏或清除浏览器数据后仍能恢复。敏感数据的本地副本受权限、加密/有效期和企业终端策略约束，且不得将原始大表整体塞入浏览器存储。

### 13.4 诊断与修复闭环

用户从错误摘要进入对应文件行列、异常记录或 DAG
节点，修补后执行局部预览/校验，查看修复前后差异，再提交新的作业和
Dataset

JobRun 和资产；血缘与影响分析指出下游影响，二者引用同一个诊断
ID，避免出现几套互相矛盾的故障记录。

## 14. 文件、Asset、Snapshot 与版本管理

原文件走统一 Asset
API,数据处理平台只保留引用,不重复存储二进制。批量导入用 COPY
写入暂存表,校验通过后合并进原始层。

Parquet 用作有明确资源
ID、权限、容量和有效期的检查点/交换文件，不作为查询旁路。**具体保留天数、容量上限需要业务方给出合规要求【待确认，见第
0 章】**，本文档定义机制（谁能生成、谁能读、什么时候清理），不预设数值。

Snapshot 机制：正式汇报或需要"回放某个时间点数据"的场景，生成绑定
snapshotId
的固定快照，与实时查询结果分开管理,避免"汇报用的数字后来又变了"的争议。

DatasetVersion、Snapshot
与草稿各自保存不同生命周期与权限；正式版本和快照可回退并可审计，草稿自动保存不能触发发布。Asset
的二进制与原始批次建立稳定引用，避免多处复制。

## 15. JobRun、运行状态与公共执行协议

数据处理平台的执行面（Polars
Worker、未来引擎）本身就是重计算任务，天然是 JobRun
协议最重的使用方。本方案约定：

-   PipelineRun 拥有 DAG
    节点依赖、分支、质量门禁、输出提交和整体领域结果；JobRun／JobAttempt（界面可简称
    Attempt）拥有排队、租约、执行尝试、执行重试、超时和取消。二者通过稳定引用和明确状态映射协作，不合并为一套状态机；JobRun
    完成不代表质量通过或正式发布成功，JobRun 失败/取消也不能未经
    Pipeline 领域判断直接改写 PipelineRun 终态；
-   数据处理拥有 DAG 编排语义、Operator
    契约、质量/发布语义及领域检查点；公共 Job / Executor 设施负责本地
    Runner
    或队列适配、持久执行、执行尝试和资源准入；工具与自动化中心拥有 Tool
    / ToolVersion、AutomationPlan / AutomationRun 等自身领域对象。Tool
    可作为某个 Operator 的受控实现引用，但不会因此取得 Pipeline /
    PipelineRun 所有权；数据处理也不依赖整个工具自动化平台安装才能运行；
-   JobRun 协议本身由能力契约 8.2–8.3 定义，本文不单方面定义；PipelineRun 的领域状态由本文 15.1 定义。

运行记录包含输入批次与版本、Pipeline/算子版本、输出版本、队列等待、节点耗时、错误诊断
ID、重试及资源用量；支持超时、取消、恢复、额度和状态回放。PipelineRun
映射一个或多个 JobRun，关联通过 domainRunRef 与 jobId 双向引用；拓扑消费同一事件，不产生第二套状态真相。

### 15.1 PipelineRun 领域状态（拟定，待工程 Schema 认证）

此前本文把"领域状态映射"交给能力契约 8.3 冻结，而 8.3 只定义 JobRun，两边互相等待，没有任何文档定义 PipelineRun 的状态。现按"不用单一 status 承载多个维度"的原则拟定如下，供 M3 实现与验收使用。

| 维度 | 取值 | 含义 |
| --- | --- | --- |
| `runKind` | `sample_preview` / `dry_run` / `full_run` | 运行类别；预览与 Dry Run 不发布 Dataset |
| `runState` | `accepted` / `running` / `reconciling` / `succeeded` / `failed` / `canceled` / `timed_out` | 编排与计算是否完成，不含发布结论 |
| `qualityResult` | `not_evaluated` / `passed` / `warned` / `blocked` | 质量门禁结论，对应"通过 / 告警 / 阻断"（10.1） |
| `publishResult` | `not_applicable` / `not_published` / `published` / `rolled_back` / `unknown` | Dataset 发布结论 |

不变量：

1. `qualityResult = blocked` 时 `publishResult` 不得为 `published`（阻断数据不进入正式版本，10.3）。
2. `publishResult = published` 要求 `runState = succeeded` 且 `qualityResult` 为 `passed` 或 `warned`，并指向输出 Dataset 版本。
3. `runKind` 为 `sample_preview` 或 `dry_run` 时 `publishResult` 必须为 `not_applicable`。
4. 任一关联 JobRun 的 `effectStatus = unknown` 时，`runState` 必须为 `reconciling`，`publishResult` 为 `unknown` 或 `not_published`，不得标为成功。
5. JobRun 成功不改变上述任一维度；JobRun 失败或取消也不直接改写 PipelineRun 终态，由数据处理按领域规则判定（ADR-012）。
6. 终态 PipelineRun 不复活；重新运行创建新的 PipelineRun 并记录来源。

对应的 JSON Schema 草案见 titanloom-contracts/pipeline-run.schema.json。

与 Query 响应的关系：已发布的 Dataset 版本其质量状态只可能是 `passed` 或 `warned`（`blocked` 的数据不会发布，10.3），因此 Query 响应的 `qualityStatus` 只取这两个值，见 titanloom-contracts/query-execute-response.schema.json。

## 17. 性能、资源预算与分析引擎扩展

按总框架 12.2

## 18. 验收标准与验收场景

-   工时链最小闭环：一次批量导入 → 去重 → 标准化 → 与考勤结果关联 → 发布
    Dataset → 可视化查询到正确数值,全链路可追溯到具体批次和 Pipeline
    版本;
-   基表闭环：业务维护/导入 → 校验并发布固定版本 → 按键和业务日期关联 →
    展示异常及影响 → Dataset 发布/重算；可追溯所用基表与映射规则版本。
-   重复/乱序变更不导致重复计数,补卡/历史修订后受影响指标正确更新;
-   文件导入失败时明确报告错误行,不将未通过校验的数据当正式结果发布;
-   查询服务在声明的行数/体积上限内正确分页,超限请求被拒绝而非拖垮服务;
-   停用某个 Executor（如 Polars Worker 不可用）时,不依赖它的 Pipeline
    和已发布 Dataset 仍可用;
-   具体性能门槛（P95/P99
    查询延迟、数据新鲜度、并发上限）在联调前登记,以实测结果为准,不用"实时""很快"代替指标。

### 18.1 场景验收

1.  工时 Excel
    补传历史月份后，系统识别更新、质量异常与受影响分区，生成新 Dataset
    版本；查询与看板按版本与权限获得正确结果。
2.  安全稽查外来 Excel
    接入后完成画像、图片/问题记录关联、质量隔离与看板使用，不依赖预先存在的内部基表。
3.  修改效率字段前，影响分析指出 Pipeline、看板组件、API
    和已登记消费者；未知字段血缘明确显示未知。
4.  模拟 企业集成平台 同步失败或效率 DAG
    延迟，运行拓扑显示最后成功时间、故障点、积压、可能受影响消费者及下钻的
    JobRun/调用证据；遥测断开时显示未知。
5.  模拟 API
    超时，通过服务拓扑定位到调用、输出版本、查询或上游作业；历史时间窗口能回看当时状态。
6.  在 Excel
    指定工作表的某行某列放入错误日期、空业务键和重复键；错误清单定位原始单元格、规则及样本，修正后复检，原始文件与旧版本仍可追溯。
7.  在 DAG JOIN、SQL/Python
    算子和单个看板组件分别注入失败；错误能定位到节点或代码位置及已知的最小数据范围，页面其他组件、编辑器、保存和修补入口保持可用；上次发布版本继续可用。
8.  编辑导入映射和 Pipeline
    时，分别模拟任务失败、页面刷新、浏览器崩溃、短时断网及服务端保存失败；已确认保存的草稿能够恢复，未同步改动有清楚提示，并发修改出现冲突提示，不静默清零或覆盖。
9.  导入进行到一半后中断或重复重试；正式 Dataset
    无半成品，新作业可续查或重跑，不产生重复数据，诊断记录可关联批次与
    JobRun。
10. 业务用户更正 9 月中旬生效的岗位分类：同一工号 9
    月上旬仍取旧分类，后续取新分类；发布前阻断重叠有效期和重复映射。明确选择历史回补后才生成新结果版本，旧发布版本和当时所用基表可复现。
11. 以受控 PostgreSQL
    表及批量导入基表分别关联同一来源批次，比较结果与未匹配报告；跨库连接超时或超预算时展示失败原因，先前发布版本继续可查。
12. 导入 `工号、姓名、1月、2月…`
    的岗位/部门宽表，显式绑定年份并生成可按事件日期检索的规范视图；核验跨年、空单元格、重复工号及同月换岗例外记录。业务仍能按原表形编辑；变换结果可回溯至原工作表/单元格。
13. 按部门假日表把日期 D 展开为 D 08:30 至次日
    08:30；计算跨日/跨月工时与多个重叠节假日区间的去重交集，给出扣除明细。跨夏令时场景以业务确认的时区和计量规则验收。
14. 业务用户使用授权 SQL 或隔离 Python
    实现现有算子未覆盖的复杂计算，声明契约后完成预览、定量配额检查、版本发布和跨流水线复用；更换实现版本不静默修改旧结果，异常代码不能影响其他作业及既有发布版本。
15. 普通用户在授权范围复制一条正式工时规则，私下修正并以同一输入版本重算；输出差异明细和非权威标识。定向分享给可读对应数据的同事后，两者只见其获准字段/行；未获授权者被拒绝，正式指标保持原版本。撤销授权后不再能查询共享结果。
16. 用户上传受支持格式的个人计算插件，自动校验、隔离测试后仅本人启用；其他用户和目录不可见。插件请求未批准的网络/凭据或超过配额时被拒绝/终止。作者只分享结果、保持插件代码私人；后续选择推广时才走相应范围的评估流程。
17. 两个部门沿用相同的"合格数÷应检数"公式，但分别剔除不同的异常记录；查询展示不同的指标
    ID、域、公式及剔除规则版本。修改一方的剔除规则，仅其指标新版本变化；逐项展示剔除数量与原因，旧结果可复算。
18. 对合格率先按各自规则剔除，再按部门汇总分子分母并计算总体比率；把两个部门百分比直接取平均的查询被拒绝或提示口径错误。新增维度导致事实行数膨胀时阻断错误聚合；个人复制权威口径并改剔除规则后，结果继续标为非权威。

上述场景须同时验证未授权访问、版本回退、失败隔离、草稿恢复、可观测性和资源配额。定量阈值按第
0 章登记后才能宣称达标。

### 19.1 插件化验收补充

首期验证解析实现替换不修改 DAG
核心、跨空间凭据隔离、实现版本固定和启动失败资源清理；停止 Polars
不影响无依赖的已发布查询。验证 JobRun 成功但质量失败时 PipelineRun
不得标记正式发布成功；旧检查点与新实现不兼容时拒绝恢复。开放第三方实现前完成对应宿主的权限、预算和兼容验收。

个人插件试运行同样属于开放实现：在开放其宿主前先完成隔离、能力与资源验收；不把平台目录上架审核作为个人插件运行的前置条件。
