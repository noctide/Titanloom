# Titanloom · 集成与消息通道子方案

> 版本：V0.1｜日期：2026-10-02｜状态：**草案，待确认后纳入现行基线**；未实现、未验收。
> 修订（2026-10-03）：3.1 来源补充"领域事件经 Notification 形成通知类别后才可路由"，首例为可视化报表生成完成。
> 定位：公共平台能力，不是业务能力域。统一管理 Titanloom 向外部推送消息（出站）与接收外部推送（入站）的通道、路径、路由和可视化配置。
> 上位约束：《Titanloom-总框架设计方案-V1.0》《Titanloom-平台能力契约与Agent接入规范-V1.0》《Titanloom-插件与扩展体系子方案-V1.0》《Titanloom-后台治理中心子方案-V1.0》及 ADR-009、011、012、013、014、018。
> 事实边界：本文不假定任何第三方平台（企业 IM、机器人、告警平台）的接口格式、签名方式或限频规则；这些在接入具体平台时逐个核验。示例字段是拟定契约，不表示已有服务。

## 1. 需求与定位

需求：消息可以推送到外部系统，外部消息也可以推送进来；两个方向的路径可配置，并有统一的可视化配置入口，例如 Webhook、机器人接口。

现行方案只有零散描述：后台治理 11.3 写明"通知渠道、模板、收件范围和限频由公共设施管理"，工具自动化把"外部 Webhook"推迟到阶段四，插件体系有"Notification Adapter""Connector"类型，总框架 8.2 有"Interaction Adapter"边界。没有一份文档回答渠道对象归谁、入站如何鉴权、如何避免 SSRF 与环路、配置如何版本化、如何可视化。本文补上这一层，不新增业务领域，不改变任何对象 Owner。

## 2. 边界

### 2.1 本方案拥有

| 对象 | 含义 |
| --- | --- |
| ChannelConnection | 一个出站目标的连接配置：类型、目标引用、认证方式、限频与超时；敏感值只存 SecretRef |
| ChannelPreset | 声明式预设：消息体模板骨架、签名方案、限频建议；首期只有内置"通用 Webhook" |
| MessageTemplateVersion | 不可变的消息模板版本，支持中英文显示键与变量 |
| DeliveryRoute | 出站路由规则：哪些来源（通知类别、告警、自动化动作）在什么条件下发往哪些 ChannelConnection |
| DeliveryRecord / DeliveryAttempt | 一次投递意图及其尝试；记录结果、重试、最终状态 |
| InboundEndpoint | 一个入站入口：路径标识、鉴权方式、Schema、限流 |
| InboundRoute | 入站路由：接收后交给谁（自动化触发、能力调用、对话），以及字段映射 |
| InboundReceipt | 一次入站接收事实，用于去重与审计 |
| ExternalIdentityRef | 外部发送者引用，只作为线索，绑定到 Person 须经平台主数据服务的核对流程 |

### 2.2 本方案不拥有

- Notification 的业务含义（投递 / read 生命周期仍归公共通知）；本方案是它的**渠道扩展**，不新增第二套通知状态。
- TriggerBinding / TriggerOccurrence / AutomationRun（归工具自动化）；入站只负责把受控事实交给它们。
- 任何领域业务对象与状态机；入站消息不能直接写领域表。
- 凭据明文；SecretRef 与轮换归后台治理 10.3 的凭据设施。
- AgentTask（归智能管家）；对话类入站只是把用户意图交给它。
- Person / SourceIdentity（归平台主数据服务）。

### 2.3 与既有概念的关系

```
DomainEvent / PlatformAlert / AutomationAction("发送消息")
        │  （已发生的事实，或受控动作）
        ▼
 公共 Notification ──DeliveryRoute──▶ ChannelConnection ──▶ 外部系统        （出站）

外部系统 ──▶ InboundEndpoint ──鉴权/去重/Schema──▶ InboundRoute
                                                      ├─▶ 工具自动化 TriggerOccurrence   （事件接入）
                                                      ├─▶ Capability / Command（经身份绑定与委托）（命令）
                                                      └─▶ 智能管家（对话）                 （对话）
```

出站与入站都不是业务写入口（ADR-011）：Notification 与 Audit 不是写入口，入站消息同样不是。入站要产生业务副作用，必须走目标领域的 Capability / Command 并重新鉴权。

## 3. 出站设计

### 3.1 通道与路由

- **通道类型**：首期内置通用 Webhook（可配置方法、头、认证、消息体模板）。多数机器人接口可以先用它表达，但各平台的签名、限频、消息格式是否适用必须逐个核验；确需专用逻辑时以 ChannelPreset 形式经插件体系的 Contribution 登记，不开放任意脚本。邮件、短信等其他类型按真实需求另行认证。
- **路由**：DeliveryRoute 以"来源类别 × 严重程度 × 范围（空间 / 项目 / 领域）→ 通道集合"表达，支持聚合窗口、去重键与限频。路由是版本化配置，发布与激活分离（复用后台治理 7.2 的 ConfigRevision / Activation）。
- **来源**：公共 Notification、平台告警（PlatformAlertInstance，ADR-009）、领域告警的受控摘要（DomainAlertRef）、自动化中的"发送消息"动作。领域事件经 Notification 形成通知类别后才可被路由，例如可视化报表生成完成（`visualization.report.generated`，可视化 16.2），消息只含摘要与受控链接。后者必须经 Capability 授权，接收人与内容是受控参数（工具自动化 16 节）。

### 3.2 内容与数据出口

外部通道是数据出口，等同模型交付之外的另一类出口，须有独立策略：

1. 每个 ChannelConnection 声明 `maxDataClass`（可发送的最高数据级别）；路由发布时检查模板变量的来源级别不超过通道上限。
2. 消息默认只含必要摘要与受控详情链接，不含原始凭据、业务明细、长效附件链接（后台治理 11.3）；点击链接后仍需登录并重新鉴权。
3. 附件字节不随消息推送；只发引用或受控链接。
4. 模板是无副作用的变量替换，不含可执行表达式；变量集合由来源声明，未声明的字段不可引用。
5. 测试发送只允许发往操作者获准的测试接收范围。

### 3.3 可靠性语义

- 业务事务内写 outbox，投递由持久任务（JobRun）领取执行；不假定恰好一次，只承诺至少一次加幂等标识（`deliveryId` 随请求发送，供接收方去重，是否被接收方使用不由平台保证）。
- 重试有上限、退避和最长等待；超限进入失败终态，保留原因，可由有权限者手动重投（新的 DeliveryAttempt，不改写原记录）。
- 同一通道有熔断与限频；下游持续失败时暂停投递并告警，不无限积压。队列有界，超出时按路由策略丢弃低级别、合并或拒绝，并记录。
- 投递失败不影响业务提交；投递状态不改写领域状态（Notification delivered ≠ 业务已处理）。
- 不保证跨消息顺序；需要顺序的场景由接收方用事件时间或序号处理。

### 3.4 出网守卫（SSRF 与资源保护）

所有出站 HTTP 经统一出网守卫：

- 目标须在批准清单内（主机名或网段），与连接配置一起版本化；
- 解析后的地址逐次校验，拒绝回环、链路本地、私有网段（除非该目标被显式批准为内网目标）与云元数据地址；重定向默认不跟随，跟随时每一跳重新校验；
- 固定短超时、响应体大小上限、并发上限；
- 证书校验默认开启，关闭须显式批准并审计；
- 连接测试用同一守卫，不能借测试访问任意地址（后台治理 10.3）。

## 4. 入站设计

### 4.1 三种入站用途（按风险递增）

| 用途 | 作用 | 风险与要求 | 里程碑 |
| --- | --- | --- | --- |
| 事件接入 | 外部事件变为工具自动化的 TriggerOccurrence | 外部内容是不可信输入；不产生业务写入，后续动作按自动化计划与委托执行 | M5 |
| 命令 | 外部消息映射为某 Capability / Command | 必须能把发送者可信地绑定到 Principal 并取得有效委托，否则不开放正式写入（能力契约 10.4）；高影响动作仍需人工确认 | M6 之后，条件阶段 |
| 对话 | 机器人聊天变成 AgentTask 的输入 | 发送者身份绑定同上；Agent 权限为调用者权限 ∩ 委托 ∩ 三道门 | 随智能管家，M5 第二步之后 |

首期只做"事件接入"。后两者在有真实需求、身份绑定机制和审计就绪后再开。

### 4.2 接收流程

```
请求 → 限流/大小检查 → 路径解析 InboundEndpoint → 鉴权（签名/共享密钥）
     → 时间窗与重放检查 → Schema 校验 → 去重（deliveryId / 业务幂等键）
     → 持久化 InboundReceipt（含事务内 outbox）→ 返回确认
     → 异步：按 InboundRoute 映射并交给目标（TriggerOccurrence 等）
```

- **先持久化再确认**：确认响应表示"已接收"，不表示"已处理成功"。
- **鉴权**：每个端点有独立的密钥或签名凭据（SecretRef）；密钥只在创建或轮换时显示一次；支持新旧密钥重叠窗口。URL 中的不可猜测路径标识只是定位手段，不是鉴权。
- **防重放**：校验时间戳窗口并记录已见 deliveryId；窗口与保留期可配置。
- **限流与大小**：按端点与来源限流，请求体大小上限，超限直接拒绝并计数。
- **Schema 与映射**：端点登记 JSON Schema 或字段映射；映射使用声明式路径选择，不执行脚本。原始载荷按保留策略存放，敏感字段可脱敏。
- **公网可达性**：外部系统要能访问入站端点，要求部署对其可达。内网部署无法被公网服务回调时，需要网关或中继，属部署决策（待决 D-15），本文不预设方案。
- **环路保护**：出站消息携带来源标记；入站事件若来自本平台出站则标记并按策略丢弃或限制跳数，避免"出站→外部系统→入站→再出站"循环（沿用工具自动化 13 节的循环保护）。

### 4.3 身份

外部发送者标识（IM 用户 ID、机器人 ID）不是 Person 主键。绑定关系经平台主数据服务的 SourceIdentity 核对流程建立，不按姓名或昵称自动合并。未绑定的发送者只能触发"事件接入"类用途，不能触发命令或对话。

## 5. 统一可视化配置

入口位于后台治理的"集成中心"（页面由后台治理承载，对象由本方案拥有；后台只提供受控入口与生效跟踪，不复制对象定义，沿用 ADR-008）。

| 页面 | 内容 |
| --- | --- |
| 通道列表 | 类型、状态、最近成功与失败、限频、最高数据级别、关联路由数 |
| 新建通道向导 | 选类型或预设 → 填目标（URL 与令牌作为 SecretRef，不回显）→ 认证 → 测试发送（仅测试接收范围）→ 保存草稿 |
| 路由编辑 | 来源类别、严重程度、范围、通道、聚合与限频、模板选择；展示"命中预览"：给定样例事件会发往哪些通道、渲染后的内容 |
| 模板编辑 | 变量清单与来源级别、中英文预览、长度上限检查 |
| 入站端点 | 创建端点 → 显示路径与一次性密钥 → 登记 Schema 或样例 → 字段映射 → "试收"（用样例载荷干跑，不触发真实动作）→ 绑定目标 → 启用 |
| 投递与接收记录 | 按通道或端点查看尝试、失败原因、重投入口；接收的去重与拒绝原因 |
| 健康与告警 | 通道熔断、连续失败、限频命中、密钥即将过期 |

配置变更统一走草稿 → 校验 → 不可变版本 → 激活，激活失败不标记完成；删除前检查被路由和自动化引用。多数 Webhook 地址本身含令牌，**一律按密钥处理**，不得出现在日志、命令摘要、导出或页面回显中。

## 6. 能力与权限

拟登记的能力（最终 ID 在工程契约阶段与公共目录对齐）：

| capabilityId | 说明 | operationKind / impactLevel | Agent 默认策略 |
| --- | --- | --- | --- |
| titanloom.integration.channel.read | 读取通道元数据（不含密钥） | read / low | 可读 |
| titanloom.integration.channel.draft_save | 保存通道草稿 | draft_write / medium | draft_only |
| titanloom.integration.channel.test | 测试发送 | control / medium | confirm |
| titanloom.integration.channel.publish | 发布与激活通道 | business_write / high | confirm |
| titanloom.integration.route.draft_save / publish | 路由草稿与发布 | draft_write 与 business_write / medium 与 high | draft_only 与 confirm |
| titanloom.integration.inbound.endpoint.create | 创建入站端点并生成密钥 | business_write / high | deny |
| titanloom.integration.inbound.endpoint.rotate_secret | 轮换端点密钥 | control / high | deny |
| titanloom.integration.inbound.route.publish | 发布入站路由 | business_write / high | confirm |
| titanloom.integration.delivery.read | 查看投递与接收记录 | read / medium | 可读（按范围） |
| titanloom.integration.delivery.retry | 手动重投 | control / medium | confirm |

Agent 永远不读取密钥明文；密钥只在服务端与执行宿主解析。安装插件、注册预设、通道可用都不等于已授权任何 Capability（ADR-013）。

## 7. 资源预算

- 投递与入站处理使用现有 JobRun 与有界本地 Runner，不引入新的消息中间件；是否需要队列服务由部署档位与实测决定。
- 需登记的参数：每通道并发与限频、重试次数与总等待、队列上限、请求与响应体上限、入站端点限流、重放窗口、DeliveryRecord / InboundReceipt / 原始载荷的保留期与容量、聚合窗口。数值上线前确定并实测，不在设计稿中猜定。
- 在 2 核 2G 主机上，通道数与并发应从小值起步（建议初值：全局投递并发 2，单通道并发 1，仅为待校准的提案），超过预算时排队、合并或拒绝并留痕。

## 8. 版本、发布与恢复

- ChannelConnection、DeliveryRoute、InboundEndpoint、InboundRoute 的定义均有草稿与不可变版本，激活指针分离。
- 三个维度分开表达，不用单一 state：**修订状态**（draft / validated / published / superseded / withdrawn，后台治理 7.2，published 后不可变）、**激活**（pending / applying / effective / partial / failed，逐目标记录已应用版本）、**运行开关**（enabled / paused / disabled）。紧急停用与暂停是运行开关，可立即生效，不依赖新修订发布；收紧类变更不因某节点未确认而回退为旧的宽松配置（后台治理 7.3）。
- 恢复后不重放历史出站投递：备份恢复环境默认停用所有出站通道与入站端点，复查撤权与密钥后才逐个启用（沿用部署文档的"恢复环境默认不触发外部副作用"）。
- 删除或停用通道不删除历史 DeliveryRecord；仍被路由引用的通道禁止删除。
- 紧急停用优先：可一键暂停全部出站或某个入站端点，立即生效并审计。

## 9. 验收场景

| 编号 | 场景 | 通过条件 |
| --- | --- | --- |
| IC01 | 创建通道并测试发送 | URL 与令牌不在任何响应、日志、审计摘要中出现；测试只发往测试接收范围 |
| IC02 | 目标解析到私网或元数据地址 | 被出网守卫拒绝并记录；重定向到未批准地址同样被拒 |
| IC03 | 通道下游持续失败 | 重试有上限，进入失败终态；熔断后暂停并告警；业务提交不受影响 |
| IC04 | 同一事件重复触发路由 | 去重键生效，只产生一次投递意图；`deliveryId` 稳定 |
| IC05 | 模板引用越级变量 | 路由发布被拒绝（超过通道 `maxDataClass`） |
| IC06 | 通知已读 | 不改变 DeliveryRecord 与告警、领域状态（Notification read ≠ 已处理） |
| IC07 | 入站签名错误或时间戳过期 | 拒绝，不创建 InboundReceipt，不触发目标，计数可见 |
| IC08 | 入站重复投递同一 deliveryId | 返回既有接收结果，不产生第二个 TriggerOccurrence |
| IC09 | 先确认后失败 | 接收已持久化；目标处理失败不丢失接收，可见失败原因并可重放（重放仍按当前授权） |
| IC10 | 入站载荷超限或洪泛 | 按端点限流拒绝，不影响其他端点与业务 |
| IC11 | 出站再入站的环路 | 来源标记生效，按策略丢弃或限制跳数 |
| IC12 | 未绑定身份的外部发送者尝试命令 | 被拒绝；仅"事件接入"可用 |
| IC13 | 轮换端点密钥 | 重叠窗口内新旧均可用，窗口后旧密钥失效；密钥只显示一次 |
| IC14 | 配置激活失败 | 保持原版本，状态可解释；不显示已生效 |
| IC15 | 恢复演练 | 恢复环境所有出站与入站默认停用，不重放历史投递 |
| IC16 | Agent 尝试读密钥或自建端点 | 被拒绝（端点创建 deny、密钥不可读）；经确认的发布才可执行 |
| IC17 | 紧急停用 | 全部出站暂停或指定端点停止接收，立即生效且留审计 |
| IC18 | 2C2G 主机混合负载 | 投递与接收处理不挤占签到与填报的交互预算，数值按实测登记 |

## 10. 实施顺序

阶段编号以《Titanloom-实施路线与首期工程基线》的 M 序列为准。

- **M4**：SecretRef 最小集与出网守卫（后台治理 10.3，随 M4 的后台治理 P3 一同交付）、ChannelConnection、通用 Webhook、DeliveryRoute 与模板、DeliveryRecord、集成中心的通道与路由页面；首批来源为平台告警与 Notification。
- **M5**：InboundEndpoint 与"事件接入"，对接工具自动化 TriggerBinding；入站记录页面；密钥轮换。
- **条件阶段**：命令与对话类入站；专用机器人预设；邮件、短信等通道；需要网关或中继时的方案（D-15）。
