# Titanloom · 工程质量与代码规范

> 版本：V1.0｜日期：2026-10-03｜状态：公共平台规范，随 M0 生效；工具选型为候选，M0 选定后登记；文中数值为提案，M0 实测后校准。
> 定位：设计文档规定"系统应当怎样"，本文规定"代码怎样证明它做到了"。本文不改变任何领域边界、对象 Owner 或公共契约；与总框架、能力契约冲突时以它们为准，并先修订本文。
> 依据：总框架 12.3（技术栈）、12.4（执行约束）、12.5（工程验证门禁）、13（一致性、版本与恢复）；能力契约 3、7、8、12、16；后台治理 5.3；插件体系；实施路线 5.1、5.3；开源与第三方依赖治理。

## 1. 原则

1.  **门禁先于评审。** 项目由个人开发，不能依赖他人评审兜底。凡能自动检查的规则都进 CI，CI 不通过不得合并；人工评审只处理自动检查无法判断的问题。
2.  **设计是代码的上位约束。** 代码不得静默偏离设计。实现中发现设计不可行或有更好做法时，先改设计（必要时写 ADR），再改代码，二者在同一合并请求中说明。
3.  **契约是唯一来源。** 接口、事件、错误码、状态机只在契约中定义一次，代码与 SDK 由契约生成或对契约测试，不手写第二份。
4.  **边界由工具强制。** 模块边界、数据所有权与隔离门禁不靠约定，靠导入检查、数据库权限和测试强制。
5.  **质量不随里程碑降级。** MVP 不是降低门禁的理由；暂不实现的功能可以缺席，但已实现的部分必须满足本文。

## 2. 仓库与模块边界

### 2.1 仓库布局

单仓（实施路线 5.3 任务 2）：

| 路径 | 内容 |
| --- | --- |
| `apps/api` | FastAPI 模块化单体；每个领域与公共服务是一个独立 Python 包 |
| `apps/web` | 门户与各领域前端（React + TypeScript + Vite）；Studio / Director / Player 独立构建入口 |
| `packages/contracts` | JSON Schema、OpenAPI、状态机、错误码注册表及契约测试（由现有 titanloom-contracts 迁入） |
| `packages/sdk-*` | 由契约生成的 Python / TypeScript SDK，不手工修改生成部分 |
| `ops` | 部署、合成数据生成器、基准与恢复脚本 |
| `docs` | 设计文档；与代码同仓、同一合并请求更新 |

### 2.2 服务端模块边界

-   每个领域（填报、考勤、工具自动化、数据处理、知识、可视化、智能管家）与公共服务（身份、授权、命令、Job、资产、审计、通知、主数据、集成通道等）各为一个包，包内分为对外接口层与内部实现层。
-   其他模块只能导入目标模块的对外接口层，或经 Capability / Command 调用；禁止导入内部实现、禁止跨模块共享 ORM 模型。该规则用导入检查工具（候选：import-linter）在 CI 强制，新增模块必须同时登记其导入契约。
-   每个模块拥有自己的数据库 schema 与数据库角色（后台治理 5.3）。迁移脚本为每个模块角色只授予本 schema 的写权限；集成测试以模块角色连接数据库，跨模块写入在数据库层被拒绝。
-   读取其他领域的数据只经其 Capability、受控 Dataset / Query 或已发布事件，不直接查对方表（总框架 5、能力契约 2.1）。
-   插件与内核遵守总框架 8.6.2：消费者依赖版本化服务接口，禁止导入其他插件私有代码或写其表。

### 2.3 前端模块边界

-   `apps/web` 按领域划分功能目录；领域之间只经公共 Shell 接口、路由与契约生成的 SDK 交互，不互相导入内部组件。边界用依赖检查工具（候选：dependency-cruiser 或 ESLint 边界规则）在 CI 强制。
-   页面数据一律经 TanStack Query 或 Data SDK / Query Manager 获取（总框架 12.3），组件内不直接调用 `fetch`；不在浏览器端对全量数据做筛选（可视化 8.2）。
-   Monaco、ECharts、Three.js、React Flow 等重型依赖只能按路由或功能懒加载，首屏入口引入它们时构建检查失败（实施路线 5.1）。

## 3. 契约优先

-   新增或修改能力的顺序：先改 `packages/contracts` 中的描述符与 Schema，并写契约测试；再生成 OpenAPI 与 SDK；最后实现。没有登记 capabilityId 的服务端写入口不得合并（总框架 8.5.3）。
-   OpenAPI 与 JSON Schema 引用同一来源，CI 检查二者无重复定义且生成物与提交内容一致（生成物不得手改）。
-   兼容规则遵守总框架 13.1：可选字段扩展须验证旧消费者；删除、改类型、改单位、改权限或改状态语义视为破坏性变更，须新版本、兼容窗口与迁移说明。CI 对契约做前后版本差异检查，发现破坏性变更时要求合并请求声明并引用迁移说明。
-   错误只使用错误码注册表中的代码；新增错误码先登记再使用，CI 检查代码中出现的错误码均已登记。
-   事件类型、状态枚举与状态迁移只在契约中定义；服务端状态转换代码对照 `state-machines.json` 测试，不允许出现契约外的迁移。

## 4. 编码规范

### 4.1 Python（服务端与 Worker）

| 规则 | 要求 | 强制方式 |
| --- | --- | --- |
| 格式与静态检查 | 统一格式化；启用错误、导入、复杂度、安全与异步相关规则集 | ruff（格式与检查），CI 失败即拦截 |
| 类型 | 全部新代码有类型标注；对外接口层与领域层不得出现未约束的 `Any` | 严格模式类型检查（候选：mypy strict 或 pyright strict，M0 选一） |
| 边界数据 | API、事件、命令载荷在边界用 Pydantic 模型校验，内部不传裸 `dict` | 评审清单 + 类型检查 |
| 异步 | 事件循环内不做阻塞 I/O 与 CPU 重计算（总框架 12.4）；重任务进 Job | ruff 异步规则 + 评审 |
| 数值精度 | 金额、工时、比率等精确值用 `Decimal` 或整数最小单位，禁止 `float`；对外以字符串编码（数据处理 12.3） | 自定义检查 + 契约测试 |
| 时间 | 只用带时区的时间；绝对时间存 UTC；业务日期与业务时区分开保存（总框架 8.7） | ruff 时间规则（禁止无时区 datetime） |
| SQL | 只用参数化查询或 SQLAlchemy 表达式；禁止字符串拼接 SQL | ruff 安全规则 + 评审 |
| 异常 | 禁止裸 `except` 与吞掉异常；对外只返回注册错误码与 messageKey，不暴露栈（能力契约 12） | ruff + 错误体契约测试 |
| 日志 | 结构化日志，带 requestId / jobId / pluginId；禁止记录凭据、令牌与不必要的业务明细 | 日志脱敏测试 + 评审 |
| 秘密 | 代码、配置默认值、测试数据中不得出现秘密；只用 SecretRef | 提交前与 CI 秘密扫描 |
| 复杂度 | 单函数圈复杂度与长度设上限（提案：复杂度 ≤ 10），超出须拆分或在评审中说明 | ruff 复杂度规则 |

### 4.2 TypeScript 与前端

| 规则 | 要求 | 强制方式 |
| --- | --- | --- |
| 类型 | `strict` 全开；禁止 `any` 与非空断言滥用；契约类型只来自生成的 SDK | tsc + ESLint |
| 格式与检查 | 统一格式化与 React / Hooks 规则 | ESLint + 格式化工具，CI 拦截 |
| 国际化 | 界面文案只用语言资源键，不写字面量；数字与日期用 Intl（总框架 8.7） | ESLint 字面量规则 + 双语构建检查 |
| 安全 | 不用 `dangerouslySetInnerHTML` 渲染不可信内容；不可信 UI 走隔离 Origin（总框架 8.6） | ESLint 规则 + 评审 |
| 精度 | 不对字符串编码的精确数值做 `Number()` 转换后计算（数据处理 12.3） | 评审 + 单元测试 |
| 性能 | 首屏 JS 体积预算、懒加载、长列表虚拟化（实施路线 5.1） | 构建体积检查，超预算 CI 失败 |
| 资源释放 | 订阅、定时器、WebGL / 媒体资源在卸载时释放（可视化 6、13） | 重复挂载测试 |

### 4.3 数据库与迁移

-   迁移采用"先扩展、迁移校验、再收缩"（总框架 13.1 第 5 条），只前滚；每个迁移可在空库与上一发布版本数据上重复执行并通过校验。
-   每张表有主键；跨模块引用使用不透明稳定 ID，不建跨模块外键（引用完整性由领域核对与对账保证）。
-   唯一约束落实幂等与业务键（能力契约 7、后台治理 5.3）；分页使用稳定排序含 ID，禁止无界查询。
-   CI 在真实 PostgreSQL（与目标主版本一致）上运行迁移与集成测试；不用 SQLite 代替。

## 5. 测试策略

### 5.1 分层

| 层 | 覆盖内容 | 要求 |
| --- | --- | --- |
| 单元测试 | 纯逻辑、规则、格式化、计算 | 快速、无网络、无数据库 |
| 契约测试 | Schema、OpenAPI、错误码、事件信封、状态机 | 每个能力与事件有正例与负例；现有契约测试为起点 |
| 状态不变量测试 | Command、JobRun / JobAttempt、PipelineRun、Revision、Release 等状态迁移 | 对照状态机穷举合法与非法迁移；候选使用基于性质的测试生成随机迁移序列 |
| 集成测试 | 模块经对外接口与真实 PostgreSQL 协作 | 以模块数据库角色连接，验证边界与事务 |
| 权限测试 | 每个 capabilityId 的允许 / 拒绝、数据范围、Agent 三道门 | 默认拒绝；每个能力至少一个拒绝用例；三道门任一关闭的用例（能力契约 A03） |
| 故障注入测试 | 重复命令、响应丢失、进程中断、Worker 失联、事件重复与乱序 | 无重复副作用，恢复先按 RunRef 找回（实施路线 M1 出口） |
| 端到端测试 | 关键业务链（总框架 15.2）与双语界面 | Playwright；只覆盖关键路径，不替代下层测试 |
| 性能与资源测试 | 体积预算、长任务、内存回基线、服务端 RSS | 实施路线 5.1 与部署第 7 节 |

### 5.2 测试数据与环境

-   测试数据一律合成（实施路线 D-10），生成器固定随机种子，同一种子两次生成逐字节相同（实施路线 5.3 任务 5）。
-   测试不访问外网；外部系统用登记的测试适配器或模拟服务。
-   测试彼此独立、可乱序与并行运行；时间相关逻辑通过可注入时钟测试，不依赖真实等待。

### 5.3 覆盖要求

覆盖率是防退化指标，不是目标本身：

-   合并请求不得降低整体覆盖率（提案）。
-   授权、命令与幂等、Job 与租约、迁移相关代码的分支覆盖率不低于 90%（提案，M0 校准）。
-   每个 capabilityId、每个注册错误码、每条状态迁移至少有一个测试引用它；CI 生成清单并检查缺口。这条比百分比更重要。

## 6. 完成的定义

一项改动只有同时满足以下各项才算完成：

1.  引用了对应的设计章节；与设计不一致时，设计已先修订。
2.  契约、生成的 SDK 与契约测试已更新。
3.  单元、集成、权限与必要的故障注入测试已补齐并通过。
4.  有数据库变更时，迁移可在空库与上一版本数据上执行并校验。
5.  界面改动已提供中英文资源，且通过体积与性能预算。
6.  日志、错误与审计符合第 4 节，没有秘密或不必要的业务明细。
7.  CHANGELOG 与相关文档已更新；遗留事项登记为 Issue，代码中不留没有 Issue 编号的 TODO。

## 7. 合并流程与评审

-   所有改动经合并请求进入 `main`；`main` 开启分支保护，必需检查全部通过才能合并，禁止强制推送。
-   每个提交带 DCO 签署行（CONTRIBUTING）；合并请求说明对应设计章节、风险与验证方式。
-   **高风险改动**（授权与委托、命令与幂等、Job 与租约、迁移、出网与入站、隔离宿主、密钥处理）须在合并请求中附风险说明与回退方式，并按第 6 节逐条自查；首次实现某类高风险机制时，另做一次隔日复查后再合并。
-   AI 辅助评审可作为补充，不替代 CI 门禁与第 6 节自查；AI 生成的代码与人工代码适用同一规则。
-   合并请求保持小而单一：一个合并请求只做一件事，便于回退与追溯。

## 8. 安全与依赖质量

-   依赖漏洞检查（候选：pip-audit、pnpm audit）进 CI；高危漏洞未处理不得发布。
-   静态安全检查（ruff 安全规则，必要时加 Semgrep 等候选）进 CI。
-   秘密扫描在提交前与 CI 各一次，并启用托管平台的秘密扫描与推送保护。
-   新增依赖须登记用途、许可证与来源（开源与第三方依赖治理）；CI 生成依赖许可证清单，先出报告、后续按治理规则拦截；发布时生成 SBOM。
-   隔离宿主门禁 G-ISO（ADR-016）通过前，代码中不得出现执行用户提交代码的路径；相关入口由特性开关关闭，并有测试证明请求被拒绝。

## 10. 待定与校准

-   工具最终选型（类型检查器、导入与依赖检查工具、基于性质的测试库、静态安全工具）在 M0 选定，按开源与第三方依赖治理登记许可证与来源。
-   复杂度上限、覆盖率门槛、体积预算等数值在 M0 以实测与首批代码校准后写入本文，校准前按提案值执行、只报告不拦截的项须在门禁清单中标明。
-   本文随实际工程经验修订；放宽任何门禁须在 CHANGELOG 中说明原因。
