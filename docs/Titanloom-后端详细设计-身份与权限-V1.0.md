# Titanloom · 后端详细设计 · 身份与权限

> 版本：V1.0｜日期：2026-10-17｜状态：维护者已确认（设计页 sketch-backend-access v1，K 节 7 处 2026-10-17 "可以"）；文中数值为起点值，M0 / M1 实测后校准，写成部署参数或业务参数。
> 定位：M1 底座第一个模块 `access` 的后端设计：存什么、怎么判"能不能"与"能看哪些"、改了多久生效、别的模块怎么调用。规则以总框架 8.5、后台治理 4 为准，本文定实现。
> 依据：总框架 3.1、8.5；后台治理 4.1–4.6、5、6.4、15.4；能力契约 5.2–5.5、6、12；ADR-025、ADR-026、ADR-027；《后端详细设计 · 总图》；草图 sketch-admin-people、sketch-admin-open、sketch-scope-open（已验收）。

## 1. 管什么、不管什么

| 组 | 内容 | 平台管理页面 |
| --- | --- | --- |
| 人 | 人员、任职、部门树、人事来源记录、平台更正层、待核对 | 账户与人员 · 组与部门 |
| 登录 | 账户、密码摘要、会话、服务身份、应急账户 | 账户与人员 |
| 在哪 | 部门空间（跟人事系统）、跨部门项目及成员、环境、平台组 | 空间与项目 · 组与部门 |
| 能做什么 | 能力目录、角色（有版本）、授权、功能开放与部门 / 项目收紧、申请、到期与复核 | 角色与授权 |
| 管家 | 一门、二门、三门（资源准入）、委托 | 管家与模型（链接） |

不管：业务数据本身（只回答能不能看、能看哪些）；单个对象的"负责人"字段（各模块存，且不自动授予权限）；登录方式的地址和密钥（连接与凭据）；审计存储（发事件给公共审计）；人事系统的连接（集成中心负责拉取，本模块负责比对与写入）。

## 2. 人、账户、任职、部门分开

-   **人员**：一个真实的人一条，有人员编号（短编号 P-xxxxx）；工号只是属性，换工号、离职再入职仍是同一人员。
-   **人事来源**：记录人事系统中对应的行（source + source_key），重名、换工号靠它和证据核对。
-   **任职**：人员 × 部门 × 岗位 × 起止日期；兼岗为多条，离职再入职为多段。历史业务记录挂在当时的任职上。
-   **部门**：来自人事系统，只读、有版本、可按日期查询；每个叶子部门自动有一个部门空间（ADR-025）。
-   **账户**：一个人最多一个登录账户，有人员不一定有账户；停用账户不等于删人。
-   **服务身份**：不能登录，必须有负责人和用途，给自动化、报表、无人值守管家用。

授权里的"谁"只能是：账户、服务身份、组（手动 / 规则）、部门（可含下级）、项目角色；资源准入行（三门）里另可为管家。不能直接授予人员。

## 3. 人事数据同步

流程：拉取（集成中心定时拉取人事系统，或管理员导入 Excel / CSV）→ 存快照 → 与上次快照比对 → 能确定的直接写 → 拿不准的进待核对 → 发事件。

| 情况 | 处理 |
| --- | --- |
| 新入职 | 建人员与任职；默认不自动建账户（业务参数 `access.hr.autoCreateAccount`，默认关） |
| 离职 | 任职写结束日期；排定时任务在离职日 23:59 停用账户；建离职交接清单进上级与平台管理员待办（后台治理 15.4） |
| 离职再入职 | 不自动合并，附证据进待核对；确认后合并、保留两段任职，旧角色不恢复 |
| 重名 | 两条人员；找人接口一律带部门返回 |
| 平台更正 | 存单独的更正层（字段、值、理由、人、时间）；读取 = 人事值 + 更正；下次同步不一致进待核对，不冲掉也不悄悄以更正为准 |
| 部门调整 | 部门树出新版本；部门空间随叶子部门建、并、撤（撤前列影响，没处理完不撤）；"本人部门"类授权自动跟随 |
| 一次大量消失 | 消失人数超过上次在职人数 5%（`access.hr.massDisappearPct`）时本次比对挂起，等人确认，不按离职处理 |

首期两个入口走同一套比对：人事系统连接器每 30 分钟拉一次（`access.hr.pullMinutes`），可手动"同步"；Excel / CSV 导入用于未接人事系统时和合成数据（K5）。

## 4. 登录与会话

-   账户名 + 密码，密码只存 Argon2id 摘要。连续输错 5 次锁 15 分钟；同时按来源地址限速。
-   会话存服务端，浏览器只持 HttpOnly cookie；闲置 8 小时退出，最长 7 天重新登录；改密码结束其他会话；停用账户结束全部会话并收回其给管家的委托。
-   密码至少 10 位，不强制定期更换，拦截常见弱密码；忘记密码由管理员重置为一次性密码，首次登录必须修改。
-   首位管理员由引导流程创建，之后关闭引导；2 个应急账户平时锁定，启用须写原因、选范围、最长 4 小时，到时自动锁回并待复核；服务身份无密码、不能登录。
-   企业统一登录（OIDC）以后接入：账户多记一个外部身份，权限仍在本模块判定。
-   参数：`access.login.maxFailures` 5、`access.login.lockMin` 15、`access.session.idleHours` 8、`access.session.maxDays` 7、`access.password.minLength` 10（K6）。

## 5. 判定"能不能"

输入：谁（主体）· 对什么（能力 + 目标对象及其真实归属）· 谁在操作（本人 / 管家 / 服务身份）。顺序（后台治理 4.3），一关不过立即停止，不读取后续需要的敏感信息：

1.  **身份**：账户正常、会话有效；管家操作时委托有效。
2.  **功能开放**：仅对登记为功能的"新建 / 发起"类能力：平台层有授权 ∩ 部门 / 项目层未收掉。
3.  **基础授权**：展开主体集合（账户 + 所属组 + 任职部门及按需的上级 + 项目角色），在目标的范围链（对象 → 项目 / 部门 → 平台）上收集允许与拒绝；有适用拒绝即拒，没有允许即拒。
4.  **管家三道门**：管家操作时：一门 ∩ 二门 ∩ 三门 ∩ 委托范围；管家权限永远是本人的子集。
5.  **数据范围**：合成数据条件（第 6 节）。
6.  **状态 · 锁 · 预算**：由所属模块补充。

结果（契约 access-decision）：允许 / 拒绝、权限版本号、卡在哪一关、原因文案键、找谁、能否申请；解释接口逐关给出。对调用者看不到的对象不出现名称与数量。

## 6. 列表"能看哪些"

模块不逐条询问，而是取得一个筛选条件（契约 access-filter），由本模块 store 层翻译为参数化查询：不限 / 一条都不能看 / 允许条件之并减去拒绝条件之并，附须遮挡的列。不返回 SQL 字符串。

数据条件只能用登记的几种（K2）：本人 · 本人部门（可含下级）· 指定部门 / 项目 · 某字段 = 本人部门（字段由模块登记为权限字段）· 全部 · 遮挡某些列（列由模块登记为可遮挡）。不支持自由公式；不够用时由模块登记新的条件类型。兼岗时"本人部门" = 所有任职部门（K3）。

## 7. 授权怎么存

| 对象 | 存法 |
| --- | --- |
| 能力目录 | 各模块代码登记，部署时同步：能力编号、影响等级、能放进哪类角色、可用数据条件字段、可遮挡列。新能力默认谁都没有，进"新能力待审" |
| 角色 | 角色 → 版本 → 格子（能力 + 数据条件）；已发布版本不可改；发布新版本时绑定者一起切换，发布前给出增减影响 |
| 授权 | 一张表（契约 grant）：谁 · 在哪（平台 / 部门 / 项目 / 某个对象）· 角色或单项能力 · 数据条件 · 起止 · 允许或拒绝 · 来源 · 授予人。拒绝只针对单项能力 |
| 单个对象的共享 | 授权表里"在哪 = 某个对象"的行；修改入口在看板、表单、数据集等自己的页面，由其调用写授权接口（K1） |
| 功能开放 | 平台档位不另存（所有人 = 在「员工」角色；指定的人 = 在所选角色 / 部门 / 组；没人 = 都没有）；部门 / 项目收紧另存（契约 feature-layer），只能往紧 |
| 组 | 手动组存成员；规则组存规则（只用人事字段和平台组），成员由后台物化，人事变化时重算 |
| 管家 | 一门、二门各一张表（二门默认全关）；三门是授权表中主体为管家的资源准入行；委托单独存 |

## 8. 改了多久生效

-   全平台一个权限版本号。授权、角色发布、组成员、部门、任职、账户状态、管家门、功能开放、委托的任何变化，都在同一事务里把版本号 +1 并发出 `access.policy.changed`（契约 access-policy-changed）。
-   主程序和后台程序在内存里按人缓存有效权限，收到事件丢弃受影响者的缓存；兜底每 5 秒比对一次版本号。最长传播时间 60 秒（部署参数），超时在进度上标注意并进总览（K4）。
-   高影响操作（导出、发布给全员、改他人数据等，能力影响等级为高或声明不用缓存）执行前直接查库。
-   排队中的后台任务开跑前、每个检查点再查一次。
-   生效进度：已记录（写库）→ 各程序已收到（回报版本号）→ 排队任务复查 → 已生效。已导出的文件收不回，页面明说。

## 9. 有流程的事

| 事 | 状态 | 要点 |
| --- | --- | --- |
| 申请权限 | 草稿 → 等批 → 批准（生成授权，默认 90 天）/ 拒绝 / 撤回 / 过期（30 天无人处理） | 批准范围与期限不大于申请；负责人不在转上级或模块管理员；管家只起草 |
| 第二人批准 | 提出 → 等批 → 批准即执行 / 拒绝 / 过期 | 平台管理类角色、敏感数据、高影响能力、功能开放影响中以上往松（后台治理 6.4） |
| 到期与复核 | 临时授权：生效 → 7 天内到期提醒 → 失效。季度复核：逐条留着 / 收回，未表态不自动收回 | 90 天未用过的能力标出（判定时记最后使用，按天汇总写库） |
| 离职交接 | 建清单 → 逐项 → 清零完成；到点照停，余项标无主 | 各模块上报负责的对象；接手人须自己有权限；自动化先暂停 |
| 应急访问 | 锁着 → 启用（≤ 4 小时）→ 自动锁回 → 待复核 → 已复核 | 通知全部管理员；不能取密钥 |
| 撤最后一位最高管理员 | 直接拦截 | 须先指定接替的人 |

被拒绝的请求不逐条进审计，只记运行日志（保留 30 天），同一主体反复被同一对象拒绝时出告警；授权变化与高影响的允许照常进审计（K7）。

## 10. 对外接口

模块间只走 `access.api`（总图四条硬规矩）：

| 接口 | 用途 |
| --- | --- |
| `whoami` | 当前主体、所在部门（含兼岗）、是否管家代办 |
| `check` | 能不能（契约 access-decision） |
| `filter` | 能看哪些（契约 access-filter） |
| `explain` | 逐关解释；查别人须有诊断资格 |
| `who_can` | 对某对象能做某事的人（只返回调用者可见的） |
| `find_people` | 按编号、姓名、拼音、部门找人，一律带部门 |
| `members` | 部门 / 项目成员，某人所在部门与项目，可按日期 |
| `register` | 模块登记能力、功能、权限字段、可遮挡列 |
| `write_grant` | 资源页修改共享时调用，同样校验"你能授予吗" |

事件：`access.person.changed`、`access.employment.changed`、`access.org.changed`、`access.account.disabled`、`access.policy.changed`、`access.membership.changed`、`access.handoff.opened`。

HTTP 接口（前缀 `/api/access`，写接口按能力契约 6 走准备 / 提交并带 Idempotency-Key）：登录 / 退出、`/me`、人员与更正、待核对、账户（建、停用、重置密码、结束会话）、组与规则预览、空间、项目、角色版本预览与发布、授权（准备返回影响）、功能开放与收紧、`/explain`、申请与批准、复核、交接、应急、`/propagation/{rev}`。

## 11. 已确认的决定（2026-10-17）

| # | 决定 |
| --- | --- |
| 1 | 单个对象的共享也存在授权表，修改入口仍在资源页 |
| 2 | 数据条件只用登记的几种，不支持自由公式 |
| 3 | 兼岗的"本人部门" = 所有任职部门 |
| 4 | 权限内存缓存，最长 60 秒生效；高影响操作执行前不用缓存 |
| 5 | 人事数据两个入口（定时拉取 30 分钟 + Excel / CSV 导入）同一套比对；入职默认不自动建账户 |

| 7 | 被拒绝的请求不逐条进审计，只记运行日志 30 天，反复被拒出告警 |

取舍见 ADR-027。

## 12. 给执行 Agent 的技术细节

**表（schema `access`，通用列见契约 record-common）**：`person`、`person_source`（unique source+source_key）、`person_override`、`employment`、`org_unit`（tree_version、valid_from / valid_to）、`hr_snapshot` / `hr_diff`、`reconcile_item`、`account`（person_id 唯一可空、login_name 唯一、kind human / emergency、status、pw_hash、failed_count、locked_until、external_subject）、`session`（只存 id 哈希）、`service_principal`、`dept_space`（org_unit_id 唯一）、`project` / `project_member`、`env`、`grp` / `grp_member` / `grp_rule`、`capability`、`role` / `role_version` / `role_cell`、`grant`、`feature` / `feature_layer`、`agent_entitlement` / `agent_enablement` / `delegation`、`policy_revision`、`propagation_ack`、`access_request`、`approval_request`、`review_campaign` / `review_item`、`handoff` / `handoff_item`、`emergency_activation`。

**判定**：按第 5 节顺序；主体展开集合与按能力分组的（范围, 条件, 效果）列表缓存于进程内 LRU（上限 2000 人，约 20 MB 内）；目标：命中 P95 < 1 ms、未命中 < 15 ms（M1 实测）。

**筛选条件**：谓词 `{field, op: in|eq, values}`，field 必须是调用模块登记的权限字段；store 层翻译为参数化 SQL。属性测试：对同一主体与样本数据，`filter` 结果与逐条 `check` 一致。

**人事同步**：快照与比对在 Runner 重道执行；离职停用通过调度在 `valid_to` 当日 23:59（`access.hr.disableAt`）生成任务。

**登录**：Argon2id m=19 MiB、t=2、p=1（OWASP 现行最低推荐），M0 在主机上实测单次 ≤ 300 ms；会话 id 256 位随机；CSRF 双提交；失败计数按账户 + 按来源地址令牌桶。

**错误码（拟定）**：`ACCOUNT_LOCKED`、`FEATURE_NOT_OPEN`、`SECOND_APPROVAL_REQUIRED`；无权限沿用 `ACCESS_DENIED`。

**验收要点**：拒绝优先；无允许即拒；管家权限 ⊆ 本人；功能开放 = 平台 ∩ 层；规则组不能引用权限；已发布角色版本不可改；撤权 60 秒内判定变化；filter 与逐条 check 一致；看不到的对象不出现在解释中；最后一位最高管理员不可撤；离职停用后会话全部失效；人事一次消失超过 5% 时挂起。契约测试 `test_contracts_part9.py`。
