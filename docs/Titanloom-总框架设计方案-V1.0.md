## 1. 平台定位

建设一个由 Agent
智能管家统一协助使用的综合数据与业务平台，以数据处理平台为数据核心，贯通表单平台、考勤、工具自动化和可视化。

人提出目标、制定规则并保有最终控制权；智能管家理解目标、安排工作、调用平台能力、跟进进度、检查结果和汇报异常；各业务中心执行自己的专业逻辑。

平台以浏览器访问为主要形态，支持企业内网部署。在共享 Linux
服务器上运行时，所有后台计算、脚本、构建、媒体处理和查询均受资源配额限制。内网或离线环境中的
Agent
能力取决于是否具备可用模型服务；模型不可用时，业务系统和已发布的确定性任务仍可运行。

### 1.1 核心原则

1.  一个统一门户、七个正式业务能力域、一套公共平台能力与公共服务底座；领域能力可通过内置模块或插件包交付，部署可按依赖裁剪，业务所有权保持明确。
2.  Agent
    是平台智能管家，熟悉并可调用全部已注册、已授权的功能，不作为业务数据的最终事实来源。
3.  所有看板业务数据统一经过数据处理平台汇聚、加工和发布，不从考勤、表单或导入文件直接旁路查询。
4.  原始业务记录由所属中心管理；分析结果和发布数据集由数据处理平台管理。
5.  附件统一存储，通过稳定 ID
    与业务记录关联；数据处理平台汇聚附件元数据及引用，可视化按权限加载文件。
6.  各中心通过受控契约协作；跨中心写操作调用业务
    API，不直接修改其他模块的表。
7.  页面操作、Agent 调用和自动化任务复用同一套服务端业务规则和权限检查。
8.  成熟、重复任务固化为确定性流水线，模型不参与每一次常规计算。
9.  模块化单体起步，重任务独立进程执行；模块边界不等于必须拆成微服务。
10. 运行可观测、任务可追踪、失败可恢复、人工可接管；缓存、日志和临时文件均有容量及保留策略。
11. 平台底座管理契约与公共治理，领域模块拥有业务事实，插件交付可变实现；不另建插件权限、数据出口或任务中心。
12. 首期参考实现采用 React + TypeScript、Python 3.12.10 +
    FastAPI、PostgreSQL 与 Polars；公共契约不绑定实现语言或分析引擎。
13. 能力不设人为上限，资源必须有明确上限；架构面向未来，生产基线面向稳定。不以最新版或单一组件版本代表平台能力。
14. 架构完整、部署可裁剪；按实际资源选择最小、标准或增强部署，不将扩展组件设为最小部署的硬依赖。

## 3. 产品结构与导航

统一门户提供登录、工作空间切换、业务项目目录、首页、我的工作台、我的待办、公告、全局搜索、消息和最近任务。首页是空间或项目的共享主页，我的工作台是个人布局（3.2）；我的待办是全平台统一收件箱，各领域待办在此汇总，办理时进入所属领域；公告归门户，支持必读与阅读确认（Shell 9、9.1）。手机等窄屏终端使用同一路由与授权，以底部标签导航呈现（Shell 4.1）。平台管理、空间／项目设置与业务能力域入口形成三层入口，共用身份授权；项目上下文不自动授予引用资源权限。

各领域可调整的单值业务参数由领域登记，统一在平台管理的"业务参数"页维护；需要编辑器的定义（班次、表单、流水线、看板等）仍在各自领域（ADR-022、后台治理 7.5）。外部通道与入站端点在平台管理的"集成中心"配置（ADR-018）。

业务能力域包括智能管家、表单平台、考勤签到、工具自动化、数据处理、数据可视化、知识与文档。具体部署可按角色、空间、许可与资源裁剪导航入口；入口是否显示不改变领域是否存在及其对象所有权。插件管理放在平台管理区，空间和项目提供启用入口；不新增插件业务中心。

智能管家拥有独立工作台，也可以在任意中心通过侧栏唤起。侧栏共享管家任务体系，并接收当前页面已授权的项目、资源和选中对象上下文。打开某个页面不代表自动授权管家修改其全部内容。

整个 Titanloom 都是平台级 Agent 的工作环境。每个已接入的业务领域都应声明面向
Agent
的发现、读取、分析、建议、草稿、正式修改及管理能力边界，并可在本领域页面提供
Agent
入口；哪些动作实际开放由能力契约、目标资源权限、有效委托、三道门、自治风险和领域审批共同裁决。Agent
可以跨领域到权威位置取证和执行已获准的修改，再把结果及证据带回原任务，不被发起页面限制在单一中心；跨域移动不转移业务所有权，也不使
Agent
获得额外权限。暂未实现或尚未启用的能力要明确显示不可用，不能用对话推断授权。

侧栏上下文发送前必须通过第 8.5 节的 Agent
资源准入与模型输入检查；人工能看见的页面内容不自动成为管家上下文。

### 3.1.1 人员主数据与跨源身份

平台主数据服务（内置公共服务插件）管理 Person（稳定
`person_id`）、Employment（任职及有效期）、Organization（组织及历史）、SourceIdentity（外部系统身份映射）和受版本管理的
Reference
Data。一个自然人的多来源记录先按有证据的映射归一；重复、换工号、离职再入职、重名及组织调动保留历史与可追溯的人工核对流程。登录主体、服务主体与
Person 分开建模，不因登录账户存在就推断人员业务身份。

姓名、工号、邮件地址、来源 `user_id`
不得作为跨模块人员主键；业务记录引用稳定
`person_id`，同时保留来源标识、原始值、映射版本及生效时间。未经核对的匹配进入待处理状态，不自动合并或覆盖历史事实。考勤和表单平台等领域中心拥有自身业务事实，主数据服务只拥有人员与组织主数据及映射，不接管领域事实。

Studio 或 Director 布局。

## 5. 平台总体关系

产品入口同级，运行时存在两条相互协作的主链路：

1.  任务链路：人工界面 / 智能管家 / 固定自动化 / 未来调用端 →
    受控能力边界 → 各中心业务服务 →
    任务结果与证据。智能管家不是其他入口的必经节点。
2.  数据链路：考勤 / 表单 / 本地导入 / 外部数据源 → 数据处理平台 →
    统一数据服务 → 可视化。

跨模块主动调用统一遵循"调用者 → Capability / Command → 目标领域 → 必要时
Job / Executor"的受控链路。Human、Agent、Automation
复用服务端业务规则；跨领域携带上下文但不继承隐式权限。领域对象只有一个权威
Owner，公共基础设施拥有执行、身份、授权、资产、审计、通知等机制，不取得领域业务语义；Shell
和后台治理可维护可重建的投影、索引和缓存，但不得成为领域事实的第二权威来源。

Command 表达希望领域执行的意图，DomainEvent
表达领域已经发生的事实；自动化消费触发源时以 TriggerBinding /
TriggerOccurrence 记录消费关系，再形成 AutomationRun。Notification
负责送达，Alert 表达需要关注的异常或治理条件，Audit
负责证据记录；已读通知、已确认告警和领域业务状态不得互相冒充。

管家调用某中心，并不意味着业务数据需要经过模型转发。查询、文件传输和大规模计算使用服务接口及任务系统执行，模型仅获取任务所需且有权访问的信息。

附件使用独立资产通路：上传 → 资产服务 → 业务关联与元数据汇聚 →
数据集返回附件引用 → 可视化授权加载。文件二进制无需为数据加工重复复制。

## 6. 统一数据处理核心

### 6.1 数据分层

  层         职责
  ---------- ------------------------------------------------------------
  统一接入   实时事件、增量同步、批量导入、来源登记、接入水位
  原始层     保留源记录、批次、版本、变更类型和原始文件引用，支持重放
  标准层     校验、去重、类型转换、人员部门映射、时间口径统一
  业务层     跨源关联、统一指标、明细与汇总、数据质量结论
  服务层     发布 Dataset / Query、版本契约、权限过滤、聚合、缓存、快照

所有数据均纳入平台接入和治理；简单数据可以轻量发布受控视图，不要求每条链路物理复制四份表，也不要求人为增加无效处理步骤。

### 6.2 实时与批量统一

-   考勤、表单的新增、修改、撤回和删除都需要进入同步协议；删除通常通过明确的变更标记传播，并遵循保留政策。
-   业务提交成功后可靠投递变更，采用事务事件记录或等效可靠机制，避免"业务已保存但事件丢失"。
-   不假定消息只到达一次：事件有稳定
    ID，消费者幂等，结合来源版本处理重复与乱序。
-   源变更包含记录
    ID、事件时间、采集时间及源版本或水位；监控同步延迟并显示数据新鲜度。
-   新签到执行增量更新；补卡、历史修订和回补只重算受影响范围，并更新相关汇总。
-   数据处理故障不阻断正常签到和表单提交；恢复后补齐积压，必要时执行对账。
-   实时延迟、积压恢复时间和数据量上限以实测确定，不承诺任意规模的零延迟。

### 6.3 考勤计算与分析计算的分界

考勤中心依据自己的规则生成正式出勤结果；数据处理平台汇聚这些结果及授权的原始明细，与工时、产量等数据关联，计算分析指标。两处不得各自维护一套同名但不一致的出勤算法。

数据处理发现业务错误时，提出异常或调用获授权的来源修正流程，不直接修改考勤或表单平台业务表。

### 6.4 看板统一出口

可视化业务数据通过数据处理平台发布的 Dataset / Query
获取，服务端执行行列权限、参数校验、行数体积限制和查询预算。展示资产、页面代码和控制命令不属于业务数据查询，不强制经过数据加工流水线。

已审批数据、草稿数据、已确认考勤和暂估结果必须有明确口径与访问权限；不能混在同一个指标中而不标识。

### 6.5 数据开发与计算分工

数据处理首期默认执行实现为 PostgreSQL SQL + Python /
Polars。控制面维护有向无环流水线（DAG）、算子注册表和统一节点契约；配置算子、SQL
节点和 Python 节点进入同一版本化流水线，统一输入输出
Schema、权限、预算、血缘、检查点和
JobRun。配置节点以配置为权威，代码节点以源码为权威；画布只编辑依赖与安全可识别的配置，不承诺任意代码与拖拽双向无损转换。

  ---------------------------------------------------------------------------------------------------------------
  工作                                     执行位置与约束
  ---------------------------------------- ----------------------------------------------------------------------
  已入库数据的过滤、关联、聚合、窗口计算   PostgreSQL 内执行，优先减少全表传出；复杂查询采用参数化 SQL

  Excel / CSV 清洗、格式统一、复杂转换     Python 调用 Polars 表达式，优先批量和可流式算子

  解析、统计、特殊算法及纯 Python 重计算   隔离执行进程，按输入数据与操作范围授权

  图表坐标、动画、颜色映射、3D 交互        浏览器 JS / TypeScript，必要时使用 Web Worker

  已授权少量结果的展示派生值               浏览器可局部计算；须区分已加载子集与全量口径，不作为正式指标事实来源

  正式考勤、跨源效率指标                   分别由考勤模块和数据处理模块计算，前端及模型不重复维护权威算法
  ---------------------------------------------------------------------------------------------------------------

算子注册条目至少声明
operatorType、实现及契约版本、输入输出字段类型与语义、参数
Schema、支持的执行环境、确定性与副作用等级、所需能力、资源预算、取消 /
重试 / 检查点能力和兼容范围。DAG
节点只引用精确算子版本及参数；发布前检查依赖环、类型兼容、权限、资源预算与执行环境，运行实例记录实际实现版本、输入版本、结果和血缘。状态变更或外部写入算子必须声明幂等或人工补偿语义；不能因更换执行器改变口径、越过数据出口或继承通用数据库凭据。首期实现
PostgreSQL SQL、隔离 Python / Polars
与受控配置算子；其他语言或引擎通过同一注册契约增量接入，不要求首期开发所有适配器。

SQL

React Flow 负责数据画布，Monaco 提供 SQL / Python
编辑；流水线状态、执行依赖和恢复由数据处理模块拥有，复用工具中心执行适配及平台任务服务。首期不增加平行的
JS 数据计算平台；将来确需 Node.js、Rust
原生算子或其他引擎时经相同契约接入，并独立验证依赖、权限、数据类型和语义一致性。

### 6.6 文件处理、数据存储与正确性

平台自有数据库明确采用 PostgreSQL。业务、元数据和分析对象按所属模块划分
schema / 表及数据库角色；schema 命名不构成权限隔离。PostgreSQL
可以分实例或增加查询副本，保持唯一业务所有权和稳定出口。外部数据库仍可作为经授权的数据源接入，不因此成为平台内部第二套事实存储。

原文件进入 Asset，源记录保留来源、批次和版本。批量数据通过 psycopg COPY
写入受控暂存表，经校验、去重及幂等合并后发布；不逐行 ORM
提交。支持增量导入、错误行报告及失败恢复。Parquet
作为受控检查点和交换文件，有资源
ID、权限、容量、有效期及清理规则，不新增独立查询旁路，也不要求每条链路必经
Parquet。

Polars 为主要表格计算实现，pandas
仅按已有脚本或库的兼容需要引入，避免大表反复转换。openpyxl
读取工作簿、XlsxWriter 生成导出；读取 Excel
不等于执行其公式。上线前盘点基表公式，分别迁移为经验证的 SQL / Python
规则或明确使用已确认结果；缓存公式值可能过期或缺失，不能静默当成已重算结果。

字段契约固定类型、单位、空值、时区、精度及舍入。需精确十进制的字段使用
PostgreSQL numeric 与匹配的计算类型；API 对超出 JS 安全整数范围的 ID /
整数和精确十进制采用明确编码，前端不得强转 Number 后损失精度。SQL /
Python 规则迁移用样本验证结果一致性，不维护两套独立权威口径。

### 6.7 实时、并发与性能门禁

界面反馈延迟、查询响应时间、源变更到数据发布的延迟、批任务完成时间分别定义。WebSocket
/ SSE
只负责进度或变更通知，不代替可靠事件、增量计算和数据库优化。可靠事件按第
6.2 节处理，重连从权威状态和水位恢复，不按推送次数累计业务结果。

查询服务先实施行列权限与参数校验，再执行可下推计算，并约束连接数、超时、并发、行数和返回体积。明细分页、图表聚合或降采样；不把几十万条记录全部送进浏览器再过滤。业务提交与批量分析使用独立资源额度，重任务排队、限流和取消不能只靠前端按钮。

并发请求采用异步 I/O 和有界连接池；Polars 可用其原生多线程，纯 Python
CPU 重任务使用独立进程。异步不自动增加 CPU 吞吐，多进程数 ×
单进程线程数也不能无约束叠加数据库并行度。按获配
CPU、内存与磁盘设置总额和预留，不将共享服务器全部资源视为本项目独占。

性能验收使用工时链和外来 Excel
稽查链，登记数据行数、字段宽度、关联基数、文件大小、并发、缓存冷热、CPU
配额及磁盘条件；记录查询 P95 /
P99、数据新鲜度、队列等待、任务耗时、内存与临时磁盘峰值。门槛在联调前确定并实测，不以某语言或前端框架保证"最快""零延迟"或无限规模。

## 7. Agent 智能管家

### 7.1 职责与能力覆盖

管家能发现和理解平台全部已注册功能，在授权范围内查询、设计、执行和跟踪跨中心任务。功能覆盖通过能力目录和逐项验收形成，不能仅在提示词中宣称"会所有功能"。

能力发现仅返回当前主体允许获知的目录信息；资源名称、Schema、样本及任务目标同样受第
8.5 节约束。已注册不等于已获 Agent 资格、范围启用或资源准入。

新增正式业务功能原则上同时提供可供界面和管家使用的业务接口、参数契约、权限要求和验证方式。需要用户现场参与或缺少执行条件的功能，能力目录必须明确限制。

### 7.2 管家任务过程

接收目标 → 解析上下文 → 形成计划 → 校验权限与预算 → 调用能力 → 检查结果
→ 继续、等待人工或结束。

任务需持久化保存状态、步骤、调用参数摘要、执行身份、关联
JobRun、产物、错误与证据。任务成功以服务结果及验收条件为依据，不以模型的一段完成说明为依据。

模型或网络中断后，先核对已有执行状态，再恢复任务，不盲目重新执行写操作。取消、超时、等待人工和部分完成都必须有明确状态。

### 7.3 自动化与人工控制

  -------------------------------------------------------------------------------------------
  操作类型                               总体策略
  -------------------------------------- ----------------------------------------------------
  已授权查询、分析、生成草稿、预览       可自主执行，受资源与数据范围限制

  已验证的周期任务                       使用已发布的确定性流水线与授权身份执行

  正式业务提交、审批、发布、导播         按业务角色和明确授权策略执行；默认保留既有人工门槛

  删除、批量覆盖、权限变更等高影响操作   提供影响预览，按规则要求明确确认并记录审计
  -------------------------------------------------------------------------------------------

确认必须绑定具体操作、目标、版本和参数；计划发生实质变化时重新校验，不能把对话中的泛泛同意当作永久授权。

定时任务使用可撤销、最小权限的服务身份或显式委托，不能长期保存用户登录令牌。

### 7.4 可靠性与安全边界

-   模型提出方案，SQL、规则或已验证程序执行确定性计算。
-   能力调用有时间、费用、重试和资源预算，防止循环执行与重复查询。
-   上传附件、数据内容和外部返回文本作为不可信输入，不得变成覆盖平台规则的指令。
-   凭据保存在服务端受控设施中，不进入提示词、页面代码或普通日志。
-   只发送任务所需数据给模型，模型接入方式必须满足部署的数据边界要求。
-   同一资源的人工和 Agent
    修改通过版本校验或锁协调，避免覆盖正在编辑的内容。
-   Agent 不可用不影响核心业务、已发布看板及不依赖模型的既有流水线。

## 8. 公共能力与统一契约

### 8.1 公共服务底座

身份组织与权限、工作空间及项目目录、资产管理、能力目录、后台任务、通知待办、审计监控由平台统一提供，具体实现通过内置公共服务插件交付。后台统一治理上述服务、插件、配置版本、资源预算及恢复，操作必须调用受控能力。

各领域保留自身有证据的发现、建议、修订、审核和落地事实，并继续拥有原始事项与结果，按权限提供本领域的"我的贡献"。当前不预设公共 ContributionEvent / Contribution Graph 服务；若未来出现真实跨域消费者，再单独定义可重建、经授权的聚合投影契约（见 ADR-010）。无论是否建设，均不计算积分、排名或绩效，不将提出问题者自动记为后续全部工作的完成者。

后台资源依赖、任务运行、权限判定和部署拓扑来自权威服务或可重建投影。Dataset／Pipeline
与字段级血缘由数据处理平台提供权威语义和受控查询；后台仅维护跨资源治理投影，不复制血缘推导。领域状态由领域服务维护；平台运行与治理告警由公共监控告警设施以 PlatformAlertRule／PlatformAlertInstance 管理，业务异常告警（如 AttendanceAlert）归所属领域，后台以 DomainAlertRef 聚合受控摘要，Notification 只负责投递（见 ADR-009）。图中显示版本、观测时间与完整性，并在服务端过滤无权节点与连线。声明依赖、实际调用与业务资源引用分别建模；图不是独立事实来源。任务、授权、配置及健康元数据通过受控管理接口读取，排障不依赖业务
ETL；该通路不交付未授权业务明细、文件内容或凭据。

数据目录和查询引擎归数据处理平台管理，对全平台提供共享服务。公共底座不再建设第二套数据加工或查询出口。

### 8.2 能力网关

统一能力网关是逻辑边界，可先作为模块化后端中的共享设施，不要求单独部署一个网关微服务。

每项能力至少声明：稳定 capabilityId、归属模块、契约版本、输入输出
Schema、所需权限、资源范围、操作影响等级、是否异步、幂等与重试规则、超时、错误类型、结果验证方式。

Agent 对写操作的自治风险采用跨领域 R0／R1／R2+
公共语义，详见《Titanloom-平台能力契约与Agent接入规范.md》第 3.1
节。风险等级决定允许的自动化上限与审核门槛，不能替代基础权限、委托、三道门和领域审批；某领域启用
R0
不代表其他领域自动启用。具体可证明规则与开启范围由领域登记并经平台治理审核。

网关在服务端校验身份、权限与参数，分发给所属模块执行。首期不实现、不部署
MCP，保留中性 Interaction Adapter
边界；后续协议接入须单独验收，不能绕过授权。

平台统一采用中性名称 Platform Capability
API（平台能力接口）。它是业务语义契约，不是 Agent
专用接口，也不是必须承载所有流量的单一网络进程。同一后端内可通过模块公共接口调用，不强制绕行
HTTP；数据查询、文件传输和任务执行保留各自受控通路及预算。

  ------------------------------------------------------------------------------------------------------------
  边界                                冻结职责
  ----------------------------------- ------------------------------------------------------------------------
  Platform Capability API             稳定业务能力、输入输出、权限、影响等级及验证方式；不依赖模型或交互协议

  Interaction Adapter                 将网页、自动化、MCP
                                      或未来入口映射到已授权能力；不复制业务规则，不拥有业务表

  Intelligence Provider Adapter       为管家等调用方适配模型或其他推理实现；不是业务核心必经依赖
  ------------------------------------------------------------------------------------------------------------

业务规则位于服务端业务模块，不藏在按钮、提示词或协议适配器中。新增调用端使用现有授权和业务能力；新增业务语义则按模块边界补充能力，不能假定所有未来需求都能只靠协议转换解决。第三方数据库、存储、通知及模型
SDK 留在相应基础设施适配层，不向领域契约泄漏其专有对象。

### 8.4 三类流程不得混淆

-   审批流程：等待人或规定角色作出业务决定。
-   后台任务：执行具体计算，处理排队、超时、失败和重试。
-   Agent 任务：围绕目标协调多个审批、查询和后台任务。

可以相互触发和关联，但状态所有权分别属于各自模块，不使用一个巨大的通用状态表替代全部业务模型。

### 8.5 人员与 Agent 权限方案（架构定稿）

本节为平台公共权限的唯一规范来源，适用于全部中心、接口适配器、后台任务及运行端。身份由平台管理，授权由服务端裁决，分析数据范围由数据处理平台执行，附件权限由资产服务结合业务关联执行。角色是能力包，不是身份或业务事实来源。页面、提示词、MCP
和按钮可见性均不能单独放行。

本节确定权限语义和默认行为，不代表安全实现已完成。精确表结构、接口字段及部署参数由工程契约细化；相关功能上线前必须通过第
8.5.11 节验收。

#### 8.5.1 基本判定与不可配置边界

-   人工有效权限：有效身份、角色与资源
    ACL、数据范围、业务状态及运行条件共同决定。
-   Agent 有效权限：基础授权 ∩ 有效委托范围 ∩ 平台资格 ∩ 范围启用 ∩
    资源与来源限制 ∩ 数据范围 ∩
    运行条件。任一项拒绝即拒绝，三道门均只能收窄权限。
-   进入 BusinessProject 或 VisualizationProject 不自动取得所引用
    Dataset、Query、Asset、Show 或快照的权限；复制项目不复制数据授权。
-   默认拒绝；适用范围内显式拒绝优先；项目例外不能覆盖上级硬限制。主体可组合多个角色，但多角色的允许不能抵消适用的拒绝。
-   数据源凭据和基础设施密钥不得进入模型或页面；不得旁路连库、修改不可变
    Release、向 On-air
    热推代码。平台管理员也不能通过配置取消这些架构约束。受限运行时令牌按第
    8.5.10 节管理，不等同于数据源凭据。

服务端先验证身份、实际调用端及委托，再检查基础 ACL、Agent
三道门（适用时）、数据与附件范围及模型输入许可（适用时）；通过后才可取数、获取锁或产生其他副作用。写入与
Take
在执行点再次校验有效页锁或导播租约、资源版本、授权及确认记录，防止检查后状态变化。资格回答"能不能"，租约回答"此刻轮到谁"。

#### 8.5.2 身份、执行者与委托

Agent
运行端由平台注册，不能自造身份或权限。每次受控调用均能识别授权主体、实际执行者、调用类型、组织或工作空间、委托标识、目标服务、能力范围及有效期。上述信息由服务端验证的凭证和委托记录确定，不相信客户端自行填写的
actorType，也不把用户登录 Cookie 或原始登录令牌交给模型或 Agent 工具。

交互式 Agent 在调用者当前有效权限与显式委托的交集内执行。无人值守 Agent
使用已登记、可撤销的最小服务委托，绑定责任人、任务用途和资源范围；该委托须由有权授予相应范围的人建立，普通用户不能通过选择高权限服务身份扩大自身权限。服务身份仍须通过
Agent 三道门。

Agent 发起的
Job、脚本和下游服务调用必须保留执行来源、委托边界与关联任务，不得进入
Worker
后变成无限制系统调用。独立由人工发布的确定性周期任务可采用专用服务身份，但
Agent 触发它时仍按本次 Agent
委托校验输入、操作范围和结果访问，不得借此绕过三道门。

新增权限先登记 capabilityId
或发布契约新版本，默认不授予，不自动加入旧角色模板、Agent
资格或范围启用配置。禁止仅增加按钮而不登记服务端能力。

#### 8.5.6 所属、引用与数据血缘

资源准入须分别处理所属层级、调用范围和数据来源：

-   所属层级：权威归属项目或父资源关闭，子资源不能自行开放；客户端不能任意改传
    projectId
    来规避。跨范围直接调用须由服务端解析资源归属及有效调用范围。
-   引用关系：项目 A 关闭后，不能通过 A 管理或访问其引用；但 A
    仅引用共享 Dataset D，不等于 A 有权封禁 D 在所有项目的使用。通过项目
    B 访问 D，须独立满足 B、D 及其权威归属和来源限制。
-   数据血缘：源表单或数据产品对 Agent
    关闭，其受限数据经清洗、关联、复制、快照、导出或索引后仍保留限制。无法证明返回结果与受限来源隔离时默认拒绝，不靠换路径或改名称放行。多个来源的限制按本次结果实际依赖合并；尚无可靠细粒度血缘时按整个结果从严处理。

最高授权管理员可按明确流程批准一个独立分析副本对 Agent
开放，默认不批准。例外须记录责任人、来源和输出版本范围、字段、转换规则、用途、有效期及审计；仍需满足副本的人工作用域、三道门与模型输入许可。例外不解除原数据限制，不自动覆盖新增字段、变更转换或范围外后续版本；源撤回和例外到期须重新判定。

平台资格的 agentMaxPolicy

确认记录绑定确认人、capabilityId
及契约版本、目标资源、预期资源版本、规范化参数摘要、有效期、关联命令和一次性消费标识。确认人须具备相应操作资格；变更目标、参数或版本后须重新确认。确认不扩大执行主体的权限。重复投递同一已接受命令按幂等结果处理，不能重复产生业务副作用。

聊天可承载受控确认交互，但普通文字"同意"不能直接放行；须由平台完成身份校验、展示具体操作并生成可验证记录。Agent
不能为自己确认。发布、Take
等原人工门槛在正式开放相应能力并通过专项验收前继续保留。

#### 8.5.8 模型输入、缓存与间接出口

允许执行能力与允许向模型提供数据分别判定。模型可见内容是基础权限、三道门、来源限制、委托范围及平台
/
资源模型输入规则的交集。许可须绑定允许的模型服务或部署边界，允许内网模型不等于允许任意外部模型。

Agent
可在获授权后启动确定性统计任务并仅获取获准的状态或汇总；原始明细无需经过模型。Query
结果、附件及 OCR、搜索摘要、资源
Schema、样本、侧栏上下文、错误日志、历史对话检索和模型记忆均纳入同一出口检查，不能作为旁路。

Human 与 Agent 的可交付缓存及授权决策缓存分离；Agent
间也须按有效主体或权限指纹、数据范围、调用范围、策略版本及数据版本隔离。Agent
不得直接取得人工缓存结果；命中缓存仍须验证当前权限与来源限制。底层是否复用受控计算是内部实现，不能省略结果出口鉴权。

资源关闭或撤权后，已有上下文及记忆在后续模型调用前重新筛选；无法可靠分离受限信息时停止复用该上下文。不得声称可以通过关闭开关收回已经发送给模型或已被用户导出的数据。

#### 8.5.9 撤权、配置入口与审计

一门收回使全部相关二门在授权判定上失效；二门、三门、人工 ACL
或委托收回，均须触发相应策略版本更新及缓存失效。新的受控调用使用最新权威策略；分布式策略缓存必须有明确最大陈旧期限，不能以仍在有效期内的旧令牌无限延续授权。

排队任务执行前重新鉴权；运行中任务在规定检查点停止后续受限操作，结果返回和送入模型前再次鉴权。不可逆操作在提交边界检查授权；已提交事务不自动撤销，补偿按业务流程另行处理。上线前必须登记策略失效最大延迟、运行中检查间隔、令牌与离线授权期限及拒绝行为，未配置并验证相应边界的功能不得启用。

界面保留三类配置入口，不新增用户体系：

1.  平台最高授权管理员：一门资格、各能力策略上限及模型输入边界。
2.  空间 /
    项目：二门逐项启用；资源页提供三门"智能管家进入本资源"开关，按管理权限显示。
3.  数据 / 附件：原有基础授权、数据范围及业务关联；Agent
    配置不得扩大其范围。

没有业务能力或相应策略管理权的行不可开启；一门未授予时项目入口禁用并显示"平台未授予
Agent
使用权"。禁止"一键与管理员相同"。策略变更审计记录操作者、目标、前后值、原因、版本、生效状态及关联委托；执行审计记录授权主体、实际执行者、能力、资源范围、使用策略版本、确认及结果证据，日志不记录凭据或无必要的业务明细。

#### 8.5.10 现场控制与 Player 展示身份

写页必须有有效页锁；Take 和紧急切屏必须具备相应 Show / Display
能力及有效导播租约；On-air 禁止热推代码。Agent 策略不能绕过这些约束。

Player
使用平台登记的受限展示身份，不继承导播个人的数据权限。运行授权至少绑定展示主体、设备
/
Display、工作空间、pageId、releaseId、capabilitySet、数据范围或其服务端引用、策略版本、目标服务及有效期；页面只获得完成播放所需的短时授权，控制台
Cookie 不进入 iframe。

数据和附件服务按展示身份检查访问；人工或 Agent 有 Take
权限，均不意味着屏幕可获得其个人数据范围。播放准入须校验目标展示身份；Player
不得被 Agent 当作读取已禁资源的代理，Agent
获取播放状态、画面采集和结果仍须通过自身三道门。

在线接收有效撤权通知后，受影响展示内容应停止更新并遮蔽或卸载，关闭受限附件及声音，禁止继续使用受影响缓存；其他有权内容可继续。断网不能保证即时获知撤权，只能在已明确允许的离线期限内使用合规缓存；到期隐藏受保护内容，重新联网鉴权后才能恢复。要求即时在线核验的数据不得启用离线展示。缓存清理结果需可观察，失败不恢复访问；客户端控制不承诺收回外部截图或已导出文件。加密与密钥托管细则须在启用敏感落盘前完成并验收。

#### 8.5.12 角色管理与权限配置

角色是可版本化能力模板，实际授权以主体、资源、capabilityId、允许 /
拒绝及约束为依据。新增角色提供名称、说明、适用范围、负责人、能力列表、数据条件和有效期；支持草稿、启用、停用、复制及依赖检查。复制角色不复制成员、Dataset
授权或 Agent
开关。角色管理权与业务操作权分别授予，管理员不能超出其可授权范围赋权。

  ----------------------------------------------------------------------------------------------------------------------
  配置项                              执行规则
  ----------------------------------- ----------------------------------------------------------------------------------
  CRUD                                新增、读取、修改、删除互相独立；删除不隐含读取或导出资格

  专项能力                            导入、导出、附件下载、构建、发布、Take、改口径、改成员分别登记，不用 CRUD 代替

  资源范围                            工作空间、项目、指定资源以及必要的 Show / Display 范围，引用不自动继承数据权

  数据范围                            保留每条授权中动作、记录条件、字段集合的对应关系，不能把不同规则拼成更大数据范围

  人员与组                            在指定范围授予角色或单项例外，可附有效期；组变化触发权限版本更新

  冲突与默认值                        未授予即拒绝；适用的显式拒绝优先；角色合并不得越过父级限制和委托上限
  ----------------------------------------------------------------------------------------------------------------------

权限界面按模块 → 资源 → 能力组织，CRUD
可成组展示但独立勾选；支持限行、限列、限屏、限节目、期限及加减例外。新增
capabilityId
默认不进入旧角色模板，权限目录升级须显式审核。保存前用服务端同一裁决逻辑预览某主体在某资源上的生效权限及拒绝原因，审计记录变更前后值；预览本身也须有权查看相关主体与资源。

例如"安全稽查员"可以新增和修改本人所属范围的问题记录、读取获准清单及预览关联图片；删除、批量导出、附件下载、发布看板和修改成员分别授权。能够打开稽查项目不代表能读取全部源表。Agent
使用该能力仍须再过三道门，角色配置不自动启用 Agent。

### 8.6 统一插件化边界

平台统一保持身份与授权、能力目录、Dataset / Query 出口、Asset ID、JobRun
和审计的语义契约。运行内核管理插件装载、服务绑定与生命周期；公共服务及领域实现均通过插件交付。领域服务拥有表单、审批、考勤、流水线和可视化等业务事实，替换实现不改变数据所有权。插件不等于工具：需要独立调用的操作才登记为工具，图表、布局和内部算子不强制再建工具入口。

  ------------------------------------------------------------------------------------
  插件贡献                            归属宿主与范围
  ----------------------------------- ------------------------------------------------
  datasource / file-parser /          数据处理接入与计算宿主；源适配不得被页面 import
  transform / quality-rule            或形成查询旁路

  form-control / validator / print /  表单平台宿主；表单版本和审批状态仍由模块管理
  workflow-action                     

  attendance-source / attendance-rule 考勤宿主；正式结果与规则版本仍由考勤模块管理

  tool / trigger / executor           工具中心与平台任务宿主；复用 JobRun

  page-component / renderer / layout  可视化宿主；代码构建进固定版本 Release
  / transition / media                

  channel-preset                      集成与消息通道宿主；出站通道预设与入站适配预设，仅声明式配置，
                                      不含任意脚本（ADR-018）

  ui-contrib / intelligence /         受控界面贡献、模型 /
  interaction-adapter / player-host   协议适配与设备宿主；不得接管核心授权
  ------------------------------------------------------------------------------------

这些是扩展目录。对每个贡献类型，宿主分别发布版本化协议，至少定义注册标识、输入输出或事件
Schema、调用方向、执行位置、权限和数据范围、隔离级别、资源预算、生命周期、失败与撤权处理、依赖与升级迁移。数据源只负责受控接入；转换算子进入
DAG 注册表；分析引擎只能由 Dataset / Query 服务调度；任务执行器领取
JobRun；renderer /
页面组件仅消费获授权的展示数据。一个插件包可贡献多种类型，但每种贡献独立声明和授权，不因安装包获得其他类型能力。具体类型只有在所属宿主发布契约、预算和验收后才能安装启用。普通页面、表单配置或内部函数不强制打包成插件。插件管理在平台管理区统一完成，不各中心另建安装器。

PluginPackageVersion 是带签名的不可变版本包，清单至少包含
pluginId、版本、发布者、贡献类型、入口、输入输出 Schema、Host SDK
兼容范围、依赖、申请权限、CPU / 内存 / 时间 / 网络 / GPU
预算、隔离要求及语言资源。签名覆盖清单和全部执行产物摘要，信任来自平台登记的发布者，不能信任包自报身份；离线交付依赖和验证材料，生产不临时联网补包。

Installation 表示部署级安装与批准的运行授权；Enablement 表示空间 /
项目按贡献启用，默认关闭；Instance
保存具体连接、工具、组件等配置和精确版本引用。安装、启用、实例使用、能力授予分别记录，批准插件运行权限不等于
Agent 一门资格。实际调用取调用者 /
委托权限、插件运行授权、数据范围与运行时约束的交集；Agent
继续叠加三道门和模型输入限制。

Host SDK
同时规定插件调用平台能力和宿主调用插件实现两个方向。插件只能使用已登记能力、事件和扩展接口，不
hook
内核、不任意写其他模块表、不自建用户或查询出口。新能力走能力目录流程，默认拒绝；插件声明的
Agent 策略上限不能覆盖平台裁决。

受审查的内部后端扩展可随模块部署；第三方代码和用户脚本使用受操作系统约束的独立进程，限制目录、网络、凭据、时间与资源。Worker
名称或容器名称不构成隔离保证。声明式 UI 由可信宿主渲染，任意第三方 UI
使用隔离 Origin；同源 CSP 不作为保护控制台凭据的唯一边界。Player 只加载
Release 钉住的编译产物，现场不热装源码。

生命周期为登记校验 → 安装未启用 → 范围启用 → 实例引用 → 升级 / 停用 /
卸载。停止新用、停止服务、紧急禁用和卸载分开：普通停止新用可保留获授权的旧
Release
依赖，紧急禁用或撤权须使受影响内容按策略遮蔽或降级；固定版本不能绕过安全禁用。卸载前检查主页、Release、On-air、流水线及实例依赖，仍被使用的产物不得物理删除。插件迁移与业务数据保留独立，卸载不自动删除业务事实。

首期验证组件、文件解析器、转换算子、工具及模型适配的真实链路，同时交付主页基础
3D 渲染实现；通用重型 renderer / media / 第三方 UI
扩展按需求逐项开放。验收包括不改核心新增组件、数据源仍走统一出口、Agent
关门后插件拒绝访问、模型停用不影响人工业务、依赖卸载拒绝、未批准权限拒绝及故障预算有效。

### 8.6.1 小内核与可信启动边界

"一切皆插件"指可独立交付的能力实现遵循统一契约；普通函数、每个表单或页面无需单独打包。Runtime
Kernel
仅管理清单校验、依赖解析、服务注册与绑定、作用域及生命周期，不拥有人员、业务数据或领域状态机。公共服务包括主数据、身份、授权、资产、任务和审计；领域插件包提供各业务能力域能力。

内核前的可信启动器校验批准的部署组合、发布者及产物摘要，生产必需能力集合由受保护的部署策略确定，普通插件及项目配置不能覆盖。授权、身份等必需服务缺席、不兼容或未就绪时拒绝相关业务准入，不能回退为放行。服务实现可替换不等于权限检查可删除；替换治理服务属于受控部署变更。

### 8.6.4 生命周期、升级与恢复

运行状态至少区分
registered、starting、ready、draining、stopped、failed；它们与安装、范围启用和发布状态分别保存。启动失败撤销已注册服务、订阅及资源预留；停止时先拒绝新工作，再排空或受控终止在途任务，撤销订阅、定时器、连接及临时资源。清理必须幂等，超时进入
failed 并保留诊断。

卸载仅撤销运行资源，不撤销已提交业务事实或外部副作用。升级计划记录影响、契约兼容、数据库迁移、在途任务、旧版本保留、验证及回退条件。代码回退不等于数据迁移可逆；不可逆迁移须声明恢复点或前向修复策略。运行默认固定原代码、输入、配置和组合版本；检查点跨版本恢复须明确验证。

按需加载以宿主和依赖为单位：前端入口延迟加载，重任务按需分配
Worker；必需治理、调度及声明的消费者按部署要求常驻。资源额度按组合总池与实例共同限制，不把所有插件同时启动作为默认行为。

## 9. 文件与附件复用

所有上传由统一资产服务生成资产 ID
和版本，记录文件类型、大小、状态及派生规格。文件完成必要检查后才可用于预览或处理。

Player 的离线发布包。

## 10. 工具、流水线与执行分工

工具与自动化中心管理可复用工具定义、脚本及固定依赖、受控执行环境和触发配置。数据处理平台拥有数据流水线的步骤依赖、数据检查点、质量规则和发布状态。公共任务服务负责通用排队、租约、运行记录及取消机制。

数据流水线可引用已发布的工具版本，无需再造一套 Python
执行器。智能管家可以创建流水线草稿、启动任务和处理异常，但不替代固定任务调度器。

脚本不在 Web 主进程或 Player 中运行。Worker 限制
CPU、内存、执行时间、网络、挂载目录和临时磁盘；不向脚本授予整个平台的数据库权限。

失败重试先判断操作是否安全；涉及写入时使用幂等、检查点或明确补偿。不是所有业务操作都能自动回滚，无法撤销的步骤必须在执行前说明影响。

## 12. 部署与资源治理

### 12.1 初期部署原则

-   前端统一门户和设计组件，各中心按需加载。
-   前后端分离：前端独立构建，通过版本化接口访问后端；支持独立部署和兼容窗口内独立升级。同域、同机或同一部署包不改变逻辑分离，沙箱内容仍遵守隔离
    Origin 要求。
-   后端模块化单体，各模块明确接口与数据所有权。
-   平台元数据、业务与首期分析数据库统一采用 PostgreSQL，按模块划分表或
    schema 并设置数据库角色；不因此允许跨模块任意写表。
-   文件通过统一 Asset API 访问，底层使用受控文件存储或对象存储。
-   数据加工、Python、媒体转码、页面构建使用分组 Worker 与各自额度。
-   交互请求与重任务分配独立预算，避免批量任务拖慢签到和填报。
-   模型接入通过可替换适配层，根据内网条件选择允许的模型服务。

PostgreSQL
是事务与权威事实核心，也承担首期经预算控制的分析查询，不承诺单实例无限承担
OLAP。数据处理平台分为控制面（Dataset / Query
定义、Schema、权限、血缘、质量、计划选择）与执行面（PostgreSQL SQL、隔离
Polars Worker、Parquet 中间结果及按需扩展的分析引擎）。执行适配器保持
Dataset / Query
的字段、权限、版本、错误与新鲜度语义稳定；切换引擎须校验等价性与回退。Parquet
是有保留期限的交换或分析产物，不是事务权威库。

首期不强制第二种数据库。先测量并发、查询延迟、数据量、写入影响和成本；PostgreSQL
副本或独立分析实例仍不满足目标时，通过架构决策评估 Apache Doris 等 OLAP
引擎。Doris、ClickHouse
等均为待实测候选，不预设优先顺序；引擎选型与部署需要真实查询样本、目标资源配额、运维条件、数据一致性和成本证据，接入适配器仍属于工程开发与认证，不是纯运维切换。可视化、Agent
和业务模块始终通过受控 Dataset / Query 出口，不直接选择或连接执行引擎。

配置发布与实际激活分别记录，激活失败不能标记完成。关键变更执行预期版本校验、影响预览及必要确认；删除在提交边界重新核对权威依赖。备份恢复验证数据库与资产引用，并重新核对撤权、调度租约和外部副作用，防止旧权限复活或重复执行。

### 12.2 统一预算

为工作空间、任务类型和服务进程定义可配置额度，包括查询并发、数据库连接、CPU、内存、临时磁盘、附件大小、缓存容量、日志保留、模型调用及重试次数。

### 12.3.1 大数据表格选型门禁

大量明细浏览的表格视为独立客户端能力，必须支持服务端分页或游标、排序、筛选与分组、行列权限、虚拟渲染、取消过期请求及可恢复的查询状态；导出由服务端按完整授权结果生成，不能把浏览器已加载页当作全量数据。评估表格引擎时用真实列宽、长文本、聚合、并发和目标浏览器进行功能与帧时间验收；封装数据请求与状态契约，避免业务规则依赖某个表格库的专有行模型。AG
Grid Server-Side Row Model 仅作为采购评估候选，属于 Enterprise
能力，需连同许可、预算和企业内网授权流程决策；也可选择满足同一验收条件的开源实现。未完成选型与采购，不在方案中确定产品。

### 12.3.2 环境与部署档位

开发验证环境为小规格 Linux 单机（CPU、内存和磁盘均受限），用于 Linux 兼容、最小部署和功能测试，不代表正式容量验收。目标共享 Linux 的具体 OS、权限、可用资源和数据库部署政策另行调查，不以物理总内存推定平台可用配额。开发验证环境与企业数据隔离，未经企业批准不得传入企业数据或凭据；测试使用合成或已授权脱敏数据。

### 12.4 执行与实时实现约束


JobRun 与领域流水线状态在 PostgreSQL
持久化。标准队列部署中，业务事务写入 outbox 后可靠入队，任务消息传 ID
和受控引用，不塞入大型结果或凭据；执行前、结果交付和不可逆提交边界再次鉴权。Celery
状态和 RabbitMQ
消息不能作为任务唯一事实来源，租约、心跳、幂等、检查点及对账用于处理中断与重复执行，不宣称恰好一次。

API 的异步路径使用可等待的数据库 / 网络接口；阻塞文件工作与 CPU
重计算不在事件循环运行。数据、构建、转码与低延迟操作使用不同队列和容量配额，定时触发有唯一活动调度者或有效租约。队列有界，超过容量明确排队、限流或拒绝；持久任务不交给进程内临时后台回调。

Polars 执行在新启动的隔离进程中初始化，采用兼容的 spawn / exec
启动方式；Celery
调度任务只负责启动、监管和收集结果，不能在已初始化多线程引擎的进程上直接
fork
计算。线程数在进程启动前配置，并受平台总预算限制；进程数、数据库并行和内存峰值共同验证。流式计划存在内存回退，必须检查实际计划并设置失败
/ 降级策略；取消须终止或回收对应执行进程及临时资源。

网络推送用于通知与控制，权威状态可重新查询；推送通道不承诺硬实时。页面采用分页
/ 虚拟列表、查询合并、取消过期订阅和有界结果，3D
与媒体只在可见和预算允许时活动。高代码不免除执行、清理和性能约束。

### 12.5 版本与工程验证门禁

上线前登记完整依赖与兼容矩阵、离线包、目标浏览器 / Device
Profile、批准的发布者和迁移路径。验证中英文、权限合并、插件隔离、契约兼容、任务恢复、数据库与资产联合恢复、发布和主页引用；不以
UI 截图代替运行验证。

先完成工时链及外来 Excel /
附件链的最小闭环，再扩大数据量与并发；指标覆盖第 6.7
节以及页面交互延迟、帧时间、GPU / 解码使用和反复挂载后的资源趋势。具体
SLO
和准入门槛在测试前登记，超预算应限流、降级或拒绝，不能事后用"机器不够"替代约定。

## 13. 一致性、版本与恢复

-   各模块在本地事务中维护自身业务一致性；跨模块同步默认采用可追踪的最终一致性。
-   定期对账发现遗漏、重复或水位异常，支持范围回补。
-   数据契约、表单、考勤规则、工具、流水线、可视化发布分别版本化。
-   变更先查询依赖和影响范围，破坏兼容性时使用迁移、兼容窗口或显式升级。
-   回滚代码不自动回滚业务数据；回滚前检查契约、规则与数据兼容性。
-   备份覆盖数据库和资产，并验证引用一致性及恢复能力。恢复目标在部署方案中确定。
-   故障恢复和重试有次数、时间及资源上限，不允许无限重启或无限重算。

### 13.1 长期兼容与替换规则

1.  平台能力、事件、任务状态、权限语义、资源引用分别维护契约版本。字段可选扩展也须验证旧消费者；删除、改类型、改单位、改权限或改状态语义按破坏性变更处理。
2.  破坏性变更采用新版本、明确兼容期限、使用方清单和弃用通知；保留适配或迁移路径，以契约测试证明支持的前后端、Worker
    和 Runtime 组合，不承诺永久兼容所有历史版本。
3.  写命令记录稳定命令标识、幂等键、预期资源版本、身份与关联任务；约定幂等有效期及参数冲突处理。重试先核验执行结果，不能仅因超时重复产生业务副作用。
4.  长任务由领域 Run 与公共 JobRun
    分层表达：PipelineRun、AutomationRun、AgentTask
    等领域运行保留各自业务状态与结果语义；JobRun / JobAttempt
    只表达公共调度、执行、尝试、进度、产物、错误、恢复与取消机制。取消
    JobRun 不自动等于取消领域
    Run，也不承诺撤销已经完成的业务操作。事件可靠投递、去重、乱序处理和重放遵循第
    6.2 节，不假定恰好一次。
5.  数据库变更采用可追踪迁移：先扩展结构、迁移并校验数据，支持必要的新旧兼容，最后移除旧结构。数据回退或修复需独立方案，不能把代码回滚当数据回滚。
6.  保留源码、依赖锁定、构建与部署配置、Schema
    和迁移记录；持续维护受支持运行环境及安全更新。不可变 Release
    不等于旧依赖可以永久安全运行，升级后生成新 Release。
7.  新技术接入优先增加适配器或局部模块；业务语义、数据模型或安全假设发生根本变化时，允许受控局部重构和迁移。目标是限制变更范围，不能保证任意未来技术零修改接入。

### 13.2 演进验收

-   新增一个非网页调用端，可在相同授权下查询、提交命令和跟踪
    Job，不复制业务规则、不直连业务库。
-   停用模型服务及 Agent
    适配器，人工核心业务、已发布看板和不依赖模型的确定性流水线仍可运行。
-   模拟命令重复、响应丢失、事件乱序和进程中断，确认无重复业务副作用，结果可追溯。
-   契约升级后，支持窗口内的旧客户端和新客户端均通过测试；数据迁移、备份恢复及不兼容发布拒绝有验证记录。
-   替换一个外部实现时，契约测试验证业务语义不变；确需数据迁移时另行校验完整性，不将"可替换"误写为"零成本"。

## 14. 子方案编写与协同规则

每份子方案统一包含：目标和范围、用户与权限、对象模型、状态与流程、功能和界面、输入输出契约、Agent
能力映射、版本与发布、异常恢复、资源预算、验收标准及阶段计划。

Tool / AutomationRun 契约；Shell

## 15. 实施与整体验收

### 15.1 建议实施路线

1.  明确公共身份、项目与资源模型，搭建公共资产和能力接口基础。
2.  完成一个简单表单及一种考勤来源，将变更可靠汇聚到数据处理平台。
3.  建立工时与出勤关联、指标计算、数据集发布，并由已有可视化能力制作看板。
4.  将所需脚本与周期处理纳入工具、流水线和统一执行体系。
5.  管家接入已验证能力，先覆盖查询、任务跟踪和草稿生成，再按风险逐步开放执行。
6.  扩展业务规模、自动化覆盖率和 Agent 自主范围，每次扩展通过专项验收。

平台能力契约从第一阶段开始设计，不等 Agent 接入时再补；Agent
只是能力消费者之一，其自主执行范围随能力验证逐步扩大。

本节只保留原则性顺序；各阶段范围、出口门禁、工程产物和待决事项见《Titanloom-实施路线与首期工程基线》，两者不一致时先修改本节。

"首期"在各子方案中的含义是各自的首期范围，其合集无法一次交付。统一口径：**最小可用发布（MVP）**为实施路线的 M0–M4；**首期基线完成**为 M0–M6 全部出口门禁通过。子方案中"首期必须包含"的条目，按实施路线登记的里程碑交付，不再各自决定开工先后（见 ADR-015）。

### 15.2 首条完整业务链

员工填报工时并上传图片 → 主管审批 → 考勤产生并确认出勤结果 →
数据处理平台汇聚与关联 → 发布效率指标及授权附件引用 → 可视化展示 →
管家接受目标、协调任务并返回结果证据。

## 16. 总体架构结论

本项目通过一份总框架统领七个正式业务能力域、公共平台能力与公共服务底座。智能管家作为平台级协作入口，各领域分别拥有自己的业务事实和领域运行语义；数据处理平台负责分析数据、Dataset
/ Query / Pipeline 及数据血缘；资产服务负责文件复用；公共 Capability /
Command、身份授权、Job / Executor、Audit、Notification
等机制支撑人工、Agent 和固定自动化的一致执行。

现有详细方案保持独立并通过公共契约协作。当前优先任务是完成全方案交叉同步和一致性核验；随后按实施路线进入工程化，并补齐经核验确认缺失的公共规范，而不是继续在总框架中复制各领域内部设计。

### 16.1 语言无关的公共契约

Python 是首期主实现语言，不是平台协议。Capability API、Dataset /
Query、Asset、JobRun、插件和事件契约以版本化 OpenAPI / JSON
Schema、HTTP、消息、文件、SQL / Parquet
等适当格式表达，保留鉴权、幂等、错误及兼容规则。独立 Java 服务或 Rust /
C++ 计算 Worker
仅在负载、团队能力和运维成本证明收益时接入，仍遵守同一权限、数据出口和预算，不因多语言而绕开领域所有权。
