# Titanloom 架构决策记录

> 起始版本：V1.0｜日期：2026-09-26｜最近追加：2026-10-06（ADR-024）｜性质：设计决策留痕，不代表实现验收。
> 与方案正文分开维护。新裁决追加记录；改变现有裁决时写明替代关系、影响、迁移和验收，不覆写原裁决。

## ADR-001：数据血缘由数据处理平台拥有

-   **状态**：V1.0 采纳。
-   **背景**：数据处理的 LineageEdge 与管理后台的 DependencyEdge
    可被误用为两套血缘模型。
-   **决策**：Dataset、Pipeline、字段映射的血缘推导和查询归数据处理平台；后台只保留跨资源治理投影，经受控接口嵌入或跳转权威血缘。公共图形组件可复用。
-   **影响**：授权、版本、覆盖率和"未知／部分"证据随权威查询返回；后台不能从
    DependencyEdge 推导字段血缘。
-   **验证**：同一 Dataset
    在两处查看的血缘版本一致，后台投影滞后时标陈旧，受限节点不泄露。

## ADR-002：统一告警实例，领域状态独立

-   **状态**：已被 ADR-009 替代；保留本条作为历史裁决。
-   **背景**：领域节点的"告警"状态与 AlertRule／AlertInstance
    容易重复实现。
-   **决策**：领域服务拥有状态及事件／指标信号；公共告警服务拥有规则评估、实例、去重、静默、路由与确认。静默不修改领域状态。
-   **验证**：质量异常信号可生成告警实例；静默和确认不把质量失败改成通过。

## ADR-003：公共任务与领域运行分开

-   **状态**：V1.0 采纳，精确工程 Schema 待验收。
-   **背景**：后台任务图、数据处理 PipelineRun 与公共 JobRun／JobAttempt
    可能各建状态真相。
-   **决策**：能力规范第 8.3 节定义公共 JobRun 设计状态；JobAttempt
    是具体执行尝试。PipelineRun 拥有 DAG、质量门禁与发布结果，通过
    domainRunRef 关联 JobRun。后台只聚合展示。
-   **验证**：JobRun succeeded 而质量阻断时不得显示 Dataset
    已发布；失联外部副作用进入 reconciling，不自动断言失败无副作用。

## ADR-004：分析引擎按负载证据选型

-   **状态**：V1.0 采纳。
-   **背景**：早期设计曾考虑预设 Doris
    优先，缺少当前真实负载证据；共享服务器资源非独占。
-   **决策**：首期以 PostgreSQL SQL 与隔离 Python／Polars
    实现。先测真实负载与资源预算，再评估 PostgreSQL
    副本／独立实例；仍不足时验证 Doris 或 ClickHouse
    等扩展，不预设优先级。
-   **影响**：Dataset／Query
    契约保持执行引擎中立；迁移必须验证权限、结果等价、容量和回退。
-   **验证**：留存
    P95/P99、并发、资源峰值及口径对照；未通过验收不得替换生产引擎。

## ADR-005：大数据表格单独设选型门禁

-   **状态**：V1.0 采纳。
-   **背景**：百万级数据体验、编辑能力和采购许可属于独立决策，不能由组件名称代替验证。
-   **决策**：Query
    先提供分页、排序、过滤和预算等中立接口；前端表格产品或企业版采购在实际场景、性能、许可与成本核验后确定。
-   **验证**：以代表性数据量、交互和权限场景测试，记录采购与维护成本。

## ADR-006：知识领域登记为增补方案，公共自治风险与贡献索引分层

-   **状态**：已被 ADR-010 替代；保留本条作为历史裁决。
-   **背景**：知识领域新增 R0／R1／R2+
    和跨领域贡献图；若只在本领域定义，后续中心可能重复发明。
-   **决策**：总框架登记 07
    号知识领域增补方案，不改变六个默认入口。能力规范定义自治风险的公共语义，知识域登记本域可证明规则与启用范围；公共治理层预留
    ContributionEvent 和可重建 Contribution Graph
    投影，领域保留原始事实和结果。
-   **影响**：风险分级不授予权限，某域 R0
    不自动扩展到其他领域。贡献索引不计算积分或绩效，也不把发现者算作后续全部工作的完成者；服务交付前各域仍可独立展示本域贡献。
-   **验证**：检查风险升档、来源失效、权限撤销、事件重放与投影重建；跨域查询不能泄露无权对象。

## ADR-007：平台级 Agent 可进入每个领域的授权能力

-   **状态**：V1.0 补充裁决；各领域具体能力仍按实现逐项启用。
-   **背景**：从知识页启动的核验可能需要读取或修改数据处理、业务记录、配置或可视化对象；若以页面边界限制
    Agent，将产生不完整的结论。
-   **决策**：所有领域模块为平台级 Agent
    声明可发现的读取、分析、建议、草稿、执行和管理能力，并可提供本域页面入口。Agent
    可跨领域进入权威服务，执行获准的查询与写入，再把证据返回发起任务。每项能力继续使用本域规则和平台身份、委托、权限、风险及审计契约。
-   **影响**：平台级身份不等于全域默认授权；不存在能力、尚未启用或无权访问须明确告知。知识检索网关只服务知识检索，不是其他领域事实的唯一入口。
-   **验证**：从知识问题跳至权威业务能力取证、获准修改并回链；撤销目标域权限后同一任务不得继续取数或写入。

## ADR-008：领域对象唯一 Owner，治理与 Shell 只持可重建投影

-   **状态**：V1.0 采纳。
-   **背景**：Shell、后台治理、搜索、关系图和扩展注册表都需要跨域展示对象；若各自保存可写副本，会形成多个事实源。
-   **决策**：每个领域对象只有一个权威
    Owner。Dataset／Query／Pipeline／PipelineRun
    归数据处理；BusinessRecord／Revision／WorkflowInstance／HumanTask
    归表单平台；Tool／AutomationPlan／TriggerOccurrence／AutomationRun／StepExecution
    归工具自动化；KnowledgeSpace／Document／KnowledgeVersion
    归知识；Page／Release／PlaybackSession／EmbedSession
    归可视化；JobRun／JobAttempt 等公共执行对象归公共 Job / Executor
    设施。Shell
    与后台治理仅保存受控引用、索引、缓存和可重建投影，必须能标记来源、版本与陈旧度。
-   **备选及不选原因**：不采用"后台统一复制所有对象"或"共享数据库即可跨域写"的方案，因为这会破坏领域状态机、授权和恢复边界。
-   **影响**：投影缺失或陈旧只能降低聚合体验，不能反向改写领域事实，也不能据此宣称对象不存在。
-   **验证**：删除并重建治理投影后领域事实不变；跨域修改仍必须调用目标
    Capability / Command。

## ADR-009：平台运行告警、领域业务告警、Notification 与领域状态分离

-   **状态**：V1.0 采纳；替代 ADR-002。
-   **背景**：ADR-002 曾规定公共告警服务拥有统一
    AlertInstance。后续考勤等领域出现具有独立业务语义、生命周期和处置规则的
    AttendanceAlert 等对象，若强制统一会丢失领域语义。
-   **决策**：公共监控告警设施拥有
    PlatformAlertRule／PlatformAlertInstance，用于基础设施、公共运行机制和治理规则；领域可拥有自身业务异常/告警对象。后台以
    DomainAlertRef 聚合受控摘要。Notification 只负责投递/read
    生命周期，领域状态仍由所属领域状态机管理。
-   **备选及不选原因**：不再采用"所有告警统一成公共
    AlertInstance"，因为技术运行故障与业务异常的确认、恢复和证据并不等价。
-   **影响**：Notification read ≠ Alert acknowledged/resolved ≠ Domain
    issue fixed；平台告警 resolved 也不能自动证明业务问题已修复。
-   **验证**：确认或静默平台告警不改变 AttendanceAlert
    或业务事实；读取通知不关闭告警；业务告警通过领域 Capability 处置。

## ADR-010：知识是正式业务能力域；Contribution Graph 不作为现成公共依赖

-   **状态**：V1.0 采纳；替代 ADR-006。
-   **背景**：旧 ADR-006 将知识定位为"07号增补"并预留公共
    ContributionEvent / Contribution
    Graph。现行文档体系已改为总体架构、公共平台规范、公共平台能力、业务能力域四层，知识已成为正式业务能力域；Contribution
    Graph 尚无独立公共契约和实现。
-   **决策**：知识与文档平台与其他业务域同级，不再使用"07增补/六中心"作为导航、依赖或所有权依据。R0／R1／R2+
    的公共风险语义继续复用能力规范。知识域拥有自身
    Issue、修订、审核、发布及贡献证据；未来若建设 Contribution
    Graph，只能作为可重建跨域聚合投影，消费各领域明确开放的证据，不预设
    `ContributionEvent` 为已存在公共服务。
-   **备选及不选原因**：不保留旧编号体系作为架构边界，也不提前创建没有实际消费者和契约的公共贡献中心。
-   **影响**：禁止积分、排名、等级的产品原则不变；各领域可独立展示本域真实贡献，跨域聚合必须权限裁剪。
-   **验证**：没有 Contribution Graph
    时知识域功能仍完整；未来投影删除重建不影响原始贡献事实。

## ADR-011：Command 表达意图，DomainEvent 表达事实；事件不是跨域写 API

-   **状态**：V1.0 采纳。
-   **背景**：自动化、插件 Event
    Handler、知识核验和跨域联动都可能消费事件；若把事件同时当作写命令，会绕过目标领域授权和状态机。
-   **决策**：业务修改统一经
    `Capability / Command -> owning Domain`。DomainEvent
    仅表达已经发生的事实。事件消费者若需产生新的业务副作用，必须调用目标领域
    Capability / Command，并在目标资源上重新鉴权。Notification 和 Audit
    同样不是业务写入口。
-   **备选及不选原因**：不采用"收到事件即可直接写目标表/状态"的松耦合假象，因为它实际上隐藏了权限、幂等、确认和失败语义。
-   **影响**：TriggerOccurrence
    是自动化对触发事实的持久消费/去重记录，不等于原始 DomainEvent。
-   **验证**：撤销目标领域权限后，即使事件仍可见，消费者也不能完成目标写入；重复事件不得重复业务效果。

## ADR-012：Execution Retry、Domain Rerun 与 Cancel 分层

-   **状态**：V1.0 采纳；补充 ADR-003。
-   **背景**：公共 JobRun / JobAttempt 与
    PipelineRun、AutomationRun、WorkflowInstance
    等领域运行具有不同语义，仅区分对象还不足以防止重试和取消向上污染。
-   **决策**：Execution Retry 是同一 JobRun 下新的 JobAttempt；Domain
    Retry / Rerun 是所属领域的新动作或新领域运行。Job Cancel
    只停止/请求停止执行工作，不自动等于 PipelineRun、AutomationRun 或
    WorkflowInstance 取消。Job succeeded
    也不自动等于领域发布、审批或业务成功。
-   **备选及不选原因**：不采用"一套 status / retry / cancel
    向所有运行对象传播"的统一状态机，因为领域可能存在质量门禁、补偿、人工任务和不确定副作用。
-   **影响**：公共 Job
    服务不能直接写领域运行终态；领域根据执行证据决定恢复、补偿、重跑或终态。
-   **验证**：JobRun succeeded + 质量失败时 PipelineRun 不发布；Job
    cancel 后领域进入何种状态由领域规则决定；网络恢复优先找回持久
    RunRef，不盲目重提。

## ADR-013：扩展实现可替换，但插件注册、Binding 与 Capability 授权分离

-   **状态**：V1.0 采纳。
-   **背景**："一切皆插件"若被理解为插件系统拥有业务对象或安装即授权，会绕过三道门和领域所有权。
-   **决策**：`Contribution -> Binding -> Host`
    只描述固定实现如何承载契约；`Capability -> Authorization -> Domain`
    决定当前主体能否执行某业务动作。Operator 描述数据处理 DAG
    的计算语义，Executor 描述 JobRun / JobAttempt 的受限执行实现；Tool
    Implementation、Automation Adapter、Model Adapter
    分类型注册。安装、启用、Binding 激活或 Executor 可用均不自动授予
    Capability。
-   **备选及不选原因**：不采用万能
    `custom.execute(any)`、插件自建用户/权限/数据出口或插件直接拥有
    Pipeline/Release 等对象。
-   **影响**：插件可以扩展能力上限，但不能改变权威 Owner、不可变
    Release、数据出口和授权边界。
-   **验证**：安装插件但未授权 Capability 时调用被拒绝；替换 Executor
    不改变 Operator 语义；插件不能直连 Titanloom 私有业务表完成跨域写。

## ADR-014：能力可持续扩展，运行资源必须有明确上限

-   **状态**：V1.0 采纳。
-   **背景**：平台目标要求高扩展上限，但运行于共享服务器；把"能力无上限"理解为"资源无界"会破坏稳定性。
-   **决策**：架构不人为限制未来
    Capability、插件类型、Operator、Renderer
    或执行宿主，但每次实际运行必须受部署预算、并发、队列、CPU/内存/IO、临时存储、超时、取消和清理边界约束。容量数字必须来自目标环境实测，不用物理主机总资源推定可用配额。
-   **备选及不选原因**：不以固定功能清单限制平台上限，也不接受无预算的动态执行。
-   **影响**：部署容量文档在真实配额、SLO、RPO/RTO 和基准测试闭环前保持
    V0.1；未来升版代表经验证基线，不代表永久硬件上限。
-   **验证**：新增贡献类型无需改写总体能力哲学，但无法获得资源预算时不得进入生产执行；混合负载持续满足目标
    SLO 后才登记安全容量。

## ADR-015：以纵向切片统一实施顺序，子方案阶段服从统一路线

-   **状态**：V1.0 采纳；《Titanloom-实施路线与首期工程基线》里程碑顺序已由项目维护者确认，升为 V1.0（2026-10-03）。
-   **背景**：各子方案分别给出 A/B/C/D 阶段且多处写明"首期必须包含"；叠加后没有统一顺序，个人开发者的交付范围无法收敛。
-   **决策**：实施顺序以总框架 15.2 的首条完整业务链为主线，按纵向切片推进；各子方案阶段服从统一路线，不单独决定开工先后。被后置的领域在首期仍须遵守同一公共契约。
-   **备选及不选原因**：不采用"各领域并行把自己的阶段 A 做完"的横向推进，因为这样会在没有端到端证据时同时固化多套未验证的抽象。
-   **影响**：新增首期范围须同时移出等量内容或延期；阶段完成必须有证据位置。
-   **验证**：每阶段出口门禁逐项有测试或演练证据；M1 用示例 Command 验证 Capability / Command / Job / Audit 抽象，不成立处先改设计并追加 ADR。

## ADR-016：隔离宿主门禁（G-ISO）先于任何用户、个人或第三方代码执行

-   **状态**：V1.0 采纳；补充 ADR-013、ADR-014。
-   **背景**：数据处理 Phase 1（个人 Python 节点）、工具自动化阶段一（受限 Python 样板）、表单平台 L1 脚本都要求执行非平台作者的代码，而插件体系、部署与总框架均规定"无法落实隔离的目标部署不开放不可信代码执行"。各方案的阶段表之间没有共同的开闸条件。
-   **决策**：设隔离宿主门禁 G-ISO。通过前，共享服务器上只运行受审查的内置实现（内置 SQL、内置 Polars 算子、内置解析器和质量规则、内置工具）；通过后才可开放个人 SQL / Python 节点、工具 Python 样板和表单脚本。G-ISO 的通过条件为插件体系阶段 C 的隔离与治理验收：操作系统强制边界的独立进程或经认证环境、网络与文件默认拒绝、CPU / 内存 / 时间 / 并发 / 临时存储限额、取消与清理、跨空间不串凭据，并有可重复的越界测试证据。
-   **备选及不选原因**：不采用"首期先放开、事后补隔离"，因为共享服务器上一次越界即影响其他租户；不采用"每个子方案各自定义隔离验收"，因为会产生互不一致的开闸标准。
-   **影响**：数据处理 Phase 1、工具自动化阶段一、表单平台 L1 在 G-ISO 前仅交付内置实现；个人插件私有启用能力顺延到门禁之后。
-   **验证**：G-ISO 前，任何用户上传代码的执行请求被拒绝；门禁通过后，越权访问文件、网络、凭据和超额资源的测试用例均失败。

## ADR-017：补充 ADR-008 的 Owner 清单（Revision 限定、业务基表、主数据）

-   **状态**：V1.0 采纳；补充 ADR-008，不改变其裁决。
-   **背景**：ADR-008 与 CHANGELOG 的 Owner 清单写作"BusinessRecord／Revision"，而考勤方案另有 AttendanceDeclaration 的 Revision；业务基表（ReferenceTable / ReferenceVersion / MappingRule）没有登记 Owner；人员主数据服务只在后台治理方案中出现。
-   **决策**：①清单中的 Revision 特指 BusinessRecord 的 RecordRevision；AttendanceDeclaration 的修订（AttendanceDeclarationRevision）归考勤，不并入表单平台的 Revision 语义。②业务基表、映射规则与引用版本归数据处理；它不冒充企业人事主数据。③Person / Employment / SourceIdentity 归平台主数据服务（后台治理方案 5.1），其维护方与来源由业务方确认（实施路线待决事项 D-03）。④填报的 WorkflowTask 统一为 HumanTask；流程中向智能管家发起任务的节点称 AgentCall，AgentTask 仍归智能管家。
-   **备选及不选原因**：不把考勤申报修订并入表单平台 Revision，因为考勤有额度占用、规则版本与团队确认等领域不变量；不把业务基表放进主数据服务，因为其有效期映射、重算影响与 Pipeline 版本强耦合。
-   **影响**：各方案引用上述对象时使用限定名；表单平台方案对象清单与流程节点名已同步。
-   **验证**：全文检索不再出现 WorkflowTask；对象 Owner 表中每个对象恰有一个 Owner。

## ADR-018：出站与入站消息通道作为公共平台能力，入站不是业务写入口

-   **状态**：V1.0 采纳；《Titanloom-集成与消息通道子方案》已由项目维护者确认，升为 V1.0（2026-10-03）；补充 ADR-009、011、013。
-   **背景**：需求要求消息推送到外部、外部消息推送进来，路径可配置并有统一可视化入口。现行方案只有零散描述，工具自动化把外部 Webhook 推迟到阶段四，Notification 渠道没有设计文档，入站没有鉴权、防重放、环路与出网保护的规定。
-   **决策**：新增公共平台能力"集成与消息通道"，不新增业务领域。出站是公共 Notification 的渠道扩展（ChannelConnection、DeliveryRoute、DeliveryRecord），入站是 Interaction Adapter（InboundEndpoint、InboundRoute、InboundReceipt）。入站按风险分为事件接入、命令、对话三种用途，首期只开放事件接入；命令与对话要求发送者可信绑定到 Principal 并取得有效委托。出站外部通道视为数据出口，须声明最高数据级别并经出网守卫。统一可视化配置入口放在后台治理的"集成中心"，对象归本能力。
-   **备选及不选原因**：不让每个领域各自实现 Webhook，因为会产生多套鉴权、密钥和出网规则；不把入站直接映射为领域写入，因为会绕过 Capability、授权和状态机（ADR-011）；不在首期开放命令与对话类入站，因为发送者身份绑定与审计尚未就绪。
-   **影响**：工具自动化的外部 Webhook 改为经 InboundEndpoint 接入（M5）；SecretRef 与出网守卫提前到 M4；插件体系新增声明式预设类型。
-   **验证**：Webhook 地址与令牌不在任何响应与日志出现；解析到私网或元数据地址被拒；重复投递与重复接收不重复产生副作用；未绑定身份不能触发命令；恢复环境默认停用所有通道。

## ADR-019：项目许可证选定 Apache-2.0，署名为 Titanloom contributors

-   **状态**：V1.0 采纳。
-   **背景**：开源发布需要确定项目许可证、版权署名和贡献者权利机制。
-   **决策**：许可证选定 Apache-2.0；版权署名为项目名"Titanloom contributors"；贡献者权利采用 DCO；第三方声明按实际构建产物生成。
-   **备选及不选原因**：不选 MIT，因缺少明文专利授权；不选 AGPL-3.0，因其对企业集成与合规审查增加摩擦，且项目目标是广泛企业采用。
-   **影响**：仓库根目录放官方 Apache-2.0 文本；NOTICE 与源文件头写署名；THIRD_PARTY_NOTICES 由锁文件与构建产物生成；若未来考虑双重许可，须先明确各贡献的可再许可权利。
-   **验证**：仓库历史不含凭据与受限资料；THIRD_PARTY_NOTICES 由锁文件生成且无未识别许可证。

## ADR-020：按子方案划分开发项目，单仓分目录，多 Agent 执行、架构审核

-   **状态**：V1.0 采纳（2026-10-03，项目维护者决定）。
-   **背景**：平台规模大而开发者只有一人，需要多个执行 Agent 协助。若让一个 Agent 读取全部方案并修改全部代码，上下文过大、修改范围失控，容易产生偏离设计的代码。
-   **决策**：每个子方案（含公共平台能力）为一个开发项目，平台内核按能力契约职责拆为身份与授权、命令与执行、资产·审计·通知三个项目，另设工程基础与契约两个项目，共 16 个。所有项目在同一仓库分目录存放；执行 Agent 只读本项目方案与登记的公共规范章节，只修改本项目目录；跨项目只经契约交互，需要改契约或他人代码时提交变更请求。架构负责拆工作包与审核，项目维护者负责合并。细则见《Titanloom-开发项目划分与多Agent协作规范》。
-   **备选及不选原因**：不采用每个项目独立仓库，因为契约变更要跨仓发版、跨项目集成测试需另行搭建，一人维护十余个仓库负担过重；不采用单一 Agent 开发全平台，因为上下文与修改范围无法控制。
-   **影响**：运行时架构不变，仍为模块化单体；新增项目清单文件、各项目 Agent 说明与 CI 范围检查（M0）；工程质量规范增加范围检查门禁与执行 Agent 规则。
-   **验证**：合并请求修改允许路径以外的文件时 CI 失败；导入边界与数据库角色检查生效；每个项目的 Agent 说明列出的读取清单与本规范附录一致。

## ADR-021：内置文案存于后台语言资源服务，统一格式与键名

-   **状态**：V1.0 采纳（2026-10-03，项目维护者决定）。
-   **背景**：总框架 8.7 规定了国际化原则，但前端（i18next）与服务端（Babel 模板）允许各用一套格式，键名风格不一，文案归属未定，配置数据中的名称没有设计。按子方案划分为 16 个项目后，各自为政会迅速失控。
-   **决策**：内置显示文案存放在平台语言资源服务（facilities 项目），在后台治理"语言与术语"页维护并发布为不可变语言包版本；代码只引用 `命名空间:路径` 形式的键名。前端、服务端与插件使用同一种 i18next 资源格式，服务端以薄适配层渲染、以 Babel 格式化。仓库根目录 `i18n/` 只存键清单与出厂默认文案，部署时只补数据库缺失的键、从不覆盖后台维护的文案。配置数据中的名称使用 LocalizedText。细则见《Titanloom-国际化与本地化规范》。
-   **备选及不选原因**：不在各项目目录分散存放语言文件，因维护者认为分散难以维护；不只在仓库中维护文案，因业务方调整措辞必须经过开发发布；不完全不在仓库中投放默认文案，因新功能与新部署在有人录入前会没有文案，且代码与文案的对应无法检查。
-   **影响**：facilities 项目增加语言资源服务，admin 项目增加语言与术语页；错误码注册表增加文案键；契约增加键清单、语言包与 LocalizedText；FieldRef 与可视化筛选器的显示名称改为 LocalizedText；工程质量规范增加文案键门禁。
-   **验证**：代码引用的键全部登记；再次导入不覆盖后台修改；关键文案缺失时语言包不能激活；前后端格式化结果一致。

## ADR-022：业务参数由各领域登记、在平台管理统一维护

-   **状态**：V1.0 采纳（2026-10-04，项目维护者决定）。
-   **背景**：考勤、表单平台、数据处理、可视化等领域都有需要业务管理员调整的单值配置（宽限时间、额度上限、导入行数、刷新间隔等）。若各领域各做一个设置页，管理员要在多处寻找，同一类参数的版本、生效、审计和回退做法各不相同；若全部收归后台，又会让后台承担它不理解的业务语义。
-   **决策**：业务参数由所属领域以 ConfigDefinition（类别为业务参数）登记定义、校验器与影响计算；参数值的修订、激活、范围覆盖与审计由配置服务按后台治理 7.2 管理；全平台只在平台管理的"业务参数"页集中维护，领域页面只读显示并链接过去。班次、规则集、表单、流水线、看板、流程等需要编辑器的"定义"仍留在各自领域。细则见后台治理 7.5。
-   **备选及不选原因**：不采用"各领域自设参数页"，因为入口分散、生效与审计不一致；不采用"后台自定义参数并下发给领域"，因为参数语义、合法范围和影响只有领域能判断，后台会成为第二个业务规则来源。
-   **影响**：后台治理 6.1 增加"业务参数"页，7.5 写明规则；各领域在能力登记时同时登记其业务参数定义；修改复用 `titanloom.admin.config.publish`，按领域与敏感级别分别授权；业务结果记录所用参数修订，便于解释与重算。
-   **验证**：越界值被领域验证器拒绝；同一参数只有一个可写入口；修改未到生效时间时旧值继续生效；已发布期间不因参数修改被静默重算；回退产生新修订并重新校验。

## ADR-023：插件扩展采用开放扩展点、作用域登记与热启停，信任只分官方内置与第三方

-   **状态**：V1.0 采纳（2026-10-06，项目维护者决定）。补充 ADR-013、ADR-016，不替代。
-   **背景**：现行插件方案按固定贡献类型目录扩展，新类型须由宿主先发布协议；界面扩展只有少数 Shell 扩展点；生命周期没有要求登记随插件自动撤销，生产不考虑热启停。维护者要求扩展性达到 Cordis 类桌面宿主（如 DeepSeek Harness）的水平：应用即插件树、插件互相提供和依赖服务、插件可开新的扩展点、界面由命名插槽组合、登记随插件卸载自动撤销、不重启即可启停。
-   **决策**：① 内置领域模块与公共服务实现都以官方内置插件组合；业务能力域模块可停用、可卸载（引用保护、业务数据保留），运行内核、可信启动器与必需治理服务不可卸载。② 任何插件可声明 ServiceContract 与 ExtensionPoint（含界面插槽）供其他插件提供或贡献，须带 Schema、版本、权限与数据范围、信任要求和失败语义；`titanloom.*` 只给官方内置。③ 插件的路由、服务、扩展点贡献、插槽界面、事件订阅、定时任务、语言包等全部登记在插件运行作用域下，停用、卸载、升级、撤权时按逆序自动撤销。④ 生产支持不重启启停、更新（同一扩展新版本）与替换（另一插件实现同一服务或扩展点后切换绑定），每次形成可回退的新部署组合版本；已发布 Release、主页、流水线、排队命令与运行尝试继续钉住精确版本。⑤ 信任只分两级：官方内置（平台官方发布者签名）可同进程运行、前端直接用平台组件渲染；第三方（含企业自建，签名不改变级别）后端只在隔离宿主运行并受 G-ISO 约束，前端只在隔离 Origin iframe 内经消息协议运行。
-   **备选及不选原因**：不照搬桌面宿主的同进程全信任，因为平台运行在企业多人共享服务器上；不保留"只有平台宿主可定义扩展类型"，因为扩展上限会受平台排期限制；不按签名再分企业自建一级，维护者要求只区分官方内置与第三方，规则简单、审查面清楚。
-   **影响**：插件体系新增 1.1、2.2、2.3、5.1、6.1、6.2 并同步 5、8 节；总框架 8.6 同步；Shell 第 8 节扩展点改为插槽目录；授权与所有权规则（ADR-013）和隔离门禁（ADR-016）不变。
-   **验证**：插件 A 定义扩展点、插件 B 贡献，停用 A 后 B 的贡献自动失效并提示依赖；停用插件后无残留路由、界面、订阅、定时器与进程；生产热更新时在途请求完成、新请求用新版本、钉住旧版本的 Release 不变；替换模型适配后新任务记录新绑定；企业自建插件签名后仍不能同进程加载；卸载业务能力域模块被引用阻止，或确认后保留业务数据、重装后恢复访问。

## ADR-024：智能管家经页面可读视图与声明的动作在被允许的页面上工作

-   **状态**：V1.0 采纳（2026-10-06，项目维护者决定）。
-   **背景**：此前 Shell 第 10 节与智能管家 19.2 规定管家"只用用户显式给出的上下文"、不自动采集整页。维护者要求管家成为整个系统的 agent：在任何页面上（被允许时）都能看、能动手，例如在数据处理页调出管家做看板，做完后开发者在页面上定位元素给出调整意见；各入口能力相同，只是出场方式不同。直接读取 DOM 或截图不稳定、难以授权与审计，模拟点击则无法保证走领域命令。
-   **决策**：页面向管家公开结构化的可读视图（PageView），Shell 为每页提供默认视图，模块可补充；页面声明可调用的动作（PageAction），每个动作映射到领域受控能力、只作用于草稿并可撤销；管家只能经视图"看"、经声明的动作"动手"，不读 DOM、不模拟点击，截图只在用户手动附加且只用于给意见。页面授权分不可用 / 只看 / 在草稿里改三级，上限为平台管理的管家策略与页面声明的较小者，用户在单个任务里只能下调。用户可在页面上钉住元素（稳定引用）交给管家，与全局反馈共用选取器。第三方插件界面须经插件 SDK 声明后才可见、可操作（界面插槽，ADR-023）。细则见智能管家 19.4–19.6、Shell 第 10 节与 9.5。
-   **备选及不选原因**：不维持"只用显式上下文"，因为无法满足"在页面上让管家动手、按元素给指导"的要求；不以截图或 DOM 读取作为主要的"眼睛"，因为结果不稳定、无法按字段做模型输入裁剪、也难以审计；不采用模拟点击作为"手"，因为会绕过领域命令的准备、确认与幂等。
-   **影响**：Shell 增默认可读视图、授权条、选取器与"看得见的手"；模块描述符登记视图提供者与页面动作；智能管家增 PageView / PageAction / Pin 与报错分析；后台治理的管家策略增页面授权上限；插件 SDK 需提供视图与动作声明。页面可见不等于可发给模型的原则（智能管家 8.2、A03）不变。
-   **验证**：智能管家 A16–A26，Shell S41–S46。
