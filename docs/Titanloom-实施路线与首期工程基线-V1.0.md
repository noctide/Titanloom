## 1. 约束事实（均来自现行方案）

- 测试只能用合成或已授权脱敏数据；开发验证环境不得传入企业数据或凭据（总框架 12.3.2）。
- 开发验证环境为小规格 Linux 单机，仅用于功能与最小部署测试，不代表容量；实测基线记录见 5.2。
- 目标共享生产 Linux 的 OS、权限、配额、数据库政策未知，不以物理内存推定可用资源（部署 V0.1、ADR-014）。
- 技术栈基线：React + TypeScript + Vite、Python 3.12.10（独立虚拟环境，不替换系统 python3）、FastAPI、PostgreSQL、Polars；最小档为 PostgreSQL 持久 JobRun + 有界本地 Runner，标准档才加 RabbitMQ / Celery（总框架 12.3）。
- OpenAPI / JSON Schema、数据库 Schema、契约测试、迁移脚本尚未建立（契约骨架见 titanloom-contracts）。

## 2. 两个口径与一个门禁

**MVP（最小可用发布）= M0–M4。** 交付总框架 15.2 首条业务链的人工闭环：员工填报并上传图片、主管审批、考勤确认、数据处理汇聚与发布指标、看板展示，含备份恢复演练与容量基准。

**首期基线完成 = M0–M6。** 各子方案"首期范围"在 M5–M6 补齐，包括智能管家、工具自动化、知识与文档、基础 3D 与主页嵌入、插件体系阶段 B2。

**G-ISO 隔离宿主门禁（ADR-016）。** 通过前，共享服务器只运行受审查的内置实现（内置 SQL、内置 Polars 算子、内置解析器、质量规则、内置工具）；个人 SQL / Python 节点、工具 Python 样板、表单脚本、服务端构建中执行用户提供的构建脚本或插件均不开放（可视化页面代码只在浏览器隔离 Origin 中执行，不在此列）。通过条件为插件体系阶段 C 的隔离与治理验收，并有越界测试证据。若目标服务器无法落实隔离，上述能力整体后置（待决 D-12）。

**G-ISO 的时点。** 通过条件所依赖的插件阶段 C 排在 M6，因此个人 SQL / Python 节点、工具 Python 样板、表单脚本等用户代码能力最早在 M6 之后开放；M3 的数据处理与 M5 的工具自动化在此之前只交付内置实现。项目维护者于 2026-10-03 决定不为提前开放而前移隔离验收，优先保证方案与实现的稳固。M4 的"G-ISO 评估"只判断目标服务器能否落实隔离（D-12），不代表门禁通过。

## 5. 里程碑与出口条件

每个里程碑必须同时满足"功能出口"和"工程出口"（契约测试进 CI、迁移可前滚、状态不变量有测试）。

### M0　工程基线与前置决策

交付：代码仓库、分支与提交规范、依赖锁定（pnpm-lock、uv.lock）、CI（lint、类型、单元测试、迁移检查）、S0 环境脚本；合成数据生成器（工时、考勤、基表，含脏数据、重复导入、跨月与修订样本）；契约骨架（Capability Descriptor、Command / Invocation、错误模型、幂等键）；在验证环境上用 uv 装 Python 3.12.10 并实测 PostgreSQL + FastAPI + 前端静态服务的启动、内存与连接上限；待决事项中标注"M0 前"的项均有结论或书面默认值；**性能基线与度量脚手架**（见第 5.1 节）；契约骨架见 titanloom-contracts（能力描述符、命令、JobRun、错误体的 JSON Schema 与状态机，附校验测试）。

出口：CI 在干净环境可重复构建；《Titanloom-工程质量与代码规范》第 9 节标为 M0 引入的门禁全部生效；验证环境资源实测入库；无"M0 前"悬空待决项。

### M1　公共最小内核

范围：
- 身份与空间：账户、Person / Employment 最小集（平台主数据服务，按后台治理 5.1）、空间与项目、角色与授权判定（含三道门最小形态与撤权）、资源目录、基本配额。
- 能力与命令：Capability 注册与调用、Authorization / Confirmation / Idempotency、outbox。
- 执行：持久 JobRun / JobAttempt、有界本地 Runner、**控制服务（Scheduler / Dispatcher / 租约与核对）**。
- 资产与审计：Asset 服务（稳定 ID、原件与派生）、Audit 最小记录。
- Shell A1：登录、导航、资源路由、ShellContext、上下文切换。

出口：
- 示例 Command（以填报最小命令实现）经授权、幂等、领域写入、JobRun、审计全链路通过；
- 重复命令、响应丢失、进程中断注入后无重复副作用，恢复先按 RunRef 找回；
- JobRun succeeded 不等于领域成功的用例可演示；
- 撤权后同一调用被拒；
- 周期性示例任务由控制服务触发，重启后不重复触发；
- 创建空间→授权→运行→排障→受控处置可演示（后台治理 P1 门槛）。

### M2　填报与流程 + 考勤人工闭环

两条内部切片均完成才算出口：
- **VS-2 填报链**：RecordType / Schema Registry、L0 表单运行、BusinessCommand、BusinessRecord / RecordRevision、乐观并发、Excel / CSV / 粘贴导入（哈希与业务键去重、部分成功、来源追踪）、HumanTask 与最小 Workflow、附件经 Asset、DomainEvent 经 outbox。验收见填报第 24 节。
- **VS-3 考勤链**：VS-3a 申报、签到证据、团队审核、正式结果；VS-3b 班次与排班发布、跨月检查、额度并发、异常对象（AttendanceAlert）、导出适配。考勤 21 节阶段一用例通过；考勤 23 节待配置项显式登记，不由实现者猜定。填报、考勤的能力描述符在本阶段开始前登记（D-09）。
- 插件 B1（文件解析器）按同一 Contribution 契约注册。

出口：总框架 15.3 中"变更重复乱序丢连""补卡或历史填报修订""文件导入失败""附件复用与撤权""人工与 Agent 同时编辑"通过。

### M3　数据处理最小链

范围：DataSource / Asset、Raw / Standard、版本化 DAG（内置 SQL 与内置 Polars 算子，经插件 B1 契约注册）、JobRun 对接、质量规则与 Quarantine、业务基表（版本、有效期、宽表月份列适配、精确与复合键、未匹配核验）、Dataset / Query、原子发布与回退、Snapshot、流水线级血缘、效率指标；对外使用能力契约 P1 的受控只读 Query。个人 Python 节点与本地恢复副本不在本阶段。

出口：PipelineRun 按数据处理 15.1 的运行、质量、发布三个维度实现，并通过 pipeline-run 契约测试；工时与考勤关联后可复算、可回退；基表修改展示影响并要求选择"仅后续 / 回补历史 / 并列修订"；JobRun 成功而质量阻断时 Dataset 不发布；重复导入不放大指标；每个指标可下钻到输入批次、规则版本与基表版本；业务提交不等待分析 Pipeline；表格选型结论（D-11）已登记或明确暂用分页表格。

### M4　看板、治理、容量与恢复（MVP 出口）

范围：可视化 A1（标准页面与 Release，三个页面、两个 Dataset）；Shell A2（主页草稿 / 版本 / 激活）；后台治理 P2（局部依赖、运行图、判定链、配置激活与撤权）与 P3 中的告警、备份恢复；集成与消息通道出站部分（见该方案第 10 节），首批来源为平台告警与 Notification，验收 IC01–IC06、IC14–IC15、IC17；数据库与资产联合备份恢复演练；DATA / DB / WORKER / MIX / FAILURE / SOAK 基准；评估 G-ISO 能否在目标服务器落实。

出口：部署 V1.0 升版门槛 ①–⑥ 逐项有证据，或书面说明哪项因缺主机配额无法完成（此时部署文档保持 V0.1 并标注阻塞原因）；总框架 15.2 业务链端到端演示通过；G-ISO 结论（通过 / 不通过 / 待条件）书面登记。

### M5　自动化与智能管家

范围：集成与消息通道入站事件接入（IC07–IC11、IC13，对接工具自动化 TriggerBinding；需 D-15 的可达性结论）；工具自动化阶段一至三（须 G-ISO 通过，否则仅内置工具）；智能管家按其 21 节首期基线，先覆盖能力发现、查询、任务跟踪与草稿，再按风险逐步开放执行；考勤阶段二（Agent 与运营增强）；填报阶段二；知识与文档阶段 A–B。

出口：智能管家验收 A01–A15 中与已启用能力对应的全部通过；至少两个不同业务领域完成真实跨域验收；关闭模型服务后人工核心业务与已发布看板仍可用；工具自动化三条验收业务链（22 节）中已启用者通过。

### M6　扩展与展示

范围：可视化 A2（基础 3D）、B（媒体交互）、C（发布播放与主页，含与 Shell B 的联合交付与联合验收）；Shell B–C；知识与文档阶段 C；插件 B2 与 C；数据处理 Phase 3。

### 5.1 性能目标与度量（M0 交付，数值为待校准的提案）

目标来源：项目维护者要求上限高、加载快、不卡顿、内存占用小。下表数值是**提案，不是已验证事实**，M0 在验证环境与目标终端上实测后校准，之后写入 Device Profile 与部署参数。

| 维度 | 提案目标 | 度量方法 | 主要风险与对策 |
| --- | --- | --- | --- |
| 首屏加载 | 登录后首屏所需 JS（gzip）有硬预算，超出则 CI 失败 | Vite 产物体积检查 + Lighthouse CI | Monaco、ECharts、Three.js、React Flow、Ant Design 全部按路由与功能懒加载，首屏不得引入 |
| 交互流畅 | 常规操作无超过 50 ms 的长任务；列表与表格虚拟渲染 | Playwright trace、INP、长任务计数 | 卡片多的主页须有联合预算；大数据在服务端分页，不进浏览器过滤 |
| 浏览器内存 | 反复切页、开关弹窗、挂载卸载 3D / 视频后，内存回到基线附近 | Chrome DevTools 堆快照与重复挂载测试 | 沿用总框架 6.7、可视化 6 节的资源预算与 Device Profile |
| 服务端内存 | 每个 API 进程常驻内存与进程数有上限，登记在部署参数 | 进程 RSS 采样、DATA / MIX / SOAK 基准 | 最小档不引入 RabbitMQ / Redis；Polars 任务用隔离进程并限线程与内存 |
| 数据库 | 连接数与 shared_buffers 按验证环境配额显式设置 | pg_stat、慢查询、MIX 基准 | 在小规格验证环境上先实测 PostgreSQL 能否与 API 同机稳定运行 |
| 上限 | 以安全容量点而非理论值登记；超出则排队、限流、拒绝 | 部署 7 节基准矩阵 | 引擎替换按 ADR-004，不预设 |

M0 同时建立：前端体积预算与 CI 检查、Playwright 性能追踪脚本、服务端内存与连接采样脚本、Excel 读取方案的内存对比（openpyxl 只读模式与 calamine 类读取器，用合成大文件）。

### 5.2 小规格主机预算草案（提案，M0 实测后校准）

**实测基线应记录**：总内存与实际可用内存、swap 与 swappiness、逻辑 CPU 数、常驻服务与其占用、监听端口，并标注日期；单次快照不能代替连续采样。预算以实测可用内存而非总量为上限，并为文件缓存和突发留余量。

下表是分配思路，**不是已测量事实**。

| 组成 | 提案做法 | 需实测的点 |
| --- | --- | --- |
| 现有常驻服务 | 视为固定成本，未经确认不停用 | 一周内的内存与负载曲线 |
| 文件缓存与突发余量 | Titanloom 总占用目标不超过实测可用量的约 70% | `free`、`vmstat` 基线 |
| PostgreSQL | 建议目标常驻约 200–250 MiB 以内：max_connections 约 20、shared_buffers 约 96 MB、work_mem 约 4 MB、关闭 JIT，仅监听本机 | 空载与导入峰值的真实占用（用 PSS，RSS 会重复计算共享内存）、慢查询 |
| API 进程 | 单进程起步，异步 I/O，进程数由实测决定 | 常驻内存、并发下延迟 |
| 有界本地 Runner | 与 API 分进程，任务并发 1–2，超限排队 | 任务峰值内存，取消清理 |
| Polars 与 Excel 解析 | 隔离子进程，限线程与内存，大文件流式读取 | 合成大文件峰值内存与耗时 |
| Nginx 与静态前端 | 前端在开发机构建，服务器只放产物，开启压缩与长缓存 | 首屏传输体积 |
| 不引入 | RabbitMQ、Celery、Redis、对象存储、容器编排 | — |

硬约束：小规格主机不同时做前端构建、完整测试和重基准；Vite 构建与 Playwright 放开发机或 CI。交换分区对 PostgreSQL 的影响须在 M0 评估后再决定是否启用。

## 8. 风险与应对

| 风险 | 应对 |
| --- | --- |
| 范围与人力不匹配：设计覆盖面远大于个人可交付量 | 严格按第 4 节裁剪；新增首期范围须同时移出等量内容或延期 |
| 抽象层次多，未经验证 | M1 用示例 Command 验证 Capability / Command / Job / Audit 抽象；某项区分落不了地，先改设计并记 ADR |
| 验证环境内存很小 | 前端构建在开发机完成；PostgreSQL、Python 进程的连接与内存上限先实测再写入部署参数 |
| 关键公共规范缺位 | 可观测性与审计细则最迟 M4 前成文；备份恢复专项在 M4 演练前成文；M1 先按最小记录实现 |
| Agent 跨域写入面大 | M5 先只读与草稿；执行类能力逐项经三道门与专项验收开放 |
| 用户代码在共享服务器执行 | 一律以 G-ISO 为前提；未通过不开放 |
| 授权判定缓存首期关闭（能力契约 14.2），每次请求读权威授权数据，与"加载快"目标有张力 | 正确性优先；M0 在验证环境实测授权判定耗时，必要时引入带最大陈旧期限的缓存，并按能力契约登记撤权传播期限 |
| Worker 心跳 5 秒、租约 30 秒、运行中授权检查最迟每 5 秒（能力契约 14.2 起点建议）在小主机上多 Runner 并行时开销未知 | M0 与 M1 实测后校准并写入部署参数；校准前按起点值执行 |
