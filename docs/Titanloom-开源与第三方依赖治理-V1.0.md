## 2. 外部来源登记

区分三类：设计思路参考、实际复制／修改的代码与资源、安装或分发的依赖。Harness／Cordis
当前属于设计参考；记录上游仓库、固定
commit、实际适用的许可证与引用范围，不把概念借鉴写成已打包依赖。实际引入代码或二进制时，核对原始版权、修改声明、再分发条件和必要的许可证文本。

外部来源登记与插件运行登记分层管理：本文件关注"来源是什么、用了什么、按什么权利和条件使用/再分发"；插件体系的
`PackageVersion / Contribution / Binding / Installation / Enablement`
关注"哪个固定产物如何进入平台并在什么范围运行"。实际插件包或扩展包引用第三方依赖时，应以精确版本、构建产物摘要（digest）或等价不可歧义标识关联其来源/许可证记录；插件安装成功不等于第三方权利核验通过，第三方权利核验通过也不自动授予插件运行权限。

## 3. 发布前交付物

1.  锁定 Python 与 JS 依赖；从**实际构建产物与锁文件**生成
    SBOM，并人工处理许可证未识别、双重许可、字体、媒体、模型权重和前端静态资源。
2.  根据实际再分发内容准备 `THIRD_PARTY_NOTICES.md`
    及必须随附的原始版权／许可证文本；`NOTICE`
    是否必需由实际许可证条款决定，不把方案中提到的全部候选技术栈抄成依赖清单。
3.  选定项目许可证后加入准确的 `LICENSE`、版权声明及贡献规则。可按
    SPDX／REUSE 标记源文件，自动化校验不能代替权利和兼容性审查。
4.  用 CI
    检查依赖清单、已知许可证限制及发布包清单；每次引入新依赖或素材重新核验。
5.  对可发布的插件、扩展包和独立 Worker/Adapter，发布清单应能从固定
    `PackageVersion` 或构建摘要追溯到对应锁文件、SBOM
    条目、第三方声明及实际随包字节；不能只按插件显示名称或"latest"推断依赖。
6.  替换、升级或卸载第三方依赖时，分别核对代码/资产权利义务和平台运行引用。删除依赖字节前仍须满足插件体系及领域
    Release
    的引用/保留规则；"不再允许新用"不等于可以立即删除仍被固定版本引用的产物。

## 4. 未决事项

-   数据、界面素材、图标、字体、模型与第三方库的来源及具体使用方式。
-   实际工程建立后，第三方来源登记、SBOM、插件 PackageVersion/digest 与发布产物清单采用何种存储 Schema 和 CI 工具链；现稿只冻结可追溯关系，不虚构尚未选定的工具。
-   漏洞扫描、修复时限、签名/可信发布者、离线制品库等安全供应链细则由插件、后台治理或后续安全规范结合使用方要求确定；本稿没有足够依据替它们预设具体产品或 SLA。
-   安全问题披露政策（SECURITY.md）与发布产物签名。
