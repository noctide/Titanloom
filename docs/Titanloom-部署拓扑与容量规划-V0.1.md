## 2. 一套逻辑架构，多种部署 Profile（FROZEN）

交互请求经网关进入模块化 Core；公共 JobRun / JobAttempt
执行事实与各领域自身业务事实分别以其 PostgreSQL
权威记录为准，不合并为一套状态机；控制服务负责 Job
调度、分派、租约与核对，受限 Worker / Executor 执行重任务；文件经 Asset
/ Object Storage Adapter 使用受控文件卷或后续对象存储。Agent
是可跨模块调用已授权 Capability 的平台服务，AgentTask
仍归智能管家；重计算按能力契约进入受限任务执行链。插件的执行位置与资源边界由其
Contribution 类型和 Host 契约决定，不能默认装进
Core，也不能因部署共置取得领域对象所有权。

``` mermaid
flowchart TB
  U["浏览器／调用方"] --> G["网关与 Core"]
  G --> C["控制服务与公共任务"]
  C --> P["PostgreSQL 权威状态"]
  C --> Q["领取通道：DB Runner 或 RabbitMQ"]
  Q --> W["隔离 Worker／执行器"]
  W --> A["Asset Adapter 与受控存储"]
  W --> P
```

队列仅用于任务运输；**Queue State ≠ Job State ≠ Domain Run
State**。消息携带 jobId 和受控引用，不携带大型文件、凭据或完整结果。Job
succeeded 不自动等于 PipelineRun 发布成功、AutomationRun 成功或
WorkflowInstance 完成；Job Cancel
也不自动等于领域运行取消。任务可重复投递，依靠原子领取、租约、幂等键、检查点与结果核对处理重复和不确定副作用；不宣称恰好一次。Core
不直接跑大型解析、计算、模型推理或无界插件代码。

S0／S1 的**最小档**遵循总框架：PostgreSQL 持久 JobRun + 有界本地
Runner，不依赖 RabbitMQ；**标准档**采用 Celery + RabbitMQ 和分组
Worker。二者共享任务领取、授权、幂等、恢复与审计契约。最小档不得以进程内临时回调代替持久任务。S1
标准档的单机 Broker 不是
HA，三个同机容器也不是独立故障域。S2"生产分离"并不自动达到 HA；S3
的每个故障域需经演练验证。

Worker 是首选横向扩展对象；添加消费者无需重写 Job／Executor
契约。PostgreSQL
扩展涉及连接、索引、备份、读副本和主备切换，不能把"多开实例"视为等价扩容。备份与高可用分别设计：复制会复制误删，恢复仍需保留策略及实际恢复演练。RPO、RTO
由业务确定（OPEN）。

Kubernetes 在 S0／S1 不纳入基线，S2 可评估，S3 是候选，S4
视调度规模及运维能力决定。Temporal、独立 OLAP、Redis、Kafka、NATS、MinIO
和 GraphRAG 均不是 S1
硬依赖；若某一功能达到采用门槛，另作决策并评估迁移成本。离线模型或本地
GPU 使用独立 Inference API 与 GPU 资源池，外部模型 API 的计算不计入主机
CPU／RAM；Agent 的本地编排和工具调用仍计入。

Polars
等多线程引擎在新启动隔离进程中初始化；控制任务只监管计算子进程，避免在已初始化线程池的进程上直接
fork。配置进程并发、引擎线程数、DB
并行和内存总预算，实测流式计划的回退及取消清理。

共享宿主机必须给
OS、文件系统缓存、守护进程及其他租户留资源；分配依据是管理员允许 Titanloom
使用的**实际 CPU／内存／磁盘／IO 配额**，而不是物理总内存乘一个想象的百分比。拿不到配额前不得填写安全并发数（OPEN／BENCHMARK）。

这里落实平台总原则：**能力不设人为上限，资源必须有明确上限**。Capability、插件类型、Operator
或未来执行宿主可以持续扩展，但每一种实际运行都必须落入已登记的部署预算、队列、并发、超时、临时存储和清理边界；"未来可扩展"不能成为无界占用共享服务器资源的理由。

## 6. 容量方程与测量口径（BENCHMARK）

``` text
M_Titanloom = M_core + M_postgres + M_broker_if_enabled + M_control
       + Σ(concurrency_i × P95_incremental_worker_memory_i)
       + M_shared_runtime + M_filesystem_cache_allowance + M_safety

D_required = D_postgres + D_broker_if_enabled + D_persistent
           + D_temporary_peak + D_cache + D_logs + D_backup + D_reserve
```

上述是**预算分解式，不是已验证的峰值上界**。Worker 的 P95
内存应按同环境、同数据形状和同并发采集的增量值估计；相关峰值可能同时发生，须以整机混合负载峰值复核，避免双计共享内存或漏计父进程和文件缓存。CPU
不能仅把每个 Worker 的并发相加当成"所需核数"；依靠吞吐／排队／延迟曲线和
CPU、IO
等待确定瓶颈。文件放大率定义为峰值增量内存或临时盘峰值与输入文件压缩体积之比，报告中同时给出未压缩体积、行宽和列型；小文件比值不稳定时同时记录绝对量。

所有数字保留三列：**配置上限／目标
SLO／实测值**。未运行实现、未知主机策略、未知生产数据特征时任何容量数字标
BENCHMARK，不能写成承诺。

## 8. SLO、并发拐点与选型结论

业务与运维先确认 API／Dashboard／Job 等待／Job 完成／DB／Agent Tool 的
P95、错误率、恢复目标和预期工作量（OPEN）。对每级并发绘制吞吐、P95、队列最老等待、RAM、IO
延迟和失败率；**并发拐点**指继续增加并发已几乎不提升吞吐且延迟／资源代价持续加剧的区域，具体判据在测试计划中预注册。**安全容量**是在代表性
MIX-NORMAL 与 MIX-PEAK 下，全部目标 SLO
连续满足且有经验证的宿主资源余量的最大已测试配置，不外推为更大并发。第一个持续违反
SLO 的资源或依赖点定义容量边界，CPU 单独到 100% 既非必要也非充分条件。

测试报告必须给出：环境及配额、数据指纹、版本和参数、单任务成本、各类
Worker
并发曲线、混合负载安全点、故障与长稳结果、瓶颈、置信和复测条件。由该报告再比较现有共享主机能分配的额度，以及未来
64／128 GB 等正式服务器方案；**目前不作任何容量承诺**。

## 9. 升级门槛与恢复边界

S1→S2：共享资源干扰、DB／Broker IO
与计算峰值互相影响，或故障域要求经压测／业务目标确认；先分离资源，不以是否使用
K8s 判定。S2→S3：业务明确可用性与 RPO／RTO，且多故障域、PG
主备切换、Broker 多节点（如需要）、Core
副本、资产访问与恢复演练均完成。S3→S4：节点与发布频率、手工调度成本或自动扩缩收益构成证据，再评估编排、工作流引擎及独立资源池。

无论
Profile，备份须定期恢复验证；主备不替代备份。同物理机多实例不是容灾。RPO／RTO
既要定义也要通过故障演练实测，不能只读配置推定。Worker 失败应保留 JobRun
/ JobAttempt 执行证据；PipelineRun、AutomationRun、WorkflowInstance
等领域运行根据自身语义决定恢复、补偿、重跑或终态，不能由 Job
失败直接污染。不可判定的外部副作用进入现行契约的
reconciling／人工接管路径。Execution Retry 是同一 JobRun 下新的
JobAttempt；Domain Retry / Rerun 是新的领域动作，二者分开。
