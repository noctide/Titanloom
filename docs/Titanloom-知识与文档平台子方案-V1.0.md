## 1. 定位与边界

知识与文档平台提供可定位、可引用、可核验、可修订的企业知识网络。文档、教程、规范、FAQ、图片、附件以及与功能、人员、版本、Issue
的关系，共同构成知识对象。允许个人空间采用轻治理，生产、安全、制度等空间按策略采用严格治理。

知识平台拥有知识正文、结构、发布版本、知识级责任和协作事项；统一 Asset
服务拥有二进制及派生文件；Identity /
Delegation、Authorization、Audit、Notification、Job /
Executor、插件运行时等复用公共能力；AgentTask、目标分解和模型运行上下文归智能管家。知识域只保存与自身业务对象有关的稳定引用，不复制这些公共或其他领域对象的权威状态。数据处理平台仍拥有分析
Dataset
及其数据血缘，知识关系不接管数据血缘事实。知识中引用业务状态时，应标明来源及核验时间；知识陈述不自动成为业务系统的实时事实。

以下为设计约束：目录决定放置位置，稳定 ID
决定对象身份，链接决定到达方式，类型化关系决定对象间的语义；人人可阅读其获授权的内容并提出反馈，正式内容的编辑、审核和发布按治理策略授权；Agent
是整个 Titanloom
的公共能力，知识平台是其工作场景之一；不建设知识贡献积分、排行榜或竞争等级。

## 3. 链接、资产与关系网络

链接支持
DOC、SECTION、BLOCK、资产和其他已注册平台资源，具有正向引用、Backlink、旧链接解析和失效检查。锚点与对象
ID 分开管理，标题变化不使稳定链接失效。无权限时不得因 Backlink
或关系图泄露受限对象的名称、数量、存在性或路径。

图片、视频、附件走统一 Asset Center
的上传、版本、权限、派生预览及生命周期；知识正文保存
AssetRef、用途、说明与引用位置。图片替换产生可追溯的版本变化，正文引用依据发布策略固定或显式升级。用户可定位某张图片被哪些知识版本引用，也可从图片返回关联文档与具体
Block。

关系类型采用注册和版本管理，例如
contains、references、depends_on、prerequisite、related、describes、implements、supersedes、affected_by、owned_by、maintained_by。每种关系定义允许的源/目标类型、方向、逆向展示、基数约束、来源、证据、维护者和变更权限。自动推断的候选边与人工确认的正式边分开；关系网允许环，遍历设置深度、节点数、耗时与结果上限。

关系可用于上游、下游、引用、被引用、路径和影响范围查询；查询结果标注关系来源、数据时间与覆盖范围。与公共后台的资源依赖视图通过受控接口互通，不能复制并宣称自己是数据血缘或运行拓扑的权威来源。

## 4. 协作、问题与变更

用户可选中文档、Section、Block 或图片区域，发起以下不同对象：

  -------------------------------------------------------------------------------------
  类型                    含义                     结果
  ----------------------- ------------------------ ------------------------------------
  Knowledge Issue         指出已存在的问题         定位、核验、指派、修复、拒绝或结案

  Suggestion              提出尚未定型的改进想法   讨论、评估、转需求或关闭并说明原因

  Knowledge Change        提供明确的修改内容或     校验、评审、合并或驳回
  Request（KCR）          Diff                     
  -------------------------------------------------------------------------------------

Issue
类型至少涵盖内容错误或过期、链接或附件失效、图片错误、功能与文档不一致、责任人错误、描述不清与其他问题。提交时保存对象
ID、发布版本、选中文字、上下文、关联资产、提交者和时间；对私人或受限内容按权限裁剪上下文。讨论与评论不能代替正式
Issue 状态。

允许 Issue → KCR、Suggestion → Requirement → Feature → Release →
Knowledge Update
等有证据的转化；保留每一步的来源、参与者、结论和时间。被拒绝的建议也有结果和原因。贡献链记录发现、建议、修改、审核、发布与功能落地的不同角色，不把提出者归功于后续所有工作。

## 5. 编辑、审核与发布

正式知识生命周期为 Draft → Reviewing → Published → Deprecated →
Archived；退回可返回
Draft，恢复历史内容须生成新版本，不改写旧发布快照。草稿可以协作编辑并保留冲突处理；提交审核固定候选版本和
Diff，审批基于该候选版本，内容有变化应重新验证受影响审核。

  动作                        基本原则
  --------------------------- ------------------------------------------------------
  阅读 / 发现 / 反馈 / 建议   受空间与对象可见性约束；可见不等于可编辑
  编辑草稿 / 提交 KCR         由 Contributor、Maintainer 等按范围授权
  审核 / 发布                 独立能力，按空间治理级别和回避规则决定是否需不同主体
  废弃 / 归档 / 回退          检查被引用关系、保留期、影响范围并留存审计

发布记录 Version、Change
Log、Diff、Author、Reviewer、Publisher、发布时间、生效时间、依据和历史版本。未发布草稿、已废弃版本和当前正式版本在界面及
Agent
引用中清楚区分。风险较高的生产、安全、权限和制度知识默认采用严格人工审核；个人空间可简化流程，但仍不能越过平台权限边界。

## 6. 平台级 Agent 与知识生命周期

Titanloom 是平台级 Agent
的完整工作环境，知识平台只是其中一个工作场景。每个已接入的领域模块均可向同一
Agent
提供页面上下文、只读查询、分析建议、草稿编辑和正式写入等受控能力；在知识页发起的核验可以按任务需要进入数据处理、表单平台、考勤、可视化、工具、后台或其他领域，执行获准的跨模块读写，再返回知识页呈现证据。Agent
不因当前页面而被限制只能使用知识能力，也不因平台级身份而自动取得所有模块权限。各领域保留自身业务规则、事实和发布状态。

Agent 可在获授权情况下帮助问答、写作、检查错误及过期、辅助 Review、起草
Issue/KCR、分析变更影响、发现关系和生成草稿。操作可由该模块内的 Agent
入口或跨模块任务发起，经现行 Titanloom Capability
API、查询及文件等受控通路进入目标领域；无须把全部业务动作包装为同一种
Tool，也不要求 Agent
只能"建议"、不能直接修改。具备相应能力、有效授权、委托、风险门槛及领域前置条件时，Agent
可以准备、提交并执行该领域允许的修改。页面文本或检索片段本身不授予访问结构化事实、API、Schema、配置、Release、Change
Log 或数据处理结果的资格。

正式写入遵循
`Human / Agent / Automation -> Capability / Command -> owning Domain`。知识域的
Relation、ChangeEvent、Issue
或检索结果可以提供证据和引用，但不能替代目标领域
Command；跨域核验和修改必须在目标资源上重新鉴权。DomainEvent
表达已经发生的事实，Notification 只负责送达，Audit
只保留证据，均不能因为"来自知识平台/Agent"而获得旁路写权限。

用户问"这句话是不是错了"时，Agent
先获得当前版本及定位上下文，再按获准能力进入真正拥有事实的业务模块核验，给出"有问题／无法确认／没有发现问题"的结论、证据、时间和适用范围。用户可自行提交
Issue，或在已有授权范围内让 Agent
代为提交；若问题实际属于业务记录、规则、看板或配置，Agent
可按该领域允许的流程直接准备或执行修复，并把结果回链至知识
Issue/KCR。知识页的授权不替代目标领域授权。权限同时受 Agent
运行身份、发起主体、委托范围、目标资源
ACL、能力策略、领域规则、模型输入限制和审计策略约束；Read、Analyze、Suggest、Execute、Admin
是分开授权的操作类别，是否开放由领域与管理者决定。

Agent 自治修订沿用《Titanloom-平台能力契约与Agent接入规范.md》第 3.1 节的公共
R0／R1／R2+
语义。本领域仅登记知识对象的可证明规则、自动执行开关与审核方式：R0
仅限证明不改变事实、操作步骤、权限或行为的确定性修复，R1
进入快速审核，R2+ 进入正式人工审核。R0
规则由经治理批准的版本化判定器验证；模型置信度不能独自降级风险。数字、端口、命令、链接目标、业务口径及安全语义的改动不得仅凭"看起来像笔误"归为
R0。启用知识域 R0 不授予 Agent 额外权限，也不自动开放其他领域的 R0。

每次自动修复都生成知识域自己的 Knowledge Change Event / KnowledgeVersion
证据，记录发现、反馈、核验、修改者，前后
Diff、依据、风险规则及版本、影响、时间和关联对象；它表达已经发生的知识变更事实，不作为跨域旁路写
API。提供查看依据、提出异议和按规则回退。回退是新的受控变更，不能声称消除已经被外部使用的旧内容影响。Agent
或模型不可用时，阅读、发布的人工路径与确定性健康检查仍可运行。

## 7. 检索与可选 GraphRAG

V1 基线为 PostgreSQL 元数据检索、全文检索、结构化对象定位和 Relation
Engine 关系检索。Agent 检索知识对象时通过 Knowledge Retrieval Gateway
取得经服务端授权的结果，引用明确指向知识对象与版本；核验其他领域事实时使用目标领域的受控能力与数据通路，知识检索网关不充当全平台唯一入口。检索结果不等于事实核验。

RetrievalProvider
按能力注册，可提供全文、元数据、关系、向量、混合或图增强检索。Provider
声明支持的能力、输入输出契约、数据范围、索引版本、资源预算、引用能力、权限过滤方式和健康状态。Retrieval
Router 根据问题、空间策略、可用能力、权限、成本与时延选择
Provider；不能因增强 Provider 不可用就误称资料不存在。

GraphRAG 是可选 GraphRAGRetriever
插件，首期定义契约和接入点，可按部署、知识空间或任务启停；V1
不要求安装或默认启用。简单操作问题优先使用全文或元数据检索；跨实体、多跳、冲突溯源等任务可以评估图增强检索的收益。图增强检索提供可能的知识路径和证据，涉及当前业务状态仍需调用对应权威
Capability 核验。任何插件均不得绕过授权、审计、索引隔离和引用溯源。

## 8. PostgreSQL 基线与演进边界

V1 由 PostgreSQL 保存知识领域的权威记录及关系边；Relation Engine
对外提供节点、邻接、入边、出边、Backlink、有界遍历、路径和影响查询等受控能力。关系数据可由领域对象与关系表组成，节点稳定引用所属模块的权威资源，不复制跨模块业务事实。业务代码通过
Relation Service 查询，不直接依赖底层表、SQL 方言或特定图查询语言。

扩展分为 Relation Store、Graph Query/Compute、Graph Retrieval、Graph
Visualization
四类能力，不能把不同产品假装成同一种可无损互换的数据库。Neo4j、Memgraph、FalkorDB、ArangoDB、Kùzu
可作为未来存储或查询候选；DuckPGQ 更接近图查询扩展；GraphRAG
属于检索方法及实现。列为候选不表示已经选型、获得许可或具备同等功能。

未来如引入外部图引擎，PostgreSQL
仍可作为权威事实源，由可靠事件/投影同步可重建的查询图；投影标明水位和延迟，写操作及关键授权复核权威来源。Provider
须证明权限过滤、结果语义、关系类型、版本、增量同步、故障恢复、迁移和性能满足相同契约。所谓"可替换"指通过适配与验证保持上层契约，不承诺修改一项配置就能无损切换任何异构产品。

## 9. 健康检查与变更影响

Knowledge Health
持续检查失效链接或引用、孤立对象、无人负责、长期未核验、引用旧版本、功能变更而教程未更新、图片或附件失效、API
版本不一致和内容冲突。自动判断应给出证据、规则版本和置信限制；疑似错误先建候选或
Issue，不擅自改写正式事实。

业务 Feature / Release /
配置变化应产生可追踪事件，经公共关系及影响接口查找受影响的文档、Block、FAQ、图片、流程和负责人，再安排确定性检查或
Agent 辅助核验，最后生成 Issue、KCR
或人工确认。影响结果区分"确切关联""推测关联""覆盖未知"；发布前可提示阻断性知识缺口，是否阻断由所属业务治理策略决定。

## 10. 我的贡献与通知

知识平台展示"我的贡献"：本人发现并确认的问题、建议及其后续结果、内容修订、审核、所维护知识与最近处理记录。知识域拥有原始
Issue、修订、审核、发布及结果事实，并可按稳定引用输出受控贡献证据。若未来建设平台级
Contribution
Graph，它只能作为可重建的跨域聚合投影，消费各领域明确开放的贡献证据与因果链接；当前不把
`ContributionEvent` 或 `Contribution Graph`
假定为已经存在的公共服务/契约。未启用时知识域仍按自身权限展示本领域贡献，不假定其他领域贡献可查询。仅展示真实事件与因果链；统计不作为绩效判断，不设积分、排名、等级或刷量机制。用户访问他人贡献或敏感
Issue 时同样适用权限裁剪。

订阅支持文档、目录、知识空间、Issue、功能相关知识或变化类型。通知按变化的影响和用户范围去重、汇总、限频；R0
拼写修复原则上不群发。通知包含可访问的版本差异和链接，不在消息中泄露无权查看的正文。
Notification 的 delivered / read 等投递状态不改变
KnowledgeIssue、KCR、Document 或 KnowledgeVersion
的业务状态；需要处理时，用户或 Agent 仍通过相应知识 Capability / Command
执行。

## 11. 页面与能力域

页面建议包含空间首页与目录树、文档阅读及深链、结构化编辑器、历史版本与
Diff、引用/被引用关系、Issue/Suggestion/KCR
工作台、审核发布、搜索结果、健康与影响面板、我的贡献，以及权限范围内的
Agent
上下文入口。关系图默认局部展开并提供列表替代视图；每个结论可回到对象、版本、证据和负责人。

知识领域划分十个能力域：Knowledge Space、Document Engine、Link
Engine、Asset Integration、Relation Engine、Search & Retrieval、Version
& Governance、Collaboration Engine、Knowledge Health、Knowledge
Intelligence。其中资产本体、Identity /
Delegation、Authorization、Audit、Notification、Job /
Executor、插件运行时按公共契约复用；AgentTask
及模型运行归智能管家。Contribution Graph
仅保留为未来可选的公共聚合投影候选，知识域负责自身贡献事实、证据输出和业务策略，不把拟建服务当作现成依赖。

### 12.1 资源预算与异常恢复原则

本节只汇总本文已有约束，精确数值待工程实测，不在设计稿中猜定。

- **预算**：关系遍历设置深度、节点数、耗时与结果上限；检索 Provider 声明资源预算与健康状态；全文与元数据检索首期由 PostgreSQL 承担，并计入部署统一预算；通知按影响与用户范围去重、汇总、限频。
- **恢复**：PostgreSQL 保存知识权威记录；外部图引擎、向量或 GraphRAG 投影均可重建，标明水位与延迟；关闭或故障时问答降级为全文与人工检索，不丢失权威记录，也不得因增强 Provider 不可用而宣称资料不存在。
- **失败边界**：健康检查失败产生候选或 Issue，不阻断人工阅读、编辑与发布；Agent 或模型不可用时人工路径照常；Agent 的自动修复可回退，回退是新的受控变更。
- **待工程化**：备份恢复与迁移测试、性能预算数值，见第 13 节。
