# Titanloom · 后端详细设计 · 命令与任务

> 版本：V1.0｜日期：2026-10-17｜状态：维护者已确认（设计页 sketch-backend-execution v1，L 节 7 处 2026-10-17 "可以"）；数值为起点值，M0 / M1 实测后校准，写成部署参数或业务参数。
> 定位：M1 底座模块 `execution` 的后端设计：命令（准备、确认、提交、防重复）、后台任务（排队、领取、重试、取消、核对）、定时、消息发件箱，以及运行中心的数据来源。语义以能力契约 6–8 为准，本文定实现与默认值。
> 依据：能力契约 6、7、8、14.2；后台治理 9；工具自动化 9、14；《后端详细设计 · 总图》C、D；ADR-026、ADR-028。

## 1. 管什么、不管什么

| 对象 | 含义 |
| --- | --- |
| 命令 | 一份固定的意图：能力、目标、参数、准备时固定的版本、影响预览、是否要确认、状态（契约 command） |
| 防重复记录 | 同一次点击只算一次的凭据（契约 idempotency-record） |
| 确认 | 谁在平台确认界面对哪份命令确认，一次性消费（契约 confirmation） |
| 调用 | 命令被正式接收的记录，一条命令至多一次（契约 invocation） |
| 后台任务 / 执行尝试 | 后台要做的一件事及每次领取（契约 job-run、job-attempt） |
| 执行登记 | 每个能力的执行方式、道、确认、重试、取消、核对窗口（契约 execution-binding） |
| 定时规则 / 计划时刻 | 周期规则与每个计划时刻是否放了任务（契约 schedule-rule、trigger-occurrence） |
| 消息发件箱 | 与业务同事务写入、由后台程序投递的事件（契约 outbox-event） |
| 待核对 | 副作用不确定的任务及其结论（契约 reconcile-case） |

不管：领域自己的运行与结果（流水线运行、审批实例、自动化运行），本模块只说"后台那件事跑完了没有"，不替领域说业务成功（能力契约 8.1、8.7）。

## 2. 一次会改东西的操作

例：周宁发布装配一部 10 月排班。

1.  **准备**：解析参数、补默认值、把"最新版""本部门"固定成"第 3 版""58 人"，计算请求摘要与命令摘要，查权限，生成影响预览。
2.  **给你看影响**："58 人会收到通知；其中 3 人本月已有补签"。
3.  **确认**：仅高影响能力（执行登记 confirmPolicy=confirm）；必须是本人在平台确认界面点，管家不能确认，聊天里的"同意"不算（能力契约 6.4）。
4.  **提交 = 一次写完**：锁命令 → 复查权限（高影响不用缓存）与版本 → 消费确认 → 写调用、任务、消息 → 置已接收，同一事务（能力契约 7.2）。准备后目标版本变了，提交被拒，要求重新准备。
5.  **后台去做 → 结果**。

命令准备后 15 分钟内不提交即过期。低影响的同步操作（改草稿、勾设置、唐宁提交补签）准备与提交在同一请求、同一事务里完成，不弹确认，不存预览，但照样记命令与防重复记录（L1）。

## 3. 命令状态

准备中（仅需后台算预览的能力）→ 等你确认 → 可以提交 → 已接收；未接收前可取消或过期。已接收不代表做完，结果看任务。状态机见契约 state-machines.json。

## 4. 防重复

-   **同一次点击**：页面每次提交生成一个防重复编号（UUIDv7），重发带同一编号。作用域 = 工作区 + 主体 + 委托 + 能力 + 契约主版本 + 编号。内容一样返回原结果，内容不同返回 `IDEMPOTENCY_CONFLICT`。首次只接受过去 24 小时至未来 5 分钟生成的编号（能力契约 14.2）。
-   **同一件业务事**：由领域定义业务唯一键（例：门禁事件编号），重复推送不重复写；同一文件不一定是同一次导入，由领域判断。

## 5. 后台任务

状态按能力契约 8.3；运行中心分组为等待（排队中、等重试）、运行（运行中、取消中、待核对）、结束（完成、失败、已取消、超时）。结束时必须写明已发生的影响：没有 / 全部 / 一部分 / 不知道。

"四件事"分开显示：收到了（命令已接收）· 执行完了（任务完成）· 质量通过 · 正式发布（后两者看领域）。

## 6. 失败、重试与核对

-   **确定没做成 → 自动重试**：默认一共试 3 次，间隔 30 秒、2 分钟，±20% 随机错开（L2，业务参数 `exec.retry.*`）；各能力可在执行登记中改（自动化已定间隔 5 分钟）。没权限、参数错、业务规则不允许不重试。
-   **不知道做没做成 → 待核对**：不自动重发。平台先调用领域核对方法自动查证，默认 15 分钟（执行登记可按能力改，L3）；仍不清转人工，结论四种：确实做完了 · 确实没做（可安全重试）· 只做了一部分（交领域补偿）· 还查不清；必须附证据，由领域命令落地；没有"直接标成功"。2 小时没人处理进负责人待办。
-   **重新运行 ≠ 重试**：重新运行是新命令、新任务，记"重跑自"，先显示会不会重复写；能否从检查点继续由领域判断。

## 7. 领取与公平

-   领取、租约 30 秒、心跳 5 秒、fencing token 见总图 11。租约过期后先确认原进程确实不在了，再允许他人接手（后台治理 9.3）。
-   轻道并发 4、重道并发 1（ADR-026）。重道按部门 / 项目轮流：刚跑完一件的范围让位给其他范围排着的任务（L4）。
-   排队上限：每个部门 / 项目重道最多 20 件，全平台 200 件，超了接收时返回 `CAPACITY_EXCEEDED`；排队 1 小时未开始提醒发起人与平台管理员，不自动取消（`exec.heavy.maxQueuedPerScope`、`exec.heavy.maxQueued`、`exec.heavy.waitAlertMin`）。
-   重道子进程限内存（默认 512 MiB）与 CPU 时间（= 登记的最长运行时间），超限终止并记失败。
-   运行中心控制：取消（需操作权限；未开始直接取消，运行中在检查点停，已提交如实报告完成，不确定进待核对）· 暂停领取（正在跑的照跑）· 排空（不接新活，做完可安全重启）· 调先后（只在同一范围的队内）。

**首期不做按 CPU / 内存等维度记账的配额（L7）**：只用两条道并发、重道子进程限额与排队上限。运行中心「配额」标签首期显示这三样的已用 / 上限；后台治理 9.3 的完整配额随标准档实施（实施路线登记）。

## 8. 定时

-   规则存：rrule、IANA 时区、有效期、错过策略、重叠策略；默认时区为业务时区（业务参数，默认 Asia/Shanghai），计划时刻存 UTC（L5）。
-   后台程序每 15 秒检查到点（`exec.scheduler.tickSec`）；同一规则同一计划时刻只放一件（唯一约束）。
-   错过默认不补跑并记"错过"；补跑必须声明次数与时间窗上限并限速；上次没跑完本次跳过并记账（工具自动化 9）。不存在的时刻跳过、重复的时刻取较早。
-   运行中心 › 计划：未来 24 小时会跑什么，同一条道同一时刻超并发标注意。

## 9. 消息发件箱

-   业务写入与事件同事务写入发件箱；后台程序按 id 顺序、每个订阅者独立游标投递，至少一次；订阅者按事件编号去重，处理与去重记录同事务。
-   单个订阅者失败只阻塞它自己，持续失败进运行中心；积压超 1 万条告警。
-   事件只带类型、对象、版本，不带业务明细（契约 outbox-event）。

## 10. 保留与清理（L1、L6）

| 数据 | 保留 |
| --- | --- |
| 命令、防重复记录 | 完整 30 天，之后转摘要（编号、摘要、命令编号）再保留 180 天 |
| 投完的消息 | 7 天 |
| 任务记录 | 180 天；失败或开过待核对的 365 天 |
| 运行日志 | 30 天 |

清理任务每晚 03:10（业务时区）分批执行，跳过仍被引用的记录（例：未结的待核对）。审计不在此清理。

## 11. 运行中心每列的来源

名称与编号（任务类型 + 模块登记显示名；短编号 JR-xxxx）· 发起人（命令主体；管家代办、定时规则分别标注）· 排队与运行耗时（接收 → 首次领取 → 结束，分开算）· 尝试次数（执行尝试条数；入队次数另记）· 进度（已完成 / 总数 / 单位，总数未知不画百分比）· 已发生的影响（effectStatus）· 业务结果（链到领域运行）· 日志（按尝试；尾部 500 行；不含密钥、连接地址、业务明文）· 资源（重道子进程内存峰值与耗时，取操作系统数据）。

## 12. 对外接口

模块内 SDK（`execution.api`）：`register_binding`（登记执行方式）· `prepare` / `confirm` / `submit` · `enqueue_in_tx` / `emit_in_tx`（在模块自己的事务里放任务、写事件）· `job_handler`（实现"拿到任务怎么干"：读输入、按检查点报进度、响应取消、交回结果与影响）· `reconcile_handler`（领域核对方法）· `schedule`（登记 / 修改 / 暂停定时规则）· `get_job` / `subscribe`。

HTTP：能力契约 6.1、8.5、8.6 的命令与任务接口；运行中心 `GET /api/admin/runs`、`POST /api/admin/runs/{id}:rerun-prepare`、`POST /api/admin/reconcile/{id}:conclude`、`POST /api/admin/lanes/{lane}:pause|resume`、`POST /api/admin/workers/{id}:drain`、`GET /api/admin/schedule?hours=24`。

## 13. 已确认的决定（2026-10-17）

| # | 决定 |
| --- | --- |
| 1 | 所有写操作都记命令；命令与防重复记录完整保留 30 天、摘要 180 天 |
| 2 | 自动重试一共 3 次，间隔 30 秒、2 分钟，随机错开；可按能力登记 |
| 3 | 副作用不确定先自动核对 15 分钟，再转人工；2 小时无人处理进负责人待办 |
| 4 | 重道按部门 / 项目轮流；每范围排队 20 件、全平台 200 件；排队 1 小时提醒 |
| 5 | 定时按业务时区（默认 Asia/Shanghai），每 15 秒检查 |
| 6 | 保留：消息 7 天；任务 180 天（失败 / 核对 365 天）；运行日志 30 天 |
| 7 | 首期不做多维度记账配额，只用道并发 + 重道子进程限额 + 排队上限 |

取舍见 ADR-028。

## 14. 给执行 Agent 的技术细节

**表（schema `execution`）**：`execution_binding`、`command`、`idempotency_record`（scope 唯一）、`confirmation`、`invocation`（command_id 唯一）、`job_run`（含 lane、scope_kind / scope_id、not_before、current_attempt_id）、`job_attempt`（worker_id、fencing_token、lease_expires_at、checkpoint、peak_rss_kb、cpu_ms）、`schedule_rule`、`trigger_occurrence`（unique rule_id + planned_at_utc）、`outbox_event`（bigserial id + event_id 唯一）、`outbox_cursor`、`consumed_event`（unique subscriber + event_id）、`reconcile_case`、`worker`。

**重道轮转**：候选按（该 scope 最近一次开始时间升序, priority, created_at）排序后 `FOR UPDATE SKIP LOCKED` 取一；排队上限在接收事务内计数校验。

**子进程**：`multiprocessing` spawn；`RLIMIT_AS` 512 MiB（`exec.heavy.memLimitMiB`）、`RLIMIT_CPU` = maxRunSec；超时 SIGTERM，10 秒后 SIGKILL。

**核对**：effect_status=unknown → reconciling + reconcile_case；Runner 轻道每 60 秒调领域 `reconcile` 至 auto_until；仍不清 → manual_review_required，进运行中心"需要处理"；2 小时投待办。

**定时**：启动时扫描上次 tick 至今的计划时刻按错过策略处理；`INSERT … ON CONFLICT DO NOTHING`。

**验收要点**：同键同摘要返回原命令、不同摘要冲突；并发提交只产生一个调用；准备后版本变化提交被拒；管家不能产生确认；旧 fencing token 写入被拒；原进程存活时不回收租约；同一计划时刻只放一件；错过不补跑并记账；消息重投不重复处理；不确定不自动重发、不能直接标成功；取消晚于提交如实报告；重道无饥饿；超排队上限明确拒绝。契约测试 `test_contracts_part10.py`。
